## Why this matters

> [!SCENARIO] Everyone is asking "anything new?"
> Three parts of the shop spend their day asking the same question. The image resizer is a timer function that lists the product-images container every minute, looking for new uploads - a minute's delay and a steady trickle of storage transactions for nothing. The secret-rotation job from [lesson 4.6](lesson:4.6) checks Key Vault on a schedule. And the shop's four delivery partners poll `GET /orders?status=shipped` every thirty seconds, which is 200,000 API calls a day, nearly all of them answered "nothing new".
>
> Priya wants the shop to be told when something happens, instead of asking all day.

## Push, not poll

Polling costs twice: work when nothing has changed, and delay when something has. The alternative is for the thing that changed to announce it, and for anyone interested to be called.

**[Azure Event Grid](gl:azure-event-grid)** is that announcement service. A **source** publishes a small event to a **topic**; an **[event subscription](gl:event-subscription)** on the topic filters events and **pushes** each match to a **handler** - a function, a webhook, a Service Bus queue, a Logic App - usually within a second. The source knows nothing about the handlers, so adding one is just adding a subscription.

## Where events come from

- **[System topics](gl:system-topic)** carry events that Azure services raise about themselves: a blob created or deleted, a secret nearing expiry, a resource group changed, an image pushed to Container Registry, a Premium Service Bus queue with messages waiting and no listener. You do not publish these; you subscribe to them.
- **[Custom topics](gl:custom-topic)** carry your own application's events, such as `OrderShipped`, published over HTTPS by your code with a managed identity.
- **Partner topics** carry events from SaaS providers that integrate with Event Grid, so a third party's changes arrive the same way as Azure's.

Events are **notifications, not payloads**. A `BlobCreated` event says which blob, how big and when - not its contents. `OrderShipped` should carry the order ID, the carrier and a URL, and the handler fetches anything else it needs. Small events stay cheap, fast and safe to fan out.

For new work, publish in the **[CloudEvents](gl:cloudevents)** format - an open standard with `id`, `source`, `type`, `subject`, `time` and `data` - rather than Event Grid's older schema, so any tool that speaks CloudEvents can read them.

## Subscriptions, filters and delivery

Each event subscription chooses what it receives and how it is delivered.

**Filters** select by event type (`Microsoft.Storage.BlobCreated`), by **subject** prefix or suffix (`/containers/product-images/`, `.jpg`), or by values inside the event data. Filtering at the subscription means handlers are only called for what they care about.

**Retries** are automatic. If a handler fails or does not answer, Event Grid retries with exponential back-off for up to 24 hours by default. After that the event is dropped - unless the subscription has a **dead-letter destination**, a blob container where undeliverable events are saved. ==Every event subscription that matters gets a dead-letter container, because without one a handler that is down for a day silently loses a day of events.==

Delivery is **at least once and in no particular order**, like every broker in [lesson 5.1](lesson:5.1). Handlers must be idempotent, should answer quickly and do slow work afterwards, and must not assume `OrderShipped` arrives after `OrderPacked`.

## Webhooks to partners

The shop replaces partner polling with a **[webhook](gl:webhook)** per partner: an event subscription on `shop-events` that POSTs `OrderShipped` to the partner's HTTPS endpoint. Two checks make that safe:

1. **Endpoint validation.** Before delivering anything, Event Grid performs a handshake that the endpoint must answer, proving the owner asked for these events. That stops anyone pointing your events at a victim's server.
2. **Authenticity.** The partner must know a call really came from the shop. Event Grid can deliver with an Entra ID token, or with a secret header you configure, which the partner checks on every call.

Partner endpoints go down. With a dead-letter container, a partner who was offline for a weekend can be sent Monday's backlog, not told it is gone.

## Event Grid or Service Bus?

They sound alike and do different jobs.

| | Event Grid | Service Bus |
|---|---|---|
| Carries | Notifications that something happened | Business messages that must be processed |
| Delivery | Pushed to the handler | Pulled by the consumer, with a lock |
| Ordering, sessions, transactions | No | Yes |
| When a consumer is down | Retries up to 24 hours, then dead-letters or drops | Waits in the queue until read, with no deadline |
| Cost | First 100,000 operations a month free, then about $0.60 per million | About $10 a month plus operations |

A common pattern combines them: an Event Grid subscription pushes into a Service Bus queue, so a reaction that must not be lost gets Service Bus's durability, and the consumer reads at its own pace. The shop does exactly that for its internal shipping-notification service.

## In practice

The shop now uses a system topic on `stshopimages` with a subscription filtered to `BlobCreated` in `/containers/uploads/`, pushing to the resize function, which writes to `product-images`. Key Vault's system topic drives rotation. A custom topic `shop-events` carries `OrderShipped`, with one webhook subscription per partner and one into a Service Bus queue. Every subscription has a dead-letter container, and there is an alert on dead-lettered events. The partners' 200,000 daily polls become about 3,000 pushed events.

**What it costs.** At the shop's volume, Event Grid is inside the free allowance or pennies a month.

**What breaks.**

- **The loop.** A resize function that writes its output to the container it watches triggers itself for ever. Watch `uploads`, write to `product-images`, or filter by suffix.
- **No dead-letter destination.** A handler down for more than a day loses events without a trace.
- **Slow handlers.** A webhook that takes too long to answer is retried, and the partner processes duplicates. Acknowledge, then work.
- **Payload creep.** Events that carry whole orders leak data to every subscriber and break when the order grows. Send IDs and URLs.
- **Assuming order.** Two events for one order can arrive either way round; design the handler to cope.

## Map it to what you know

| You already know | On Event Grid |
|---|---|
| Stripe or GitHub webhooks calling your API | Exactly this model; now the shop sends them |
| `FileSystemWatcher` on a shared folder | A `BlobCreated` subscription on a container |
| A SQL Server trigger reacting to an insert | A system event reacting to a change in an Azure service |
| A cron job asking "anything new?" | A subscription that is told |
| AWS EventBridge | Event Grid |

## Guiding your team

> [!TEAM]
> Whenever a design polls, ask:
>
> 1. **Could the source tell us instead?** If it is an Azure service, it probably already can.
> 2. **Is this a notification or work that must not be lost?** Notifications stay on Event Grid; durable work goes into a Service Bus queue.
> 3. **Where do undelivered events go?** Every important subscription has a dead-letter container and an alert.
> 4. **What exactly is in the event?** IDs and URLs, not the whole record.
> 5. **How does the receiver know the call is genuine, and what happens when it sees the event twice?**

## Key takeaways

- Event Grid pushes small notifications from sources to handlers within a second, so systems react instead of polling.
- System topics carry Azure's own events; custom topics carry yours; subscriptions filter by type, subject or data.
- Events are notifications with IDs and URLs; handlers fetch what they need. Prefer the CloudEvents schema.
- Delivery is at least once, unordered, retried for up to 24 hours - and then dropped unless a dead-letter container is set.
- Webhooks need endpoint validation and a way for the receiver to verify the sender.
- Event Grid for reacting, Service Bus for processing; push Event Grid into a Service Bus queue when a reaction must not be lost.
