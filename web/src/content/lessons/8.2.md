## Why this matters

> [!SCENARIO] The prototype on a personal credit card
> Dev's product-description script works. It calls OpenAI's public API with a key on his personal card, sends each product's supplier spreadsheet row, and writes back a tidy paragraph. It uses the biggest model available "to be safe".
>
> Then three things happen in one week. Legal asks where the product data and, for the assistant, customer messages are processed, and whether they train someone's model. The script dies after 2,000 products with `429 Too Many Requests`. And Finance does the arithmetic on 40,000 products at flagship prices.
>
> Priya needs to answer three questions properly: which provider, which model, and which kind of deployment.

## Azure OpenAI and Foundry Models

**[Azure OpenAI](gl:azure-openai)** runs OpenAI's models - the GPT family, the reasoning models, embeddings, image and audio models - inside Azure. The API is the same shape as OpenAI's, and the official OpenAI SDKs work against it. What changes is the contract:

- **Your data stays yours.** Prompts and outputs are not used to train models and are not sent to OpenAI.
- **Azure controls apply**: Microsoft Entra ID and [managed identities](gl:managed-identity) instead of keys, [private endpoints](gl:private-endpoint), Azure Policy, an SLA, and a bill on your Azure invoice.
- **You choose where processing happens**, which is how you meet [data residency](gl:data-residency) commitments.

Azure OpenAI is now one family inside **[Foundry Models](gl:foundry-models)**, the catalogue in Microsoft Foundry. Next to OpenAI's models it offers models sold directly by Azure, including Meta's Llama, Mistral, DeepSeek, xAI's Grok and Microsoft's small Phi models, plus partner models such as Anthropic's Claude and thousands of open models from Hugging Face. Most run as pay-per-token endpoints that Microsoft hosts. Some can instead be deployed on managed compute you pay for by the hour.

==Pick the provider for the contract, then the model for the task.== For almost every organisation already on Azure, the answer to Legal's question is "a model in our own Azure subscription, in a data zone we chose".

## Choosing a model

| Kind of model | Good at | Cost and speed |
|---|---|---|
| **Flagship** (the largest GPT and similar) | Hard reasoning, long and messy documents, subtle writing | Most expensive, slowest |
| **Small** (mini, nano, Phi) | Classification, extraction, short drafting, high volume | Often ten times cheaper or more, fast |
| **Reasoning** models | Multi-step problems such as planning, maths and code | Slower; they spend hidden "thinking" tokens you pay for |
| **Embedding** models | Turning text into vectors for search ([lesson 8.5](lesson:8.5)) | Very cheap |
| **Open-weight** (Llama, Mistral, Phi) | Control, running on your own compute or offline | Varies; you may run the hardware |

The rule: ==start with the smallest model that passes your evaluation, and move up only when it fails.== A product description from a spreadsheet row is a small-model job.

## Tokens, context and prompts

Models read and write **[tokens](gl:token)**: pieces of words, roughly four characters or three-quarters of a word each. You pay for input and output tokens separately, and output costs several times more than input. Small models cost cents per million input tokens; flagship models cost a few dollars.

Every call has a **[context window](gl:context-window)**: the most tokens the model can take in and give back in one call. That is anywhere from about 128,000 tokens to over a million. A big window is not free memory. You pay for every token you send on every call, and models pay less attention to material buried in the middle of a long prompt.

A chat request is a list of messages. The **[system prompt](gl:system-prompt)** comes first: the role, the rules, the tone and the output format ("Write 80-120 words in British English. Never invent materials. Return JSON matching this schema."). The user's message follows. Because the model is stateless, a chat app resends the whole conversation on every turn, so a long conversation costs more with every message. Two settings matter often: **temperature** (low for extraction, higher for creative copy) and **structured outputs**, which make the model return JSON that matches a schema your code can trust.

The deployment type decides where requests are processed and how you pay. Stored data stays in the resource's geography whichever type you choose.

| Deployment type | Processed in | You pay | Use for |
|---|---|---|---|
| **Global Standard** | Any Azure region worldwide | Per token | Most workloads without residency limits; highest default quota |
| **Data Zone Standard** | Within the EU or within the US | Per token | Personal data under GDPR or similar rules |
| **Standard** (regional) | The resource's region | Per token | Strict single-region requirements |
| **Global Batch / Data Zone Batch** | As above, within 24 hours | Per token, about half price | Bulk jobs that can wait |
| **Provisioned** (global, data zone or regional) | As above | Per reserved unit, hourly or reserved | Steady high volume needing predictable latency |

Capacity is **[tokens per minute](gl:tokens-per-minute)** (TPM). Each subscription has a TPM quota per model, per region and per deployment type, and you share it out among deployments. Go over it and the service returns 429 with a `retry-after` header. That is exactly what stopped Dev's script, which never retried.

**[Provisioned throughput units](gl:provisioned-throughput-unit)** (PTUs) reserve model capacity instead. Latency is predictable and the price is fixed whether you use it or not, with big discounts for monthly or yearly reservations. They pay off for steady, heavy traffic, usually costing thousands a month. A common pattern is PTUs for the baseline, with overflow spilling to a Standard deployment.

## Fine-tuning comes last

**[Fine-tuning](gl:fine-tuning)** retrains a model on your examples. It is good for teaching a consistent *style or format*, and for getting a small model to do a narrow task as well as a big one. It is poor at teaching *facts*: they go stale, and the model still invents things. Work in this order: improve the prompt, then add retrieval ([lesson 8.5](lesson:8.5)), and fine-tune only if both fall short. A fine-tuned model also carries an hourly hosting charge while it is deployed.

## In practice

Priya's decisions:

- **Everything moves into a Foundry resource in Sweden Central** in the company subscription. Apps call it with managed identities, and key-based access is switched off.
- **Descriptions**: a small model on **Global Batch**. The input is product data with nothing personal in it, so global processing is fine. Around 30 million input and 10 million output tokens comes to tens of dollars, not the hundreds the flagship would have cost. A merchandiser approves each description before it is published.
- **Assistant**: **Data Zone Standard (EU)**, because customers type names, addresses and order numbers into it.
- **429s**: retry with backoff that honours `retry-after`, move bulk work to batch, and request more quota only once real usage shows the need.
- **Pinned versions**: each deployment names its model version, and upgrades go through evaluation ([lessons 8.7](lesson:8.7) and [8.8](lesson:8.8)).

**What breaks.**

- **The flagship for everything**, at ten or more times the price, when a small model would pass.
- **Unbounded chat history**: every turn costs more, until the conversation hits the context limit.
- **API keys in config files**, shared across apps and never rotated.
- **Global processing of personal data** because it had the most quota.
- **Fine-tuning to teach the product catalogue**, which is stale by next week.

## Map it to what you know

| You already know | In Azure OpenAI |
|---|---|
| A connection string and a database name | The endpoint and the deployment name |
| A third-party API's rate limit (Stripe, GitHub) | TPM quota and 429 with `retry-after` |
| SQL Server Standard vs Enterprise per core | Small vs flagship model, priced per token |
| Reserved capacity or a reserved VM instance | Provisioned throughput units |
| `appsettings.json` checked into the repo | The system prompt, versioned with the code |
| Parsing free text with a regex | Structured outputs: JSON that matches a schema |

## Guiding your team

> [!TEAM]
> For every model call in a design:
>
> 1. **Which deployment type, and does it match the data's residency?**
> 2. **Is this the smallest model that passes our evaluation?** Show the comparison.
> 3. **How many tokens per request, times how many requests?** That is the bill.
> 4. **What happens on a 429?** Retry, batch, or queue.
> 5. **Is the model version pinned, and who owns upgrades?**

## Key takeaways

- Azure OpenAI runs OpenAI's models under Azure's contract: your data is not used for training, you get Entra ID, private networking and a region you choose. It sits within Foundry Models, next to Llama, Mistral, DeepSeek, Grok, Phi and partner models.
- Start with the smallest model that passes evaluation; flagship and reasoning models cost many times more.
- You pay per token, in and out; chat history is resent every turn, and a large context window is not free.
- You call a deployment, not a model. Its type sets where requests are processed and how you pay: Global, Data Zone, Standard, Batch or Provisioned.
- TPM quota causes 429s: retry with backoff, batch bulk work, and buy PTUs only for steady heavy traffic.
- Prompt first, retrieval second, fine-tuning last. Fine-tuning teaches style and format, not facts.
