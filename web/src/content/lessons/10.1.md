## Why this matters

> [!SCENARIO] The Monday report that slowed checkout
> Every Monday at 08:30 the finance director's trading pack refreshes. It joins fourteen months of orders, order lines, returns and products in one query that runs for eleven minutes. Marketing's Monday email goes out at 08:00, so the report and the busiest hour of the week arrive together. Last Monday checkout went from 300 milliseconds to four seconds, the orders database sat at 100% CPU, and baskets were abandoned until Dev found the query.
>
> Priya bans reporting against production that afternoon. Tom, from the data team, has run SQL Server reporting for fifteen years, and his first answer is a replica. But finance's next request already wants three years of history, stock from the warehouse system and the clickstream. Where should analytics live?

[Lesson 3.7](lesson:3.7) pointed at the door to analytics. This module walks through it, and this lesson is the map.

## Why the report hurts the shop

The orders database is an [OLTP](gl:oltp) system: many small, fast transactions. The trading pack is [OLAP](gl:olap) work: a few huge scans over history. Azure SQL Database has read committed snapshot on by default, so the report rarely blocks checkout with locks. It hurts more quietly: it takes the CPU, pushes the pages checkout needs out of memory, and spills sorts to tempdb.

Tom's first move is right. On Business Critical and Premium, [read scale-out](gl:read-scale-out) gives a readable replica at no extra cost: add `ApplicationIntent=ReadOnly` to the connection string. General Purpose has no such replica, but an [active geo-replication](gl:active-geo-replication) secondary does the job. Northline already has one: the [failover group](gl:failover-group) from [lesson 3.2](lesson:3.2) keeps a readable secondary in UK West. The report had simply been pointed at the read-write listener.

==A readable replica is the right first step: it takes reports off the primary today, for little or no extra cost.==

It stops being enough when any of these appear:

- **The schema fights the question.** The replica is an exact copy, tuned for checkout. Any index the report needs must be built on the primary, where it slows every write.
- **History is missing.** When a customer moves region, the row is overwritten, and last year's regional revenue quietly changes.
- **The question spans sources.** Stock sits in the on-premises warehouse system, clicks in the data lake, campaigns in a marketing tool. A replica of one database cannot join them.
- **Every report defines its own "revenue".** A replica has nowhere to hold a shared definition.
- **Long queries fight replication.** A query that holds up replication can be cancelled.

## Lake, warehouse and lakehouse

| | Data warehouse | Data lake | Lakehouse |
|---|---|---|---|
| Holds | Tables in a fixed schema | Files of any shape: CSV, JSON, Parquet | Lake files in an open table format, read as tables |
| Good at | Fast, trusted SQL | Cheap storage, raw history, any engine | Both: cheap open files with transactions and SQL |

A **[data warehouse](gl:data-warehouse)** is the star schema Tom has built on SQL Server for years. A **[data lake](gl:data-lake)** is files in cheap object storage: on Azure, a storage account with [hierarchical namespace](gl:hierarchical-namespace), where [Event Hubs Capture](gl:event-hubs-capture) already writes the clickstream as Parquet ([lesson 5.4](lesson:5.4)). A **[lakehouse](gl:lakehouse)** adds an open table format over those files. A transaction log turns folders of Parquet into real tables with transactions and updates, and SQL and Spark read the same copy. Fabric and Databricks are both built on this idea.

Loading has changed too. The SSIS habit was [ETL](gl:etl): transform in flight, load only the clean result. With cheap storage and elastic compute, the norm is **[ELT](gl:elt)**: land the raw data first, then transform it inside the platform, so a corrected transformation can be rerun over all of history. Most of it is **[batch processing](gl:batch-processing)**: scheduled jobs over last night's orders or the last hour's clicks. Streaming ([lesson 10.5](lesson:10.5)) is for questions that cannot wait minutes. Finance's Monday pack can wait.

### The medallion layers

A lakehouse is usually organised as a **[medallion architecture](gl:medallion-architecture)**: three layers, each built from the one before.

- **Bronze**: raw, as landed, append-only. Nobody edits it. It is the replay button.
- **Silver**: cleaned and conformed. Duplicates removed, times in UTC, one customer key across shop and loyalty, test orders gone.
- **Gold**: business-ready. Star schemas and agreed measures, with "net revenue" defined once.

## In practice

**This week: repoint the report.** The trading pack moves to the failover group's read-only listener. Checkout is safe by Tuesday, at no new cost, because the UK West secondary is already paid for as disaster recovery. One risk: a report heavy enough to slow replication also widens the recovery point.

**This quarter: a platform.** Tom picks Fabric: Northline is Microsoft-shaped and finance already lives in Power BI. Orders flow into the lake continuously ([lesson 10.3](lesson:10.3)), are layered bronze to gold ([lesson 10.4](lesson:10.4)) and are served through one shared model ([lesson 10.6](lesson:10.6)). What it costs is [lesson 10.2](lesson:10.2).

**What breaks:**

- **A lake with no layers and no owner.** It becomes a swamp, and finance goes back to Excel.
- **No bronze.** A transformation bug cannot be replayed.
- **The OLTP schema copied one-to-one** and called a warehouse. Every report still does eight joins.
- **"Real-time" for a weekly report**, paid for by the hour.

## Map it to what you know

| You already know | In the analytics world |
|---|---|
| An Always On readable secondary for reports | Read scale-out or a geo-replica: the first step |
| An SSIS package transforming in flight | A pipeline that lands raw, then transforms: ELT |
| A staging database | Bronze |
| Conformed warehouse tables and data marts | Silver and gold |
| An SSAS tabular model | A Power BI semantic model |
| A columnstore index | Parquet: columnar files, compressed per column |

## Guiding your team

> [!TEAM]
> When someone asks for a new report or dataset:
>
> 1. **How fresh does it really need to be?** Daily, hourly and seconds are three different price points.
> 2. **Could a read-only replica answer it?** One source, current data and no new definitions means the cheapest answer is already running.
> 3. **Which layer does it read from?** Anything below gold means the report is doing the cleaning itself.
> 4. **Who owns the definition of each gold measure?** "Revenue" with no owner becomes forty revenues.
> 5. **Can we rebuild silver and gold from bronze today?** If not, the next transformation bug is permanent.

## Key takeaways

- Reporting on the orders database competes with checkout for CPU, memory and tempdb. Move it off the primary first.
- A readable replica is the right first step. It stops being enough when you need history, several sources or shared definitions.
- A warehouse is structured and trusted, a lake is cheap and raw, and a lakehouse adds tables and transactions to lake files. ELT lands raw, then transforms.
- Bronze is raw and replayable, silver is cleaned, gold is business-ready. Reports read gold only.
- Fabric is the default platform; Data Factory moves data, Power BI serves it, Purview governs it, Databricks is the Spark-first alternative, and Synapse is the previous generation.
