## Why this matters

> [!SCENARIO] "Could that happen to us?"
> A competitor loses two million customer records. The write-up is depressingly ordinary: a developer was phished, the attacker used a pipeline secret found on his laptop to reach a dev VM, the dev network was peered to production "for convenience", and the production database trusted anything on the internal network. Nobody noticed for five weeks.
>
> The shop's board asks Priya one question at the next meeting: could that happen to us?
>
> Seven lessons have given her the parts. Now she needs to put them together into one picture she can defend, walk an attacker through it step by step, and name what still depends on luck.

## Zero trust in three sentences

The old model was a castle: a strong perimeter, and everything inside the network trusted. The competitor's breach is what that model looks like when one thing inside goes wrong. **[Zero trust](gl:zero-trust)** replaces it with three principles:

| Principle | Means | On Azure |
|---|---|---|
| **Verify explicitly** | Every request is authenticated and authorised using every signal - identity, device, location, risk - wherever it comes from | Entra ID tokens, MFA and Conditional Access ([4.4](lesson:4.4)); APIs that check every token |
| **Use least privilege** | Just enough access, just in time | Scoped roles, data-plane roles, PIM, managed identities ([4.5](lesson:4.5)) |
| **[Assume breach](gl:assume-breach)** | Design as if an attacker is already inside: limit what one foothold reaches, and make sure you would notice | Segmented networks, private endpoints, encryption, alerts to people ([4.1](lesson:4.1), [4.3](lesson:4.3), [4.7](lesson:4.7)) |

==Zero trust is not a product you buy; it is the rule that being on the network earns nothing, so every request proves who it is and every foothold is kept small.==

It works alongside **[defence in depth](gl:defence-in-depth)**: independent layers - identity, edge, network, application, data, monitoring - so that when one fails, and one eventually will, the next still holds.

Now walk the competitor's attacker through it, one step at a time:

| The attacker tries to... | What stops it | Lesson |
|---|---|---|
| Phish a developer's password | MFA with passkeys; Conditional Access requires a managed device for admin apps | [4.4](lesson:4.4) |
| Use a pipeline secret from the laptop | There is none: GitHub deploys through workload identity federation, scoped to one resource group | [4.5](lesson:4.5) |
| Pivot from a dev VM into production | Dev and prod are separate spokes with no peering between them; dev identities hold no prod roles | [4.1](lesson:4.1), [4.5](lesson:4.5) |
| Reach the database from inside the network | Private endpoint only, and the database trusts Entra identities, not network location | [4.3](lesson:4.3) |
| Hit the API directly, around the WAF | The origin accepts only Front Door's traffic | [4.2](lesson:4.2) |
| Use a compromised API instance to copy every blob | Its identity reads one container; a private endpoint cannot reach other accounts | [4.5](lesson:4.5), [4.3](lesson:4.3) |
| Delete the backups before encrypting | PIM means no standing Owner; soft delete, purge protection and vault multi-user authorisation | [4.5](lesson:4.5), [4.6](lesson:4.6), [3.6](lesson:3.6) |
| Stay unnoticed for five weeks | Defender alerts routed to an on-call phone within minutes | [4.7](lesson:4.7) |

That is defence in depth made concrete: every row has an answer, and no row depends on another row holding.

## Threat modelling: doing this for every design

The table above is a **[threat model](gl:threat-modelling)**, and it should exist for every workload before it ships, not after a competitor's breach. The method fits in a design review:

1. **Draw the data flows** - who and what talks to what, over which protocol.
2. **Mark the trust boundaries** - internet to Front Door, app to database, staff to admin portal, pipeline to Azure.
3. **For each flow across a boundary, ask what can go wrong.** The **STRIDE** prompts help: **S**poofing an identity, **T**ampering with data, **R**epudiation (no record of who did it), **I**nformation disclosure, **D**enial of service, **E**levation of privilege.
4. **Decide a mitigation, an owner and a date** for each - or accept the risk in writing.

Microsoft's free Threat Modeling Tool draws the diagram and suggests threats; a whiteboard works as well.

## In practice

The shop's one-page **minimum bar** for any new workload:

| Layer | The minimum |
|---|---|
| Identity | Entra ID sign-in with MFA; managed identities or federation for code; no stored passwords or long-lived secrets |
| Access | Roles for groups at resource-group scope; data-plane roles on specific resources; admin rights through PIM |
| Edge | Front Door with WAF for anything public; origin accepts only Front Door |
| Network | Private endpoints with public access disabled for data; NSGs denying by default; no public management ports |
| Data | Encryption at rest (default) and TLS 1.2 or later; backups tested by restore; soft delete and purge protection |
| Operations | Defender plans where the data is; alerts to on-call; Azure Policy in Deny for the rules above |
| Application | Authorisation checked in code on every request; parameterised queries; dependencies patched - the OWASP Top 10 is still yours |

**What it costs.** For the shop, roughly $1,100 a month: Front Door Premium, Entra ID P1 and a few P2 licences, Defender plans, private endpoints, the DNS resolver, the VPN gateway and Bastion. The competitor's breach cost more than the shop's annual revenue.

**What breaks.**

- **Zero trust as a purchase.** A vendor sells "zero trust" in a box; the internal network is still trusted.
- **Security that blocks delivery.** When the secure path is slow, people build around it. Make it the easy path: templates and landing zones ([Module 9](module:9)) that come secure by default.
- **Exceptions without expiry.** One temporary public endpoint becomes permanent. Every exemption has an owner and an end date.
- **Trusting the VNet.** "It is only reachable internally" is the competitor's sentence. Internal callers authenticate too.
- **Forgetting the application.** Every Azure control in this module is powerless against an API that forgets to check whether this user may see that order.

## Map it to what you know

| You already know | Zero-trust version |
|---|---|
| The corporate LAN and VPN: inside means trusted | Every request authenticates, wherever it comes from |
| The DMZ in front of the web servers | Front Door and its WAF, with the origin locked to it |
| "Only the app server can reach SQL" by firewall rule | Private endpoint plus Entra identity: network and identity both required |
| A security checklist at the end of the project | A threat model at the design review |
| OWASP Top 10 in code review | Still yours - no Azure service fixes broken authorisation |

## Guiding your team

> [!TEAM]
> For every workload, before it ships, ask:
>
> 1. **Where is the threat model, and who owns each mitigation?** A diagram with trust boundaries, and a name and date per row.
> 2. **If one developer's laptop is compromised today, what can the attacker reach?** The answer should be "their own dev resources, briefly".
> 3. **Which requests are trusted because of where they come from, rather than who sent them?** Each one is a gap.
> 4. **Does this meet the minimum bar, and which exceptions have end dates?**
> 5. **How would we know within an hour?** Name the alert and the person.

## Key takeaways

- Zero trust: verify explicitly, use least privilege, assume breach. Being on the network earns nothing.
- Defence in depth means independent layers, so that one failure is an incident rather than a breach.
- Walk an attacker through the design step by step; every step should meet a control from a different layer.
- Threat model every workload at design review: data flows, trust boundaries, STRIDE, and a mitigation with an owner.
- Keep a one-page minimum bar and make the secure path the easy one, with expiring exceptions.
- Azure secures the platform around your code; authorisation and input handling in the code are still yours.
