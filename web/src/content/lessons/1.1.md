## Why this matters

> [!SCENARIO] The Black Friday that nearly broke the shop
> Priya runs engineering at a mid-sized retailer. The web shop is a React front end, a Node API and a SQL Server database, all on four servers in a rack the company bought three years ago. Last November the marketing team ran a promotion that went viral. Traffic hit twelve times the usual peak. The servers could not be made bigger in an afternoon, the checkout timed out for two hours, and the finance team asked why they were paying for servers that sat at 8% utilisation for the other 364 days of the year.
>
> Priya's board has one question: "Why are we still running our own servers?"

That question is the whole reason cloud computing exists. This lesson gives you the vocabulary to answer it properly - and to say, honestly, when the answer is "we should not move".

## What "cloud" actually means

**Cloud computing** is renting computing resources - servers, storage, networks, databases, and increasingly whole services - from a provider, over the internet, and paying only for what you use. The provider owns the buildings, the hardware and the power; you get an API and a portal.

Five properties separate real cloud from "someone else's data centre":

| Property | What it means in Priya's world |
|---|---|
| **On-demand self-service** | A developer creates a database from a portal or a script in minutes. No ticket to a hardware team, no purchase order. |
| **Broad network access** | Everything is reachable over standard protocols from anywhere - a laptop, a phone, a CI pipeline. |
| **Resource pooling** | Microsoft runs millions of servers shared across customers. You never see a physical machine. |
| **Rapid elasticity** | Capacity grows and shrinks with demand. Twelve times the traffic means twelve times the instances - then back down on Saturday night. |
| **Measured service** | Every second of compute and every gigabyte is metered and shows up on a bill. That is a feature: cost becomes visible. |

==Cloud is not "cheaper hosting". It is turning capacity from something you buy into something you rent by the minute.==

## The money: CapEx versus OpEx

Priya's four servers were **capital expenditure (CapEx)**: a large up-front purchase, depreciated over years, sized for a peak that happens once a year. Cloud is **operational expenditure (OpEx)**: a monthly bill that tracks actual use.

| | On-premises (CapEx) | Cloud (OpEx) |
|---|---|---|
| When you pay | Up front, before the first user | After the fact, for what ran |
| Sizing | For the worst day you can imagine | For today, adjusted tomorrow |
| Trying something new | Weeks of procurement | Minutes, and delete it if it fails |
| Idle capacity | You paid for it anyway | Costs nothing if it is switched off |
| The risk | Over-buying, or under-buying | Forgetting to switch things off |

The last row matters. Cloud cost is a behaviour problem, not a pricing problem. [Lesson 1.6](lesson:1.6) covers the tools that keep it honest.

## Elasticity, scale and the shape of demand

Two words get mixed up constantly:

- **Scalability** is the *ability* to handle more load by adding resources. Scaling **up** means a bigger machine; scaling **out** means more machines.
- **Elasticity** is doing that *automatically and in both directions* as demand changes.

A cloud platform gives you both; the point is that you rarely have to think about the physical side. Here is Priya's shop before and after, drawn with the real Azure icons you will see throughout this course:

## Economies of scale and the hyperscalers

Microsoft, Amazon and Google each run data centres at a size no single company could justify. Buying power, custom hardware, automated operations and energy deals mean their cost per unit of compute is far lower than a company rack - and, because they compete, some of that saving is passed on. These three are the **hyperscalers**.

| | Strengths people cite | Where you meet it |
|---|---|---|
| ![Azure](az:globe) **Microsoft Azure** | Deep integration with Microsoft 365, Entra ID, Windows, SQL Server and .NET; strong hybrid story; enterprise agreements | Organisations that already run on Microsoft |
| **Amazon Web Services** | First mover, the largest catalogue, the most third-party tooling | Start-ups, and estates that began before 2015 |
| **Google Cloud** | Data, analytics and Kubernetes heritage | Data-heavy and container-first teams |

Be honest with stakeholders: AWS holds the largest market share. Azure is a strong second and grows fastest inside organisations that already pay Microsoft for Office, identity and Windows licences.

## Why Azure, specifically

For Priya the answer is practical, not ideological:

1. **Identity is already there.** Her staff sign in with Microsoft 365, which means they already have a [Microsoft Entra ID](gl:microsoft-entra-id) tenant. Azure uses the same identity for everything, from the portal to the database.
2. **SQL Server has a home.** ![Azure SQL](az:azure-sql) Azure SQL Database is SQL Server run by Microsoft. Her schema, her T-SQL and most of her tooling move as they are.
3. **Licensing carries over.** Azure Hybrid Benefit lets existing Windows Server and SQL Server licences reduce the cloud bill.
4. **The tooling is familiar.** Visual Studio, VS Code, GitHub and Azure DevOps all treat Azure as the default target.
5. **Hybrid is expected, not tolerated.** Azure assumes some things stay on-premises for years and gives you the networking and management to run both as one estate.

None of these make Azure "better" in the abstract. They make it the lowest-friction choice for a Microsoft-shaped organisation - which is most of the enterprises you will work with.

## When *not* to move

A lead earns trust by knowing the counter-cases:

- **Steady, predictable, fully depreciated workloads** with no growth can be cheaper to leave alone for now.
- **Data that legally cannot leave a site** (some defence, healthcare and government work) - though Azure has sovereign and on-premises options, covered later.
- **Latency-critical systems** talking to factory equipment on the same floor.
- **A team with no cloud skills and no time to learn** - the technology will not fix that, and the bill will show it.

> [!WARNING] The lift-and-shift trap
> Copying four on-premises servers to four cloud virtual machines, one to one, is the most common first move and usually the most expensive way to run in the cloud. You keep all the patching and none of the elasticity. Better options appear in [Module 2](module:2).

## Map it to what you know

| You already know | The cloud equivalent |
|---|---|
| Renting a shared host or a VPS for a side project | Same idea, but the whole data centre is on demand, with an API for everything |
| `npm install` pulling a package instead of writing it | Consuming a managed database or queue instead of installing and patching one |
| A React component tree re-rendering only what changed | Elasticity: only the tier under pressure scales |
| SQL Server on a box you own | Azure SQL Database, where Microsoft owns the box and the patching |
| Waiting weeks for a new server | Waiting minutes for a resource, then deleting it in one command |

## Guiding your team

> [!TEAM]
> When someone proposes "moving to the cloud", ask:
>
> 1. **Which workloads, and why those?** Bursty, growing or new workloads gain the most; steady old ones the least.
> 2. **Who will own the bill?** Cost visibility is only useful if someone reads it every week.
> 3. **Are we moving servers or moving to services?** Lift-and-shift is a step, not a destination.
> 4. **What stays on-premises, and for how long?** Hybrid is normal; plan for it.
> 5. **What will the team need to learn?** Budget time for it, or the migration stalls.

## Key takeaways

- Cloud computing is renting metered, on-demand, elastic resources from a provider that runs the hardware.
- CapEx buys capacity for the worst day; OpEx pays for the actual day. Cloud cost is a behaviour, not a price list.
- Scalability is the ability to grow; elasticity is growing and shrinking automatically.
- Azure wins on friction for Microsoft-shaped organisations: identity, SQL Server, licensing, tooling and hybrid.
- Know the cases for staying put, and never present lift-and-shift as the end state.
