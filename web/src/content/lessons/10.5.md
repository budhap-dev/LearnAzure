## Why this matters

> [!SCENARIO] Twenty minutes nobody saw
> Last Black Friday a payment provider started declining cards at 10:40. Orders halved. The live dashboard from [lesson 5.4](lesson:5.4) showed clicks climbing nicely, because clicks were fine. Nobody noticed the drop until a customer tweeted at 11:00. At about 1,200 orders an hour, those twenty minutes cost roughly £20,000.
>
> This year marketing wants more: a live view of sessions, baskets and **checkout conversion** (orders placed divided by checkouts started), and an alert the moment conversion falls. They want to ask new questions on the day, not wait for a developer.
>
> Tom owns the data platform now. Should he extend the Stream Analytics job, or move to Fabric?

## Do you really need real time?

Real time is a price point, not a quality. Each row down costs more to build, run and support.

| Freshness | Northline example | Cheapest way to get it |
|---|---|---|
| Daily | Finance's trading pack | Nightly [batch](gl:batch-processing) into gold |
| Minutes to an hour | Stock levels, campaign results | [Mirroring](gl:mirroring) or an hourly copy ([lesson 10.3](lesson:10.3)) |
| Seconds | Conversion during a sale, payment failures | A stream processed as it arrives |

==If nobody will act within minutes of seeing a number, it does not need to be real time.== Most dashboards fail that test. Black Friday conversion passes: someone will phone the payment provider.

So the same data takes two routes, the **[hot path and cold path](gl:hot-path-and-cold-path)**. The hot path processes events within seconds, to watch and alert. The cold path lands every event in the lake for batch processing, history and trusted numbers. Northline already has one: [Event Hubs Capture](gl:event-hubs-capture) writes the clickstream to bronze. The hot path answers "what is happening now?"; the cold path answers "what happened?"

## Two engines for the hot path

**[Azure Stream Analytics](gl:azure-stream-analytics)** (ASA), the service behind lesson 5.4's job, runs a SQL-like query continuously over a stream and pushes results to outputs. It keeps no history: each result is computed, sent and forgotten.

**[Real-Time Intelligence](gl:real-time-intelligence)** is Fabric's workload for data in motion, built from items in a [Fabric workspace](gl:fabric-workspace):

- An **[Eventstream](gl:eventstream)** reads sources such as [Azure Event Hubs](gl:azure-event-hubs), Kafka and database change feeds, then filters, aggregates and routes events with no code.
- An **[Eventhouse](gl:eventhouse)** stores events in KQL databases, indexed by time, and answers [KQL](gl:kql) queries over billions of rows in seconds.
- **KQL querysets** hold saved queries; **Real-Time Dashboards** are tiles over them that refresh every few seconds.
- **[Fabric Activator](gl:fabric-activator)** watches a stream, query or report and acts when a condition holds: a Teams message, an email, a pipeline or a flow.

| | Stream Analytics | Real-Time Intelligence |
|---|---|---|
| Keeps the events | No | Yes, for the retention period you set |
| A new question on the day | Edit the query and restart the job | Write a KQL query over what is already stored |
| Typical outputs | Azure SQL, Cosmos DB, Service Bus, Functions | Dashboards, Power BI, Activator, OneLake |
| Billed by | Streaming units per hour | [Capacity units](gl:capacity-unit) on a Fabric capacity |

==Keep Stream Analytics when an application needs fixed answers computed from a stream; choose Real-Time Intelligence when people need to watch, question and act on the events themselves.==

The Eventhouse engine also exists on its own as **[Azure Data Explorer](gl:azure-data-explorer)** (ADX): a standalone Azure service where you size a cluster and pay by the hour. It suits Azure-native teams without Fabric; on Fabric, the Eventhouse gives you the same engine on capacity you already pay for.

There is a deadline too. Lesson 5.4's dashboard uses Power BI real-time streaming, which is deprecated: from 31 October 2027, ASA jobs with a Power BI output stop.

## Windowing: aggregating a stream

A stream never ends, so "count the orders" has no answer until you say *over which period*. **[Windowing](gl:windowing)** says it. ASA and Eventstream share the same main shapes:

| Window | In plain words | Northline use |
|---|---|---|
| **Tumbling** | Back-to-back, fixed blocks that never overlap. Each event counts once | Orders per minute, for a chart |
| **Hopping** | Fixed blocks that start at a regular step and overlap, so an event can count twice | Conversion over the last 10 minutes, every minute |
| **Sliding** | Produces a result only when an event enters or leaves the window | "Five payment failures within 30 seconds", the moment it happens |

A **session** window groups events separated by less than a gap, such as one shopper's visit.

In an Eventhouse you can store every event and bucket by time at query time instead:

```kusto
Clicks
| where Timestamp > ago(1h)
| summarize starts = countif(Event == "checkout_start"),
            orders = countif(Event == "order_placed") by bin(Timestamp, 5m)
| extend conversion = todouble(orders) / starts
```

That is a tumbling window written as a query, and marketing can change it on Black Friday morning without a redeploy.

## In practice

Tom's design for this year:

- **A new [consumer group](gl:consumer-group), `rti`**, on the `clickstream` hub. Sharing `dashboard` with the ASA job would split the stream between them. The Eventstream connects with the workspace identity, granted the Event Hubs Data Receiver role, not a shared key.
- **The Eventstream drops bot traffic** and loads the rest into a KQL database with 30 days' retention; the lake keeps everything.
- **A Real-Time Dashboard** for marketing, refreshing every 30 seconds: sessions, baskets, conversion by device.
- **An Activator rule:** if 5-minute conversion stays below 40% for ten minutes (it normally sits near 55%), post to the on-call Teams channel and email Dev. An Azure Monitor [alert rule](gl:alert-rule) watches the infrastructure; Activator watches the business number.
- **The ASA job stays** for now: it is cheap and it works. It goes after one sale on the new dashboard, well before October 2027.

**What it costs.** An Eventhouse suspends when idle, but one fed every second is never idle, so it draws capacity around the clock. Northline gives the real-time workspace its own small [capacity](gl:fabric-capacity), so a Black Friday spike cannot [throttle](gl:smoothing-and-throttling) finance's reports. Size it from a week of real traffic.

**What breaks.**

- **Event time versus arrival time.** Phones send events late, in batches. Window on the time the event happened, or a train journey looks like a conversion crash.
- **An alert nobody owns.** An Activator rule with no named recipient and no runbook is just noise.
- **Hot numbers in board packs.** The hot path treats bots and late events differently from gold. Revenue comes from the cold path.

## Map it to what you know

| You already know | In real-time analytics |
|---|---|
| SQL Server StreamInsight, or an Agent job polling every minute | Stream Analytics |
| `GROUP BY DATEADD(minute, DATEDIFF(minute, 0, OrderTime), 0)` | A tumbling window, or `bin()` in KQL |
| Log Analytics queries from [lesson 6.2](lesson:6.2) | Eventhouse: the same KQL, over your own events |
| A SQL Agent alert that sends Database Mail | Activator |

## Guiding your team

> [!TEAM]
> When someone asks for a live dashboard:
>
> 1. **Who acts on this number within minutes, and what will they do?** No action, no real time; a nightly or hourly refresh is cheaper.
> 2. **Which consumer group does it read from?** Two readers sharing one fight over partitions, and each sees only part of the stream.
> 3. **Do we need to ask new questions of stored events, or just compute fixed results?** Stored and queryable means Eventhouse; fixed results into an app can stay on Stream Analytics.
> 4. **Which capacity does it run on, and what does it draw on a sale day?** A busy hot path must not throttle the board's reports.
> 5. **Where does the trusted version of this number come from?** The cold path, so both paths must agree on definitions.

## Key takeaways

- Real time is a price point. If nobody acts within minutes, use batch or mirroring instead.
- The hot path watches and alerts within seconds; the cold path keeps every event for trusted, historical numbers. You usually need both.
- Real-Time Intelligence is Eventstream to ingest, Eventhouse to store and query with KQL, Real-Time Dashboards to watch and Activator to act. Azure Data Explorer is the same engine as a standalone Azure service.
- Stream Analytics computes fixed windowed results and keeps nothing; its Power BI output stops on 31 October 2027. Tumbling windows do not overlap, hopping windows overlap on a schedule, sliding windows report when events enter or leave.
- Give each reader its own consumer group, and give the hot path its own capacity.
