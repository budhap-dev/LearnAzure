## Why this matters

> [!SCENARIO] The £600 box nobody switched off
> Priya's retailer moved almost everything to managed services, but one thing would not move: a fifteen-year-old ERP that ships as a Windows installer and a licence key tied to a machine name. Dev, the ops lead, created a virtual machine for it. He picked `Standard_D8s_v5` "to be safe", attached a 1 TiB Premium SSD, and left the defaults alone.
>
> Three months later finance flagged the line: about £600 a month for a box that runs eight users' order entry between nine and five. Worse, when Dev resized it on a Friday to try something smaller, the change failed because the VM was running. And when he stopped it from inside Windows to save money over Christmas, Azure billed the whole fortnight anyway.
>
> Nothing here was a bug. Every one of these is a default that a team has to know about.

## What you are actually renting

A **virtual machine** is [IaaS](gl:iaas): Microsoft runs the building, the power, the network fabric and the hypervisor. Everything above the hypervisor is yours. Go back to the [shared responsibility model](gl:shared-responsibility-model) in [lesson 1.2](lesson:1.2) and read the line again with a VM in mind.

| Microsoft owns | You own |
|---|---|
| Data centre, power, cooling, physical security | The operating system and its patches |
| The hypervisor and the host hardware | The runtime: Node, .NET, the JVM, IIS |
| The virtual network fabric and storage service | Firewall rules, hardening, antivirus, users |
| Replacing a failed physical host | Backup, monitoring agents, log shipping |

==Choosing a virtual machine means volunteering to patch, harden, back up and monitor an operating system for as long as that machine exists.== That is the real price, and it is not on the invoice.

## Reading a size name

Azure size names look cryptic until you take them apart. `Standard_D4s_v5` reads as: **Standard** tier, **D** family, **4** vCPUs, **s** for premium-storage capable, **v5** generation.

| Family | What it is tuned for | Pick this when |
|---|---|---|
| **B** | Burstable - banks CPU credits when idle | Dev boxes, build agents, low-average-CPU internal tools |
| **D** | General purpose, balanced CPU to memory | The default. App servers, small databases, domain controllers |
| **E** | Memory optimised, roughly 8 GB per vCPU | SQL Server, caches, anything that wants RAM more than cores |
| **F** | Compute optimised, high clock per GB | Batch jobs, encoding, CI agents, chatty APIs |
| **L** | Storage optimised, big local NVMe | Cassandra, Elasticsearch data nodes, heavy local I/O |
| **N** | GPU | Model training and inference, rendering, CAD workstations |

Later generations are usually cheaper for the same work, so `v5` or `v6` beats `v3` on price-performance almost every time. Prices and exact specifications in this lesson are illustrative and change by region and month - re-run the [pricing calculator](gl:azure-pricing-calculator) before you quote a number.

Dev's mistake was not the family. `D` was right for an ERP. Eight vCPUs for eight users was not: a `D2s_v5` would have cost about a quarter as much.

## Disks

A VM has one **OS disk** and zero or more **data disks**, all [managed disks](gl:managed-disk) - Azure looks after the replication underneath. It also has a **temporary disk** (usually `D:` on Windows), which is local to the host, fast, and wiped whenever the VM moves. Never put anything you care about there.

| Tier | What it is for | Rough IOPS ceiling |
|---|---|---|
| **Standard HDD** | Backups, archives, noise. Cheapest, slowest | ~500 |
| **Standard SSD** | Dev and test, light web servers | ~6,000 |
| **Premium SSD** | Production OS and data disks; required for the single-VM SLA | ~20,000 |
| **Premium SSD v2** | Production where you want to buy size and IOPS separately | ~80,000 |
| **Ultra Disk** | SAP HANA, top-tier databases, sub-millisecond latency | ~400,000 |

> [!WARNING] Two ceilings, not one
> Disk throughput is capped by **both** the disk tier and the VM size. A `D2s_v5` with an Ultra Disk will not go fast: the VM's own I/O limit stops it first. If storage feels slow, check the VM size before you buy a bigger disk.

[Ephemeral OS disks](gl:ephemeral-os-disk) are a useful trick: the OS disk lives on the host's local storage, costs nothing extra, boots faster - and is destroyed if the VM is reallocated. Perfect for stateless scale set instances, wrong for anything that keeps state.

## Images, and getting a machine to be useful

You start from a **[VM image](gl:vm-image)**: a Marketplace image (Windows Server 2022, Ubuntu 24.04, a vendor appliance) or one you built yourself with your agents, hardening and runtime baked in. An [Azure Compute Gallery](gl:azure-compute-gallery) stores that golden image with versions and replicates it across regions and subscriptions, so every team builds from the same base.

**[VM extensions](gl:vm-extension)** finish the job at boot: run a custom script, install the Azure Monitor agent, join a domain, configure Desired State Configuration. Between an image and extensions, a new VM should be useful with no human logging in.

## Staying up

A single VM is a single point of failure. Azure's [SLA](gl:sla) reflects that ([lesson 1.7](lesson:1.7)): roughly 99.9% for one VM on Premium SSD, and no SLA at all on Standard HDD.

| Approach | What it protects against | Rough SLA |
|---|---|---|
| One VM, Premium SSD | Nothing but host repair | ~99.9% |
| **[Availability set](gl:availability-set)** (2+ VMs) | Rack failure and host patching *inside one data centre* | ~99.95% |
| **[Availability zones](gl:availability-zone)** (2+ VMs, 2+ zones) | Loss of a whole data centre | ~99.99% |

An availability set spreads instances across **[fault domains](gl:fault-domain)** (separate racks, power and switches) and **[update domains](gl:update-domain)** (reboot groups Azure patches one at a time). Zones go further, spreading across physically separate data centres in the same [region](gl:region) - the concept from [lesson 1.3](lesson:1.3).

The answer for anything stateless is a **[virtual machine scale set](gl:virtual-machine-scale-set)**: N identical VMs from one image, behind a load balancer, across zones, with [autoscale](gl:autoscale) rules and rolling upgrades.

Two orchestration modes exist. **Flexible** is the modern default: instances are ordinary VMs you can manage individually, and it is what you should choose. **Uniform** is the older mode, optimised for large fleets of truly identical instances.

## What it costs, and the deallocation trap

Compute bills per second while the VM is **allocated** - that is, while Azure is holding hardware for it.

- **Stopping from inside the OS** (`shutdown`, or the Windows Start menu) leaves the VM allocated. **You keep paying.**
- **[Deallocating](gl:deallocation)** through the portal, CLI or a schedule releases the hardware and stops compute charges. Disks, public IPs and licences keep billing.
- Resizing across hardware generations, and changing zones, usually needs the VM deallocated first - which is why Dev's Friday resize failed.

Everything from [lesson 1.6](lesson:1.6) applies: a one- or three-year [reservation](gl:reservation) for a box that runs 24/7, [spot virtual machines](gl:spot-virtual-machine) for interruptible batch work, [Azure Hybrid Benefit](gl:azure-hybrid-benefit) for Windows Server and SQL Server licences you already own. For dev machines, turn on auto-shutdown at 19:00 on day one; it is a checkbox and it removes two-thirds of the bill.

## When a VM is right, and when it is defeat

| A VM is the right answer | A VM is an admission of defeat |
|---|---|
| Software that only ships as an installer or an appliance | A Node API or a .NET web API - that is [App Service](gl:app-service), [lesson 2.2](lesson:2.2) |
| GPU work, or kernel-level agents and drivers | A React bundle - that is Static Web Apps, [lesson 2.3](lesson:2.3) |
| Licences that demand a named machine or a fixed core count | A scheduled job or a queue worker - that is Functions, [lesson 2.4](lesson:2.4) |
| Full OS control for legacy, or a specific old runtime | "It is what we know" - that is a training gap, not a design |
| A [lift-and-shift](gl:lift-and-shift) step **with a dated exit plan** | A lift-and-shift with no exit date, which becomes permanent |

## Map it to what you know

| You already know | The Azure equivalent |
|---|---|
| A VPS, or the box under the desk | A virtual machine - same job, billed per second, rebuildable in minutes |
| `apt upgrade` on a Tuesday night | Still yours. Update Manager schedules it; nobody does it for you |
| An AMI in AWS | A [VM image](gl:vm-image); the Compute Gallery is the sharing and versioning layer |
| A Docker base image everyone builds `FROM` | A golden image in the Compute Gallery, minus the layer caching |
| Nginx load-balancing two web servers | A scale set behind an Azure Load Balancer, with autoscale on top |
| Killing an EC2 instance versus stopping it | Deallocate versus stop - only deallocate stops the compute bill |

## Guiding your team

> [!TEAM]
> When someone proposes a virtual machine, ask:
>
> 1. **Why not a managed service?** Make them name the specific thing that forces a VM. "Control" is not a reason; a kernel driver is.
> 2. **Who patches it, and when?** If nobody can name a person and a window, the VM is already a liability.
> 3. **What size and why that size?** Start two sizes smaller than instinct and watch the metrics for a fortnight.
> 4. **Is it stateless?** If yes, it should be a scale set across zones, not a pet with a hostname.
> 5. **What is the exit date?** Every lift-and-shift VM gets a date in the backlog, or it is there in 2035.

## Key takeaways

- A VM is IaaS: Azure runs the hardware, you own the OS, patching, hardening, backup and monitoring for its whole life.
- `Standard_D4s_v5` decodes as family, vCPU count, premium-storage capable, generation. B burstable, D general, E memory, F compute, L storage, N GPU.
- Disk performance is capped by the disk tier *and* the VM size; the temp disk is disposable; ephemeral OS disks are free and vanish on reallocation.
- Availability sets protect against rack and patch failures in one data centre; availability zones protect against losing a data centre. Scale sets give you both plus autoscale.
- Stopped in the OS still bills. Only deallocated stops compute charges, and disks bill either way.
- Choose a VM for installers, GPUs, kernel agents and licensing - never for a web app that a managed service would run for less.
