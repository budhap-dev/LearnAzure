## Why this matters

> [!SCENARIO] Three surprises in the first month
> The new event-driven checkout from [lesson 5.1](lesson:5.1) survives Black Friday. The first month still brings three surprises.
>
> The warehouse subscription has 1,200 messages in a *dead-letter* queue that nobody knew existed; each one is an order whose stock was never reserved. A cancelled order was processed before the order itself, so stock went negative. And during a two-minute blip, the API saved 37 orders in SQL but crashed before publishing their events, so the warehouse never heard of them.
>
> Dev asks whether Service Bus is broken. It is not. Each surprise is a feature the team had not designed for.

## Namespaces, queues, topics and subscriptions

**[Azure Service Bus](gl:azure-service-bus)** is Azure's broker for business messages - the orders, payments and stock changes that must not be lost. Everything lives in a **namespace** (`sb-shop-prod`), which holds:

- **Queues**: point-to-point; each message goes to one receiver, and competing consumers share the work.
- **[Topics](gl:service-bus-topic)** and their **subscriptions**: publish-subscribe. The publisher sends to the topic; each subscription is effectively its own queue holding a copy of every message that passes its **filter**, such as `eventType IN ('OrderPlaced','OrderCancelled')`.

## Receiving safely: locks and the dead-letter queue

Receivers normally use **[peek-lock](gl:peek-lock)**. The broker hands over a message and locks it for a period, 60 seconds by default. The receiver does the work, then **completes** the message, which deletes it. If the receiver crashes, or **abandons** the message, the lock expires and the message is delivered again. Every delivery increments a counter.

When the counter passes the **max delivery count** (10 by default), Service Bus moves the message to the entity's **[dead-letter queue](gl:dead-letter-queue)**, together with the reason. Messages that expire can go there too. The dead-letter queue is not a bin: it keeps messages until someone reads them, and they count towards the entity's size.

==A dead-letter queue is part of the design, not an error log: every one needs an alert on its count, an owner, and a way to inspect, fix and resubmit messages.== The portal's Service Bus Explorer does that by hand; a small tool does it properly. The 1,200 unreserved orders were a missing alert, not a Service Bus fault.

The other receive mode, *receive-and-delete*, removes the message as it is handed over. It is faster, and any crash loses the message. Use it only where losing some messages is acceptable, such as telemetry.

## Order and duplicates

**Ordering.** A single queue does not promise first-in, first-out once there are several receivers. **[Message sessions](gl:message-session)** do: set `SessionId` to the order ID, and all messages for that order go to one receiver at a time, in order. Different orders still run in parallel. That fixes the cancellation that overtook its order. The cost is that one slow session holds up only its own messages - but it does hold them up.

**Duplicates.** **[Duplicate detection](gl:duplicate-detection)** remembers each `MessageId` for a window you choose, from minutes up to seven days, and drops any repeat sent within it. Set the message ID to something meaningful, such as `1042-OrderPlaced`, and a publisher that retries after a timeout cannot double-send. It protects the sending side only. Consumers must still be [idempotent](gl:idempotent), because redelivery after a lock expires is not a duplicate send.

## The two writes problem and the outbox

The 37 lost orders came from two writes: the API saved the order to SQL and then published an event. There is no transaction across a database and a broker, so a crash between the two leaves them disagreeing. Swap the order and the reverse happens: an event for an order that was never saved.

The **[transactional outbox](gl:transactional-outbox)** fixes it. In the same database transaction that saves the order, the API inserts a row into an `outbox` table. A separate relay reads unsent outbox rows, publishes them, and marks them sent. If anything crashes, the relay simply tries again - which is why duplicate detection and idempotent consumers matter.

## Tiers, and what they cost

| Tier | Gives you | Rough price |
|---|---|---|
| **Basic** | Queues only; no topics, sessions or duplicate detection | Cents per million operations |
| **Standard** | Topics, sessions, duplicate detection, transactions; shared capacity; messages up to 256 KB | About $10 a month plus operations |
| **Premium** | Dedicated capacity with predictable latency, messages up to 100 MB, private endpoints and VNet access, geo-replication | About $680 a month per messaging unit |

Service Bus accepts [managed identities](gl:managed-identity) with the *Azure Service Bus Data Sender* and *Data Receiver* roles. Grant those and **disable local (SAS key) authentication**, the same move as disabling storage account keys. Functions and Container Apps both scale on queue length, so consumers grow with the backlog.

## In practice

The shop's `sb-shop-prod` namespace on **Standard**: the `order-events` topic with filtered subscriptions for the warehouse, email and analytics; sessions keyed by order ID on the warehouse subscription; duplicate detection with a one-hour window; an outbox table and a timer-triggered relay; Entra-only authentication. Every dead-letter queue has an alert on its count and an owner. A small internal page lists dead-lettered messages with their reasons and a *resubmit* button.

The private-endpoint rule from [lesson 4.8](lesson:4.8) would need Premium at about $680 a month. Priya records a dated exception instead: Standard with Entra-only auth, reviewed when Premium's other features are needed or the budget allows. That is a real trade-off, written down, not a quiet gap.

**What breaks.**

- **Unwatched dead-letter queues.** Messages rot and orders quietly fail.
- **Work longer than the lock.** A job that takes 90 seconds on a 60-second lock is redelivered while still running. Renew the lock or split the work.
- **Payloads over 256 KB.** Store the body in Blob storage and send a reference - the *claim check* pattern.
- **A subscription nobody reads.** It fills to the namespace quota, and then sends to the whole topic fail. Delete unused subscriptions, and alert on size.
- **Relying on duplicate detection alone.** It stops duplicate *sends*, not redelivery. Consumers stay idempotent.

## Map it to what you know

| You already know | On Service Bus |
|---|---|
| MSMQ or SQL Server Service Broker | Queues, with transactions and dead-lettering |
| RabbitMQ exchanges and bindings | Topics and subscription filters |
| BullMQ or Bee-Queue on Redis in Node | A Service Bus queue that survives restarts and has a dead-letter queue |
| `BEGIN TRAN ... COMMIT` around two tables | The outbox: the order and its event in one transaction |
| A poison-message table someone checks on Mondays | A dead-letter queue with an alert and a resubmit tool |

## Guiding your team

> [!TEAM]
> For every queue and subscription, ask:
>
> 1. **Who is alerted when the dead-letter queue has messages, and how are they resubmitted?**
> 2. **Does order matter here?** If yes, what is the session ID?
> 3. **How does the publisher avoid the two-writes problem?** An outbox, or an honest explanation of why not.
> 4. **Is every consumer idempotent, and is the lock longer than the work?**
> 5. **Which tier, and is its limit - no private endpoint on Standard - a recorded decision?**

## Key takeaways

- Service Bus is the broker for business messages: queues for commands, topics with filtered subscriptions for events, all in a namespace.
- Peek-lock plus max delivery count moves failing messages to a dead-letter queue. Monitor it, own it, and build a way to resubmit.
- Sessions give first-in, first-out per key; duplicate detection stops repeated sends in a window. Consumers must still be idempotent.
- A database write plus a publish can disagree; the transactional outbox makes them one transaction.
- Standard covers most workloads; Premium buys dedicated capacity, large messages and private networking. Use Entra roles and disable SAS keys.
