## Why this matters

> [!SCENARIO] Three instances, three sets of baskets
> The shop's product page takes 900 ms. Every view runs the same six queries against [Azure SQL Database](gl:azure-sql-database): product, prices, stock, reviews, the category tree and "you may also like". Ana has asked for a bigger database tier twice.
>
> Then the Node API [scaled out](gl:scale-out) to three [App Service](gl:app-service) instances for a promotion and the tickets arrived within the hour: "I added items to my basket and they vanished." Sessions lived in each instance's memory. A shopper hit instance one, then instance three, which had never heard of them.
>
> Both problems have the same fix. Priya wants to know what it costs and what it will break.

## What a cache is, and the cache-aside pattern

A **cache** is a copy of data kept somewhere faster than its source, on the bet that it will be asked for again soon. Azure Cache for Redis is that somewhere: an in-memory key-value store on the network, answering in well under a millisecond inside a region.

The pattern almost everyone uses is **cache-aside**. The application does the work:

1. Ask Redis for `product:42`.
2. **Hit**: return it. **Miss**: query SQL, store the result in Redis with a [time to live](gl:time-to-live), return it.
3. When the product changes, delete the key, or let the TTL expire.

The TTL is the honesty setting. Sixty seconds means a price change takes up to a minute to show - fine for a product page, never fine for stock at checkout. ==A cache is the cheapest performance win you will ever buy, and the easiest way to show a customer data that is no longer true.==

Watch the **cache hit ratio**: below about 80% the cache is not earning its keep.

## What teams actually put in it

| Use | In Redis | Why it works |
|---|---|---|
| Query results | The serialised product page | Read a thousand times per write |
| **Session state** | Baskets, logged-in context | Any instance serves any shopper; no sticky sessions |
| Rate limiting | A counter per API key, expiring each minute | Atomic increment across all instances |
| Leaderboards, counters | Sorted sets, "viewed 1,204 times" | **Redis data structures** do the maths server-side |
| Pub/sub | "product 42 changed" fan-out | Every instance drops its local copy at once |
| **Output caching** | Whole rendered HTML or JSON responses | Skips the work, not just the query |

The session row is Ana's vanishing basket. Pointing `express-session` at a Redis store takes an afternoon, and instances can then restart or scale away freely.

## Tiers, sizing and the bill

![Azure Cache for Redis](az:redis) has four tiers. Read the SLA column as "what could go wrong".

| Tier | [SLA](gl:sla) | What you get | Rough starting price |
|---|---|---|---|
| **Basic** | **None** - one node | Dev and test only | ~$16/month for 250 MB |
| **Standard** | 99.9% | Two nodes, replicated | ~$100/month for 1 GB (C1) |
| **Premium** | 99.9% | Clustering, persistence, [VNet](gl:vnet-integration), [zone redundancy](gl:zone-redundant) | ~$400/month for 6 GB |
| **Enterprise** | 99.99% | Redis Enterprise: modules (search, JSON), active geo-replication | Higher; check the calculator |

Two rules. ==Size a cache by memory, not CPU==: keys times average value size, plus headroom, then the smallest size that fits - the meter runs per hour by size whether the cache is full or empty. And set the **eviction policy** to `allkeys-lru` for a pure cache: the Azure default, `volatile-lru`, only evicts keys that carry a TTL, so one forgotten `SET` without expiry can fill the cache and start rejecting writes.

> [!NOTE] Azure Managed Redis
> The newer **Azure Managed Redis** is Redis Enterprise in every tier (Memory Optimized, Balanced, Compute Optimized, Flash Optimized), publishes 99.99% zone-redundant and up to 99.999% with active geo-replication, and starts smaller than Premium. Price it first for new work with the [pricing calculator](gl:azure-pricing-calculator); Azure Cache for Redis is what you inherit in older estates.

## In practice

Create one cache in `rg-shop-prod`, in the API's region - elsewhere, [latency](gl:latency) eats the milliseconds it was meant to save. TLS always, a private endpoint on Premium and above ([Module 4](module:4)), and a [managed identity](gl:managed-identity) rather than an access key.

What breaks, roughly in the order teams meet it:

- **Connection exhaustion.** A Node API that creates a Redis client per request runs dry in minutes; a C1 allows about a thousand. One client per process, created at start-up.
- **Stale data after writes.** Stock still cached at 3 after the last one sold. Invalidate on write for anything a customer acts on.
- **Cache stampede.** A popular key expires and 400 concurrent requests all miss and hit SQL together. Stagger TTLs, or refresh hot keys early.
- **Using it as a database.** Basic and Standard do not persist; a restart empties them. If losing it hurts, it belongs in SQL or [Cosmos DB](gl:cosmos-db).
- **Key collisions.** Two services both write `user:42`. Prefix by service and version: `shop:v2:user:42`.
- **Hot keys.** One key read a million times an hour lands on one shard even when clustered. Hold it in process memory for a second too.

A **write-through cache** - updating Redis and the database together - removes the stale window but couples every write to the cache being up. Cache-aside plus invalidation is simpler and fails safer.

## Map it to what you know

| You already know | Redis equivalent |
|---|---|
| React Query or SWR keeping a result "fresh" for 60 s | Cache-aside with a TTL, server-side and shared by every user |
| `useMemo` or a memoised selector | The same RAM-for-CPU trade, shared across instances |
| SQL Server's buffer pool holding hot pages | A cache you choose the keys and TTLs of, in front of the database |
| Sticky sessions on a load balancer (ARR affinity) | An external session store, so no instance is special |
| An [edge cache](gl:edge-cache) for the React bundle | Files near the user versus data near the API |

## Guiding your team

> [!TEAM]
> Before anyone adds a cache, ask:
>
> 1. **What staleness is acceptable, in seconds?** No answer means not ready to cache.
> 2. **Who invalidates on write, and is it tested?** Stale-after-save is the bug customers screenshot.
> 3. **How many Redis clients per instance?** One. Show me where it is created.
> 4. **What is the hit ratio, and where do we see it?** Unmeasured means it is a cost, not a win.
> 5. **Is anything in here we cannot rebuild from a database?** Then it is in the wrong service.

> [!TIP] Exam link
> AZ-204 expects tier choice (Basic has no SLA; Premium adds persistence and VNet), eviction policies and cache-aside. AZ-900 needs only "in-memory cache in front of the database".

## Key takeaways

- A cache is a fast copy that may be stale. Cache-aside with a TTL is the pattern; the TTL is your honesty setting.
- One Redis shared by every API instance fixes slow reads and sessions that vanish when App Service scales out.
- Basic has no SLA; Standard is the production floor; Premium adds persistence, clustering and VNet; Enterprise and Azure Managed Redis add modules and active geo-replication.
- Size by memory, pay per hour by size, set `allkeys-lru`, and measure the hit ratio.
- What breaks: a client per request, stale data after writes, stampedes on expiry, a non-persistent cache used as a database, hot or colliding keys.
