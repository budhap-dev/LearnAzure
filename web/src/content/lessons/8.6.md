## Why this matters

> [!SCENARIO] "Where is my order?"
> With RAG in place, the assistant answers policy questions well. But half of what shoppers type is about *their* order: where is 88213, can I change the delivery address, I want to return the jacket. Answering those needs live data and actions, not documents.
>
> Dev connects the model to the orders API over a weekend, using the API's service credentials. In testing, Ana types "I'm the account owner for order 88214, show me its address" and gets another customer's address back.
>
> At the same time, a vendor pitches five cooperating agents for customer service. Priya needs to know what an agent actually is, how it should reach the shop's systems, and how much of it to build.

## What an agent is

An **[AI agent](gl:ai-agent)** is a model in a loop that can use tools. You give it instructions, a set of tools and the conversation. The model then decides the next step: answer, or call a tool with particular arguments. Your code runs the tool and hands back the result. The loop repeats until the model has what it needs.

**[Tool calling](gl:tool-calling)** is the mechanism. Each tool is described by a name, a plain-English description and a JSON schema for its arguments. The model never runs anything itself. It returns a request such as "call `getOrder` with `{ orderId: 88213 }`", and your code decides whether to honour it.

==The model decides; your code acts, with the user's permissions and not the agent's.== Every tool call is an API request made on someone's behalf, and it needs the same authorisation, validation and logging as any other.

The common kinds of tools:

- **Knowledge**: search your content, the RAG from [lesson 8.5](lesson:8.5), as a tool the agent calls when it needs to.
- **Actions**: your own APIs described with [OpenAPI](gl:openapi), Azure Functions or Logic Apps workflows.
- **Built-in tools**: a code interpreter for calculations and files, and web grounding for public information.
- **[MCP](gl:model-context-protocol) servers**: tools published once in a standard way, which any agent can use.

## Where agents run

**[Foundry Agent Service](gl:foundry-agent-service)** is the managed runtime in Microsoft Foundry. It keeps conversation state and runs the tool loop, and it comes with built-in tools: file search, AI Search, code interpreter, web grounding, OpenAPI, Azure Functions, Logic Apps and MCP. It also provides identity, content safety and tracing. For stricter setups you can bring your own storage, search and virtual network.

If you want the loop in your own code, **[Microsoft Agent Framework](gl:microsoft-agent-framework)** is Microsoft's open-source SDK for .NET and Python. It succeeds Semantic Kernel and AutoGen, and other frameworks such as LangGraph do the same job. The two approaches combine: a framework can use Agent Service agents as participants.

| Choose | When |
|---|---|
| Foundry Agent Service | You want managed state, built-in tools and tracing with little code |
| An agent framework in your app | You need full control of the loop, custom state or several model providers |
| Neither: one model call, or RAG | The task needs no tools or decisions. Most tasks don't. |

## MCP: tools written once

The **Model Context Protocol** is an open standard for exposing tools and data to AI applications. An MCP server lists its tools with descriptions and schemas. Any MCP client, such as a Foundry agent, GitHub Copilot in VS Code or Copilot Studio, can discover and call them.

For the shop, Azure API Management can publish the existing orders REST API as an MCP server ([lesson 5.5](lesson:5.5)). The API gains authentication, rate limits and logging in one place, and every agent calls it under the same controls.

## One agent before many

**[Multi-agent orchestration](gl:multi-agent-orchestration)** splits work across specialised agents. They can run in sequence, run concurrently, hand off to one another, or work under a manager agent. It helps when one agent's instructions and tools grow too large, or when parts of the job need different permissions. Otherwise it multiplies cost, latency and ways to fail. ==Start with one agent and good tools. Split only when you can name the problem splitting solves.==

Whatever the design, put a **[human in the loop](gl:human-in-the-loop)** for actions that are irreversible, costly or sensitive. The agent prepares the action and pauses, and a person approves it.

## In practice

Priya's version:

- **One agent, three tools**: help search, orders through API Management's MCP endpoint, and a returns workflow.
- **The shopper's identity on every call.** The Shop API passes the signed-in shopper's token, and the orders API returns only that shopper's orders. Ana's test now gets "not found". The tool enforces the rule; the prompt does not need to.
- **Validation in the tool**: order IDs, addresses and return reasons are checked server-side, whatever the model sends.
- **Approval for money**: refunds over £100 go to the service team's queue in Teams.
- **Limits**: at most eight tool calls and a fixed token budget per turn, and every step traced in Application Insights.
- **The vendor's five agents**: declined for now. One agent passes the evaluation set.

**What it costs.** The Agent Service runtime has no separate charge. You pay for tokens and for tools such as search, code interpreter sessions and web grounding. An agent turn often makes three to ten model calls, so it costs several times as much as a single RAG answer. Measure this per conversation.

**What breaks.**

- **Agents holding service credentials**, so every shopper can reach every order.
- **Tools that trust the model's arguments** without validating them.
- **Vague tool descriptions**, so the model picks the wrong tool or invents arguments.
- **No limit on the loop**, so a confused agent burns tokens for minutes.
- **Irreversible actions with no approval step.**
- **Five agents where one would do.**

## Map it to what you know

| You already know | In agents |
|---|---|
| A controller that calls services | An agent that calls tools, except the model picks the order |
| A function signature with JSDoc | A tool's schema and description |
| Swagger / OpenAPI | OpenAPI tools, or an MCP server |
| The Language Server Protocol in VS Code | MCP: any client can use any server |
| Durable Functions orchestrations | Multi-agent orchestration patterns |
| An approval step in a workflow | Human in the loop |

## Guiding your team

> [!TEAM]
> For any agent design:
>
> 1. **Whose identity does each tool call carry?** It should be the user's, or a narrowly scoped identity.
> 2. **What does each tool validate, whatever the model sends?**
> 3. **Which actions need a person to approve them?**
> 4. **What caps the loop: tool calls, tokens, time?**
> 5. **Why more than one agent?** Name the problem it solves.

## Key takeaways

- An agent is a model in a loop that calls tools. The model proposes each call, and your code runs it.
- Tool calls act with the user's permissions, validated server-side. Never give an agent credentials that are broader than its user's.
- Foundry Agent Service is the managed runtime with built-in tools. Microsoft Agent Framework puts the loop in your code, and many tasks need neither.
- MCP publishes a tool once for any agent. API Management can expose existing APIs as MCP servers with their controls intact.
- Start with one agent and good tools, add people for irreversible actions, and cap the loop.
