## Why this matters

> [!SCENARIO] The pipeline nobody can read
> The warehouse integration stays in Azure DevOps ([lesson 7.1](lesson:7.1)). It deploys a sync service to the warehouse server in the office and a function in Azure. Its pipeline is a *classic* release pipeline, built in the web UI by a contractor three years ago. Nobody can see its history or review a change to it.
>
> Last month it stopped deploying: the service principal it used had a client secret that expired. The month before, a fix worked in test and failed in production, because the pipeline rebuilt the code for each environment and picked up a newer dependency the second time. And nothing stops a deployment going straight to production on a Friday night.
>
> Priya wants it rebuilt properly: in code, built once, gated, and without a secret to expire.

## YAML pipelines: the pipeline is code

**[Azure Pipelines](gl:azure-pipelines)** runs CI/CD for any language and any target - Azure, other clouds or on-premises servers. Pipelines can be defined in the older *classic* editor or as a **[YAML pipeline](gl:yaml-pipeline)**: a file such as `azure-pipelines.yml` in the repository. ==Use YAML for everything: the pipeline is then versioned, reviewed in pull requests and rebuilt from the repository, like the code it ships.==

A YAML pipeline is a hierarchy:

- **Stages** - the big phases, such as Build, Deploy to test, Deploy to production. They run in order and can have conditions and approvals.
- **Jobs** - units of work inside a stage, each running on one agent. A **deployment job** targets an environment and records deployment history.
- **Steps** - the individual scripts or **tasks** (prebuilt actions such as `AzureFunctionApp@2`) inside a job.

```yaml
trigger:
  branches: { include: [main] }

variables:
  - group: warehouse-prod-kv        # secrets from Key Vault

stages:
  - stage: Build
    jobs:
      - job: build
        pool: { vmImage: ubuntu-latest }
        steps:
          - script: npm ci && npm test && npm run build
          - publish: dist
            artifact: warehouse-sync

  - stage: DeployTest
    dependsOn: Build
    jobs:
      - deployment: test
        environment: warehouse-test
        pool: { vmImage: ubuntu-latest }
        strategy:
          runOnce:
            deploy:
              steps:
                - task: AzureFunctionApp@2
                  inputs:
                    azureSubscription: sc-warehouse-test    # federated, no secret
                    appName: func-warehouse-test
                    package: $(Pipeline.Workspace)/warehouse-sync/**/*.zip

  - stage: DeployProd
    dependsOn: DeployTest
    jobs:
      - deployment: prod
        environment: warehouse-prod                         # approvals and checks live here
        pool: warehouse-onprem                              # self-hosted agent in the office
        strategy:
          runOnce:
            deploy:
              steps:
                - script: ./deploy-to-server.ps1 $(Pipeline.Workspace)/warehouse-sync
```

The key line is `publish`. The build stage produces **one artefact**, and every later stage deploys that same artefact. ==Build once, deploy many: test and production run exactly the same bits.==

## Agents: where the work runs

Every job runs on a **[pipeline agent](gl:pipeline-agent)** from an agent pool.

| Agent | What it is | Good for | Watch out |
|---|---|---|---|
| **Microsoft-hosted** | A fresh VM per job, managed and patched by Microsoft | Most builds and cloud deployments | Cannot reach private networks; no state between jobs |
| **Self-hosted** | Your own machine running the agent software | Reaching on-premises servers or private endpoints; special tools | You patch, secure and clean it; it tends to become a pet |
| **Managed DevOps Pools** | Microsoft-managed agents that run in *your* VNet, scaled on demand | Private-network deployments without maintaining machines | Priced per agent runtime plus VM cost |

A self-hosted agent only makes **outbound** HTTPS connections to Azure DevOps, so no inbound firewall ports are opened on the warehouse network.

## Environments, approvals and checks

A **[deployment environment](gl:deployment-environment)** is a named target - `warehouse-test`, `warehouse-prod` - that deployment jobs point at. It keeps a history of what was deployed, from which run and commit, and it is where production gets protected. Checks on an environment must pass before any job targeting it runs:

- **Approvals**: named people or groups must approve, with the changes in view.
- **Branch control**: only runs from `main` may deploy.
- **Business hours**: deployments only within a window.
- **Azure Monitor alerts**: block if the target is already unhealthy.
- **Exclusive lock**: one deployment at a time.

Because the checks live on the environment, not in the YAML, a developer cannot remove the production approval by editing the pipeline file.

## Service connections without secrets

Pipelines reach Azure through a **[service connection](gl:service-connection)**. Create Azure Resource Manager connections with **[workload identity federation](gl:workload-identity-federation)** ([lesson 4.5](lesson:4.5)): the pipeline exchanges its own token for an Azure one, so there is no client secret to expire. That is exactly what broke last month. Then:

- **Scope each connection** to one resource group and one environment - `sc-warehouse-test`, `sc-warehouse-prod` - with Contributor, not Owner on the subscription.
- **Restrict which pipelines may use it**, and put approvals and checks on the production connection too, so no other pipeline can quietly borrow it.
- **Link variable groups to Key Vault** for the few remaining secrets, so they are never typed into the pipeline.

## Templates: write it once

Pipelines across many repositories should not be copies of each other. **[Pipeline templates](gl:pipeline-template)** hold reusable stages, jobs and steps in a shared repository. An **extends template** goes further: a pipeline that extends the platform team's template *must* run its mandatory steps - dependency scanning, publishing test results - and cannot skip them. That is how an organisation raises the floor for every pipeline at once.

## In practice

The warehouse pipeline was rebuilt in YAML in two days. One artefact per commit. Test deploys automatically. Production requires an approval from operations, runs only from `main` and only within business hours, and deploys to the office server through a self-hosted agent that makes outbound connections only. The Azure function deploys through federated service connections scoped to its resource group. Build and security steps come from the platform team's extends template. Every deployment shows in the environment's history with its commit and approver.

**What it costs.** One Microsoft-hosted parallel job (about $40 a month beyond the free grant) and one self-hosted parallel job (about $15). The expired secret alone cost a day of blocked deployments.

**What breaks.**

- **Classic pipelines nobody can read.** Convert them to YAML, one at a time.
- **Rebuilding per environment.** Production runs different bits from those that were tested. Build once, deploy the artefact.
- **Service connections with secrets and wide scope.** They expire at the worst time and let any pipeline touch everything.
- **Self-hosted agents as pets.** Leftover files, stale tools, admin credentials. Prefer Managed DevOps Pools or ephemeral agents, and patch the rest.
- **Rubber-stamp approvals.** An approval that nobody reads is a delay, not a control. Keep approvers few and informed.

## Map it to what you know

| You already know | In Azure Pipelines |
|---|---|
| TFS XAML builds and classic release definitions | YAML pipelines in the repository |
| A `Jenkinsfile` | `azure-pipelines.yml` |
| Octopus Deploy environments and lifecycles | Environments with approvals and checks |
| A build server under someone's desk | A self-hosted agent - or better, Managed DevOps Pools |
| Web Deploy publish profiles with passwords | Service connections with workload identity federation |

## Guiding your team

> [!TEAM]
> For every pipeline, ask:
>
> 1. **Is it YAML in the repository, reviewed like code?**
> 2. **Is the artefact built once and promoted, or rebuilt per environment?**
> 3. **What protects production - approvals, branch control, business hours - and can a YAML edit remove it?**
> 4. **Does any service connection use a secret, or reach more than one resource group?**
> 5. **Who patches the self-hosted agents, and could they be Managed DevOps Pools instead?**

## Key takeaways

- Define pipelines in YAML in the repository: stages, then jobs on agents, then steps and tasks.
- Build once and deploy the same artefact to every environment.
- Microsoft-hosted agents suit most work; self-hosted agents or Managed DevOps Pools reach private networks and on-premises servers.
- Environments hold deployment history and the checks - approvals, branch control, business hours - that YAML edits cannot bypass.
- Service connections use workload identity federation, scoped narrowly and protected; templates and extends templates make every pipeline meet the same floor.
