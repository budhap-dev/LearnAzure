## Why this matters

> [!SCENARIO] Confidently wrong, and nothing found
> The assistant prototype is fluent, friendly and wrong. Asked whether the Alpine jacket is waterproof, it says yes. It is only water-resistant. Asked about returns, it says 60 days. The policy is 30. The model is not lying. It knows nothing about Northline and fills the gap with something plausible.
>
> Meanwhile the site's search box returns nothing for "warm waterproof jacket for a six-year-old". The catalogue says "kids", "insulated" and "rain shell". Keyword search matches words, not meaning.
>
> Priya needs one thing that fixes both: search that understands what people mean, and an assistant that answers from Northline's own data and shows where each answer came from.

## Retrieval-augmented generation

**[Retrieval-augmented generation](gl:retrieval-augmented-generation)** (RAG) is the standard pattern for this. For each question:

1. **Retrieve**: search your own content for the few passages most likely to hold the answer.
2. **Augment**: put those passages into the prompt, with instructions to answer only from them and to cite them.
3. **Generate**: the model writes an answer grounded in what you gave it, or says it does not know.

==The model answers from what you retrieve, not from what it remembers. So RAG quality is mostly search quality.== If the right passage is not among the top few results, no prompt will rescue the answer. Retrieval also keeps answers current: change the returns policy document, re-index, and the next answer changes, with no retraining.

## Azure AI Search

**[Azure AI Search](gl:azure-ai-search)** is Azure's managed search engine, and the usual retrieval layer for RAG. The parts:

- **A [search index](gl:search-index)**: the searchable copy of your content, with fields such as title, text, category, price, in-stock and the groups allowed to see it. Some fields are searchable text, some are filters or facets, and one holds the vector.
- **[Indexers](gl:indexer)**: scheduled crawlers that pull from Blob Storage, Azure SQL, Cosmos DB and other sources, then chunk, embed and load the content, so the index follows the data without your code.
- **Query types**, which work best combined:

| Search type | Finds | Misses |
|---|---|---|
| **Keyword** (BM25) | Exact words, product codes, names, SKUs | Synonyms and meaning: "kids" does not match "children" |
| **Vector** | Meaning: "rain shell" matches "waterproof jacket" | Exact codes and rare words |
| **[Hybrid](gl:hybrid-search)** | Both, merged into one ranked list | Little; this is the default to start from |
| **+ [Semantic ranker](gl:semantic-ranker)** | Re-orders the top results with a language model and extracts the best captions | - |

Newer **agentic retrieval** goes a step further: a model breaks a complicated question into several searches and merges the results. Try it once the basics are measured.

## Chunks and embeddings

Documents are too long to retrieve whole, so they are split. **[Chunking](gl:chunking)** cuts content into passages of a few hundred to about a thousand tokens. The best splits follow headings and sections, with a little overlap so no sentence loses its context. Each chunk keeps metadata, such as its source, title, product ID, last-updated date and who may see it.

Each chunk is then turned into an **[embedding](gl:embedding)**: a list of numbers that captures meaning, from an embedding model ([lesson 8.2](lesson:8.2)). Texts with similar meaning get nearby vectors. That is how "warm waterproof jacket for a six-year-old" finds "kids' insulated rain shell". A question is embedded with the same model at query time.

AI Search is not the only home for vectors. [pgvector](gl:pgvector) on PostgreSQL and Cosmos DB vector search ([lesson 3.7](lesson:3.7)) are fine when the data already lives there and simple similarity is enough. Choose AI Search when you need hybrid ranking, the semantic ranker, indexers over several sources, and filtering by permissions.

## In practice

Priya's setup:

- **One index for products and one for help content**, fed by indexers from Azure SQL and Blob Storage. Chunks follow document headings, and embeddings come from the embedding deployment. Embedding all 40,000 products costs less than a dollar.
- **Hybrid search plus the semantic ranker**, filtered to in-stock items in the shopper's country. The top five chunks go into the prompt.
- **The system prompt**: answer only from the sources provided, cite each one, and say so plainly when the sources do not cover the question.
- **Security trimming**: help chunks carry an audience field. The public assistant filters to `public`, so internal returns-fraud guidance never reaches a shopper.
- **Measure retrieval first**: 150 real questions, each with the passage that answers it. The first run found the right passage in the top five 71% of the time. Better chunking and hybrid search raised that to 92% before anyone touched the prompt.

**What it costs.** You pay per search unit per month. Basic is about $75 and Standard S1 about $250. Two replicas give the read SLA and three the read-write SLA, and partitions add storage. The semantic ranker has a free monthly allowance, then a charge per thousand queries.

**What breaks.**

- **Whole documents as chunks**, so the answer is buried in the middle of a 20-page PDF.
- **Vector-only search** that cannot find SKU `NL-4471`.
- **A stale index**, because the indexer schedule was never set or its failures go unwatched.
- **No security trimming**, so internal documents answer public questions.
- **Stuffing in 50 chunks** "to be safe", which costs more and confuses the model.
- **Tuning the prompt when retrieval is the problem.**

## Map it to what you know

| You already know | In AI Search and RAG |
|---|---|
| SQL Server full-text search | Keyword (BM25) search |
| A covering index for one query shape | A search index designed for the questions people ask |
| An SSIS or ETL job that refreshes a reporting table | An indexer on a schedule |
| `WHERE TenantId = @tenant` on every query | Security-trimming filters |
| An open-book exam | RAG: the model answers from the pages you hand it |

## Guiding your team

> [!TEAM]
> In a RAG design review:
>
> 1. **How often is the right passage in the top five?** Show the retrieval test set and its score.
> 2. **How is content chunked, and what metadata does each chunk carry?**
> 3. **Are we using hybrid search and the semantic ranker, and if not, why not?**
> 4. **How do permissions reach the index?** Which filter enforces them?
> 5. **What happens when nothing relevant is found?** The answer should be "I don't know", with a way to a human.

## Key takeaways

- RAG retrieves your own content, puts it in the prompt and asks the model to answer only from it, with citations. It keeps answers current without retraining.
- RAG quality is mostly retrieval quality: measure whether the right passage is in the top few results before tuning prompts.
- Azure AI Search provides indexes, indexers and keyword, vector and hybrid queries, plus a semantic ranker. Start with hybrid and semantic ranking.
- Chunk by structure with overlap, keep metadata on every chunk, and embed chunks and queries with the same model.
- Filter by permissions in the index, and let the assistant say "I don't know".
