## Why this matters

> [!SCENARIO] Twenty thousand tabs asking "yet?"
> The order-tracking page and the app's order screen ask the API for the order's status every five seconds.
>
> On Black Friday, 20,000 tabs and app screens are open at once. That is 4,000 requests a second through Front Door and API Management, and almost every answer is "no change". The Node API scales to eight instances and Azure SQL runs hot. Meanwhile the "only 2 left" badge on product pages is up to five seconds stale, and people buy items that have already sold out.
>
> Priya asks Ana to push changes instead of answering the same question 4,000 times a second. Leo adds a warning: phones lose their connection in every tunnel.

## Polling, server-sent events or WebSockets

**[Polling](gl:polling)** is the client asking on a timer. It is simple and works everywhere, but its cost grows with how many people are *watching*, not how often anything *changes*.

**[Server-sent events](gl:server-sent-events)** (SSE) keep one HTTP response open while the server writes events into it. They are one-way, and the browser's `EventSource` reconnects for you. The catch for Northline: Front Door's current docs state that it **does not support SSE**.

A **[WebSocket](gl:websocket)** upgrades an HTTP request into a long-lived, two-way connection. It is the most efficient option, but it is *stateful*: some server holds every open connection, messages must reach whichever instance holds the right client, and dropped connections must be re-established.

| Option | Direction | Through Front Door |
|---|---|---|
| Polling | Client asks on a timer | Yes |
| SSE | Server to client | No |
| WebSocket | Both ways | Yes, with limits |

==Polling costs grow with how many people are watching; push costs grow with how much actually changes.==

Self-hosting WebSockets on App Service means turning on the **Web sockets** setting, pinning clients to instances with **ARR affinity**, and a Redis adapter on [Azure Cache for Redis](gl:azure-cache-for-redis) so every instance can reach every client. [Azure Front Door](gl:azure-front-door) carries WebSockets, but only on uncached routes, with the WAF checking just the handshake, a five-minute idle timeout, a two-hour cap, and, for now, up to 3,000 concurrent WebSocket connections per profile. Twenty thousand tabs do not fit. Clients should connect to a managed service directly.

## SignalR Service or Web PubSub

Azure has two managed connection brokers. Clients connect to the service, not your API; your code tells the service what to send.

**[Azure SignalR Service](gl:azure-signalr-service)** speaks the SignalR protocol. Its client libraries reconnect automatically, fall back to SSE or long polling when a network blocks WebSockets, and call named methods on a **[SignalR hub](gl:signalr-hub)**. It has three modes:

- **Default:** an ASP.NET Core app hosts the hub. That is a .NET model, so a Node API cannot be the hub server.
- **[Serverless mode](gl:signalr-serverless-mode):** no hub server, which suits [serverless](gl:serverless) code. A `negotiate` [Azure Function](gl:azure-functions) hands the client a URL and a short-lived token; Functions or the REST API send to a user, a group or everyone.
- **Classic:** for old apps only.

**[Azure Web PubSub](gl:azure-web-pubsub)** is plain WebSocket plus [publish-subscribe](gl:publish-subscribe) groups. Any WebSocket client can connect, there is a JavaScript server SDK, and a *reliable* subprotocol recovers messages missed during a short drop. **Web PubSub for Socket.IO** has been generally available since November 2023: a Socket.IO app moves over with a few lines of change, and the Redis adapter goes away.

Microsoft is clear that Web PubSub does not replace SignalR. Choose SignalR Service for its client's reconnects and fallbacks, a .NET stack or Functions bindings. Choose Web PubSub for raw WebSockets, Socket.IO, your own subprotocol, or clients publishing to each other.

## Units, security and reconnects

Both services are sized in **[units](gl:signalr-unit)**. On Standard and Premium, one unit holds 1,000 concurrent connections and includes 1 million messages a day; only outbound messages count, in 2 KB chunks. Free is one unit of 20 connections with no SLA. Standard scales by hand to 100 units, with a 99.9% SLA. Premium adds [autoscale](gl:autoscale), [availability zones](gl:availability-zone), geo-replication and 99.95%, and its P2 size reaches 1,000 units. At approximate pay-as-you-go list prices, which vary by region, a Standard unit is about $1.61 a day and a Premium unit about $2.00, with extra messages about $1 per million. Web PubSub is priced the same.

**Messages multiply.** A broadcast to 5,000 viewers is 5,000 billed messages. Stock pushed every second to 5,000 people watching one product is 18 million messages an hour.

**Security.** The token is the connection's identity, so issue it only after checking the customer's [External ID](gl:microsoft-entra-external-id) token, and set the user ID on the server. Add connections to groups on the server too: a group called `order-1042` that anyone can join leaks orders. Turn off access keys and let the Functions use a [managed identity](gl:managed-identity).

**Reconnects.** The SignalR JavaScript client retries after 0, 2, 10 and 30 seconds, then gives up, and anything sent while the phone was in the tunnel is gone. ==Treat a push as a hint that something changed and the API as the source of truth: refetch on every reconnect.== On a phone, close the socket when the app goes to the background, let a push notification ([lesson 11.4](lesson:11.4)) cover "out for delivery", and reconnect and refetch on return.

## In practice

Ana's design: `sig-shop-prod`, SignalR Service **Premium** in serverless mode in UK South. A new `realtime` subscription on the `order-events` topic ([lesson 5.2](lesson:5.2)) triggers `notify`, which sends each status change to that customer's user ID. Product pages join a `stock-<sku>` group, with at most one stock push every ten seconds per product.

- **Sizing.** A normal evening is about 2,500 connections; Black Friday is 20,000 tabs plus 6,000 app screens. Autoscale runs between 3 and 30 units.
- **Cost.** About $180 a month at three units and about $60 a day at the peak. Standard is cheaper per unit but means someone scaling by hand at midnight.
- **Front Door.** `negotiate` goes through Front Door and APIM like any API call; the WebSocket goes straight to the service.
- **Customer service chat.** A contractor's Socket.IO server on one App Service instance moves to Web PubSub for Socket.IO.

**What breaks.** A client that never refetches shows "preparing" for a delivered order. A group anyone can join by name. Every stock tick broadcast to everyone. A WebSocket on a cached Front Door route, where the upgrade quietly fails.

## Map it to what you know

| You already know | On Azure |
|---|---|
| Pusher Channels and its auth endpoint | Web PubSub groups and a negotiate endpoint |
| Socket.IO with the Redis adapter | Web PubSub for Socket.IO |
| ASP.NET SignalR on IIS | SignalR Service in Default mode |
| Firestore `onSnapshot` | No direct equivalent: these push messages, they do not sync data |

## Guiding your team

> [!TEAM]
> In a design review for anything live, ask:
>
> 1. **What changes, how often, and how many people are watching?** That decides polling versus push, and the unit count.
> 2. **What does the client do after a reconnect?** Without a refetch it shows stale state after every tunnel.
> 3. **Who sets the user ID and the group membership?** Anything the client chooses, an attacker chooses.
> 4. **How many outbound messages does one change create?** Group size times frequency is the real bill.
> 5. **What happens when the app is backgrounded?** Sockets die there; push notifications do not.

## Key takeaways

- Polling cost scales with watchers. SSE is one-way and not supported through Front Door. WebSockets are two-way but stateful.
- SignalR Service brings reconnect and fallback transports; Web PubSub brings plain WebSockets and Socket.IO.
- Serverless mode needs no hub server: a negotiate Function issues the token, and Functions or the REST API send messages.
- One unit is 1,000 connections and 1 million included messages a day. Premium adds autoscale and zones.
- Authenticate at negotiate, set identity and groups on the server, and refetch on every reconnect.
