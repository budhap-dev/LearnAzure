## Why this matters

> [!SCENARIO] Three experiments, three setups
> A month after lesson 8.2, the shop has AI experiments everywhere. Dev works in a hub he created in the portal last spring, with its own storage account and key vault. Ana's team made their own Azure OpenAI resource in the sandbox subscription. A contractor evaluates models in a third place.
>
> The assistant's system prompt was tuned in a playground and pasted into the code by hand, twice, differently. An API key is pinned in a Teams chat. When the assistant's dev and prod traffic both slowed on the same afternoon, it turned out they shared one quota.
>
> Priya wants one structure: which resources exist per environment, who can do what, and how an experiment becomes production.

## The resource and its projects

**[Microsoft Foundry](gl:microsoft-foundry)** is Azure's platform for building AI applications and agents: models, AI services, agents, evaluation, tracing and governance, in one portal and one SDK. Underneath it is ordinary Azure, with two levels.

- **The Foundry resource** is the Azure resource you create in a resource group. It holds the [model deployments](gl:model-deployment), the prebuilt AI services ([lesson 8.4](lesson:8.4)), networking, encryption keys and the link to quota. It is the unit for billing, networking and policy.
- **A [Foundry project](gl:foundry-project)** is a child of the resource: a working area for one application or team. Agents, uploaded files, evaluations, traces and [connections](gl:foundry-connection) live in the project. It has its own managed identity, its own access control and an endpoint that your code calls.

==The resource is the boundary for governance, and the project is the boundary for a piece of work.== Projects in the same resource share its model deployments, so one team does not need its own copy of a model.

## Hubs: the older model

Before Foundry projects existed, the unit of work was a **[hub](gl:foundry-hub)**-based project. A hub is built on an Azure Machine Learning workspace and brings its own storage account and key vault, with optional container registry. Many organisations still have hubs.

| | Foundry project | Hub-based project |
|---|---|---|
| Parent | A Foundry resource | A hub (an Azure Machine Learning workspace) |
| Extra resources | None required | Storage account and key vault, often a container registry |
| Agents, latest SDK and evaluations | Yes, first | Partly, and later |
| Still needed for | - | Some Azure Machine Learning features, such as prompt flow and training open models on managed compute |

The rule: **new work goes in Foundry projects**. Keep a hub only for a feature that needs one, and plan to move off it.

## Connections and access

A **connection** is a named, reusable link from a resource or project to something else: AI Search, a storage account, Application Insights, another model endpoint, or Bing for web grounding. Code and agents refer to the connection by name, not to a URL and a secret. Wherever the target supports Microsoft Entra ID, the connection should use the project's managed identity, so there is no key to leak.

Access is ordinary Azure RBAC ([lesson 4.5](lesson:4.5)). Builders get a role such as **Azure AI User** on their project, which lets them use deployments, agents and evaluations but not change the resource. Leads get project-management rights. Only the pipeline changes production. Apps call the project endpoint with their own managed identity.

## The developer loop

Foundry's portal and SDK support a loop that turns an idea into a production change:

1. **Explore in the [playground](gl:ai-playground).** Try models, system prompts and your own data in minutes. *View code* shows the equivalent SDK call.
2. **Move to code straight away.** The prompt, model choice and parameters go into the repository, not a portal text box. The Foundry SDK or the OpenAI SDK calls the project endpoint.
3. **Evaluate against a test set** of real questions with expected qualities. Foundry runs evaluators for groundedness, relevance and safety ([lesson 8.7](lesson:8.7)).
4. **Trace** every call with OpenTelemetry into Application Insights ([lesson 6.3](lesson:6.3)): prompts, tool calls, tokens and latency.
5. **Ship through the pipeline** ([Module 7](module:7)). A pull request that changes a prompt runs the evaluation, and a drop in scores fails the build.
6. **Monitor production**: quality, safety, cost and user feedback, which feed the next test set.

==A prompt is code. It lives in the repository, is reviewed in a pull request, and ships only if the evaluation passes.==

## In practice

Priya's structure:

- **One Foundry resource per environment** (dev, test and prod), each in that environment's subscription and defined in Bicep ([lesson 7.5](lesson:7.5)), with model deployments declared alongside it.
- **Separate subscriptions matter for AI.** Quota is per subscription, per region and per model, so dev load testing in the prod subscription eats prod's tokens. That is what happened on the slow afternoon.
- **One project per application**: *assistant* and *catalogue*. Each has its own identity, connections and evaluation history.
- **Builders** hold Azure AI User on the dev projects and Reader on prod. Everything reaches prod through the pipeline.
- **Clean-up**: Dev's hub work moves to a Foundry project, Ana's stray resource is deleted once its deployments are recreated in Bicep, and the key in Teams is rotated and key access disabled.

**What it costs.** The Foundry resource and projects cost nothing on their own. You pay for tokens, AI service calls, and connected resources such as AI Search, storage and Application Insights. A hub adds its own storage and key vault, and any compute you leave running.

**What breaks.**

- **Playground to production by copy and paste.** Nobody knows which prompt is live.
- **One project for everything**, so every team sees every other team's files, agents and traces.
- **Keys in connections and chats** where managed identity would work.
- **Dev and prod sharing a subscription**, and so sharing quota.
- **Portal edits to production deployments** that the next Bicep deployment reverts.

## Map it to what you know

| You already know | In Microsoft Foundry |
|---|---|
| A Visual Studio solution with several projects | A Foundry resource with a project per app |
| SQL Server Management Studio's query window | The playground: try it, then save it as code |
| Connection strings in `web.config` | Connections, using managed identity |
| An Azure Machine Learning workspace | A hub, the older model |
| Unit tests in the pull request build | Evaluations that gate a prompt change |

## Guiding your team

> [!TEAM]
> When the team sets up Foundry:
>
> 1. **Is there one Foundry resource per environment, defined in code, in that environment's subscription?**
> 2. **Which project does this app use, and who has which role in it?**
> 3. **Where does this prompt live, and what evaluation runs when it changes?**
> 4. **Does any connection or app still use a key?** Why not managed identity?
> 5. **Are we still on a hub, and what feature keeps us there?**

## Key takeaways

- Microsoft Foundry (formerly Azure AI Foundry) is where you build AI apps and agents: models, AI services, agents, evaluation and tracing, on ordinary Azure resources.
- The Foundry resource holds deployments, networking and quota; projects are per-app working areas with their own identity, access, connections and history.
- Hub-based projects are the older model, built on Azure Machine Learning; new work goes in Foundry projects.
- Connections link projects to AI Search, storage and monitoring, ideally with managed identity.
- The loop: playground, then code, evaluate, trace, ship through the pipeline, monitor. A prompt is code.
- Use one resource per environment in separate subscriptions, because quota is per subscription and region.
