## Why this matters

> [!SCENARIO] Black Friday, 11:02
> The checkout API does five things before it answers the shopper: it takes the payment, reserves stock on the warehouse system, sends the confirmation email, adds loyalty points and records the sale for analytics. One after another, while the shopper waits.
>
> At 11:02 on Black Friday the warehouse VM slows to eight seconds a call. Checkouts take thirty seconds, the browser gives up, and shoppers press *Pay* again. By noon there are 340 double orders. At 14:00 the email provider has an outage, and checkouts start failing outright - after the card has already been charged.
>
> None of those five steps was broken on its own. They were broken by being done together, in line. Priya needs to know what really has to happen before the shopper gets an answer, and what can happen afterwards.

## Now, or after?

A synchronous call ties two systems together in time: the caller waits, and if the callee is slow or down, so is the caller. Five calls in a row means the checkout is only as fast as the slowest and only as available as all five multiplied together - the same series arithmetic as [lesson 1.7](lesson:1.7).

**[Asynchronous messaging](gl:asynchronous-messaging)** breaks that tie. The API records what needs doing and answers straight away; other services do the work when they can. If the warehouse is slow, work queues up instead of shoppers.

The design question is simple and worth asking out loud: ==do synchronously only what the customer must wait for; everything else goes on a message and happens afterwards.== For the shop, the shopper must wait for the payment to be authorised. They do not need to wait for an email, loyalty points or an analytics row, and the stock reservation can follow a moment later.

## Messages, events and streams

Three kinds of thing travel between systems, and mixing them up is the root of most bad designs.

| Kind | What it is | Example | The sender... |
|---|---|---|---|
| **[Message](gl:message)** (a command) | A request for one specific consumer to do something | `ReserveStock { orderId: 1042 }` | ...cares that it gets done, exactly once in effect |
| **[Event](gl:event)** | A fact about something that has already happened | `OrderPlaced { orderId: 1042 }` | ...does not know or care who listens |
| **[Event stream](gl:event-stream)** | A high-volume, ordered sequence of events, kept for a while and replayable | Every click on the shop, every sensor reading | ...just appends; readers keep their own place |

An event is named in the past tense and cannot be refused - the order *was* placed. A message is an instruction and can fail, so someone must handle the failure.

A **[message broker](gl:message-broker)** sits between senders and receivers, holds messages safely until they are processed, and handles the delivery rules. On Azure there are four brokers, and choosing between them is mostly choosing which of these three kinds you have.

## The patterns

**Point-to-point queue.** One sender, one queue, one kind of worker. Each message is processed by exactly one receiver. Add more workers reading the same queue and you have **[competing consumers](gl:competing-consumers)**: throughput scales with the number of workers, and a slow worker only slows itself.

**[Publish-subscribe](gl:publish-subscribe).** The publisher sends one event to a **topic**; every subscriber gets its own copy and processes it independently. Adding a new consumer - fraud checks, say - means adding a subscription, not changing the checkout code. That is how the shop's five-step checkout becomes one step plus an event.

## What asynchronous costs you

Decoupling is not free. Four things change, and each needs a decision.

- **Delivery is [at least once](gl:at-least-once-delivery).** If a consumer crashes after doing the work but before confirming it, the broker delivers the message again. Every consumer must be **[idempotent](gl:idempotent)**: processing `OrderPlaced 1042` twice must add loyalty points once. Use the order ID as the key.
- **Order is not guaranteed** unless you ask for it (Service Bus sessions, Event Hubs partitions) - and asking costs throughput.
- **Some messages will never succeed.** A malformed order fails every time; after a few retries it must move aside to a **dead-letter queue** for a human, not block the queue for ever.
- **The system becomes eventually consistent.** For a few seconds the order exists but the email has not gone. The UI must say so honestly: *"Order confirmed - your email is on its way."*

## Choosing the Azure service

| If you have... | Use | Lesson |
|---|---|---|
| Simple background work, huge backlogs allowed, no ordering or dead-lettering needed, cheapest possible | [Queue storage](gl:queue-storage) | [3.1](lesson:3.1) |
| Business commands and events that must not be lost: ordering, transactions, dead-lettering, duplicate detection, topics | Service Bus | [5.2](lesson:5.2) |
| Reactions to things happening - a blob uploaded, a resource created, a custom event - pushed to many handlers, cheaply | Event Grid | [5.3](lesson:5.3) |
| Millions of events a second - telemetry, clickstream, logs - to be read by several consumers and replayed | Event Hubs | [5.4](lesson:5.4) |

They combine well. Event Grid often feeds a Service Bus queue when a reaction must be reliable; Event Hubs feeds analytics while Service Bus carries the orders.

## In practice

Priya's new checkout: the API authorises the payment and checks stock against the database synchronously, writes the order, and publishes `OrderPlaced` to a Service Bus topic. The warehouse, email and loyalty services each have a subscription, retry with back-off on [transient faults](gl:transient-fault), and dead-letter what they cannot process. Image resizing, which never needed any guarantees, moves to Queue storage with competing Functions workers. Checkout time drops from up to thirty seconds to about one, and an email outage delays emails, not orders.

**What it costs.** Queue storage costs pennies. Service Bus Standard is roughly $10 a month plus a few cents per million operations - small next to one Black Friday of double orders.

**What breaks.**

- **Duplicate processing.** Consumers that are not idempotent double-count on every redelivery.
- **Silent backlogs.** A consumer dies and messages pile up for days. Alert on queue length and on the age of the oldest message.
- **Breaking the event contract.** Renaming a field in `OrderPlaced` breaks subscribers you have never met. Version events, and add fields rather than change them.
- **Async for everything.** If the shopper must see a result, making it asynchronous just moves the waiting into polling. Keep the synchronous core small but honest.
- **Losing the thread.** One order now touches five services; without a correlation ID in every message, nobody can trace it ([Module 6](module:6)).

## Map it to what you know

| You already know | In messaging terms |
|---|---|
| A `jobs` table polled by a cron job | A queue, without the locking bugs |
| MSMQ or SQL Server Service Broker | Service Bus |
| Node's `EventEmitter` | Publish-subscribe, but inside one process and lost on restart |
| Redux: dispatching `ORDER_PLACED` to every reducer | An event with many subscribers |
| RabbitMQ | Service Bus |
| Kafka | Event Hubs |
| Webhooks from Stripe or GitHub | Event Grid's push model |

## Guiding your team

> [!TEAM]
> When a design review shows a chain of calls, ask:
>
> 1. **Which of these steps must the user wait for?** Everything else is a candidate for a message.
> 2. **Is this a command, an event or a stream?** The answer picks the service.
> 3. **What happens when this consumer sees the same message twice?** "It cannot happen" is the wrong answer.
> 4. **Where do failed messages go, and who looks at them?**
> 5. **What does the user see in the seconds before everything catches up?**

> [!TIP] Exam link
> AZ-204 expects you to choose between Queue storage, Service Bus, Event Grid and Event Hubs from a scenario, and to know at-least-once delivery and dead-lettering. AZ-305 asks the same choice at design level.

## Key takeaways

- Synchronous chains are as slow as their slowest step and as available as all steps multiplied. Do synchronously only what the user must wait for.
- Messages are commands for one consumer; events are facts for anyone; streams are high-volume sequences you can replay.
- Queues with competing consumers scale work; publish-subscribe lets many services react to one event without the publisher knowing them.
- Asynchronous means at-least-once delivery, idempotent consumers, dead-letter queues and eventual consistency the UI admits to.
- Queue storage for simple work, Service Bus for business messages, Event Grid for reactions, Event Hubs for streams - and they combine.
