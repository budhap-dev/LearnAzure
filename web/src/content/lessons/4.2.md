## Why this matters

> [!SCENARIO] Four proposals with "load balancer" in the name
> Two bad weeks. First, UK South has a forty-minute App Service incident on a Saturday and the shop is simply down, because nothing knows there is anywhere else to send shoppers. Then a botnet tries 200,000 stolen passwords against `/login` in one night.
>
> The fixes arrive as four proposals. Dev wants an **Azure Load Balancer**. The contractor wants **Application Gateway** with a web application firewall. Ana has read that **Front Door** does "CDN, WAF and failover in one". A consultant recommends **Traffic Manager** because "it is the global one".
>
> All four are real products and all four balance load. Priya needs to know which problem each one solves, and why the answer is not "all of them".

## Two questions sort all four

Every one of these services spreads requests across healthy backends. They differ on two questions: **what does it understand**, and **where does it run**?

**[Layer 4 and layer 7](gl:layer-4-and-layer-7)** is the first. A layer 4 balancer sees TCP and UDP: addresses and ports, nothing more. A layer 7 balancer understands HTTP: it can read the path, the host name and the headers, terminate TLS and block a malicious request. The second question is whether it runs **in one region**, inside or next to your VNet, or **globally** at Microsoft's edge.

| | Regional | Global |
|---|---|---|
| **Layer 4** (TCP, UDP) | [Azure Load Balancer](gl:azure-load-balancer) | Cross-region Load Balancer (rare) |
| **Layer 7** (HTTP, HTTPS) | [Application Gateway](gl:application-gateway) | [Azure Front Door](gl:azure-front-door) |
| **DNS only** | - | [Traffic Manager](gl:traffic-manager) |

==For a public web app, start with Front Door; add Application Gateway only for a regional requirement it cannot meet, and use Load Balancer for traffic that is not HTTP.==

## The four, one at a time

**Azure Load Balancer** is layer 4 and regional: it forwards TCP and UDP connections to VMs or scale sets that pass a **[health probe](gl:health-probe)**. Public or internal, zone-redundant, and cheap - about $18 a month plus a fraction of a cent per GB. It is the right answer for non-HTTP traffic: SQL Server on VMs, a custom TCP protocol, the scale set from [lesson 2.1](lesson:2.1). It cannot read a URL, so it cannot route `/api` differently or stop an attack. App Service and Container Apps have balancing built in; you never put one in front of them.

**Application Gateway** is a layer 7 reverse proxy that lives in a dedicated subnet of your VNet. It routes by path and host name, does **[TLS termination](gl:tls-termination)** (and re-encrypts to the backend if you ask), and in the WAF_v2 tier runs a **[web application firewall](gl:web-application-firewall)** with the OWASP rule set. It is regional, so it does nothing for a region outage, and it is not small: roughly $320 a month for WAF_v2 before capacity units. Choose it when the backends are private - VMs or internal services with no public address - or when a regulator wants the inspection point inside your own network.

**Azure Front Door** is the same layer 7 idea run globally. Shoppers connect to the nearest of Microsoft's [points of presence](gl:point-of-presence) over an anycast address; TLS ends there, cacheable content is served from the edge, and requests continue over Microsoft's backbone to the healthiest **origin** in any region. It is the CDN, the global load balancer and, in Premium, a WAF with managed rules and bot protection in one service. Standard starts around $35 a month, Premium around $330, both plus traffic.

**Traffic Manager** is not in the request path at all. It is DNS: when a client looks up `shop.example.com`, it answers with the address of a healthy endpoint, chosen by priority, weight, performance or geography. No TLS, no caching, no WAF, and cents per million queries. Its weakness is DNS itself: after a failover, clients keep the old answer until their cached record expires, so recovery takes minutes, not seconds. Use it for non-HTTP services across regions, or to steer between whole stacks.

## Health probes decide everything

All four send traffic only where a health probe says yes, so the probe is the most important line of configuration you will write. A probe of `/` that returns 200 while the database is down keeps sending shoppers to a broken region. A probe that checks every dependency can take the whole site down when one of them hiccups.

Give the API a `/health` endpoint that checks what makes this instance useless - it cannot reach its database - and nothing further. Then decide, per origin, how many failed probes mean "out".

> [!WARNING] The origin nobody closed
> Front Door's WAF protects only traffic that goes through Front Door. If the App Service still answers on `shop-api.azurewebsites.net`, the botnet simply goes there. Restrict the app to the `AzureFrontDoor.Backend` [service tag](gl:service-tag) and check the `X-Azure-FDID` header carries your own Front Door's ID, or put the origin behind Private Link on Premium ([lesson 4.3](lesson:4.3)).

**[DDoS Protection](gl:ddos-protection)** sits underneath all of this. Every Azure public IP gets basic infrastructure protection free. Front Door absorbs volumetric attacks at the edge as part of the service. The paid DDoS Network Protection plan - around $2,900 a month for up to 100 public IPs - is for estates with many public IPs of their own, and adds cost protection and rapid-response support.

## In practice

Priya's decision for the shop: **Front Door Premium** in front of everything public, with WAF managed rules and a rate limit on `/login` for the botnet; the API in UK South as priority 1 and a warm standby in UK West as priority 2; images and the React build cached at the edge. App Service access restricted to Front Door. No Application Gateway, because nothing public is private, and no Traffic Manager, because everything is HTTP. An **internal Load Balancer** stays in the plan for the warehouse VMs if they ever become a pair.

**What it costs.** Front Door Premium runs about $330 a month before traffic, which replaces a separate CDN and WAF. Application Gateway WAF_v2 would add about $320 a month per region; Load Balancer about $18; Traffic Manager a few pounds.

**What breaks.**

- **The origin is still public.** See the warning; the WAF is decoration until the back door is shut.
- **Caching the basket.** A cache rule on `/api/*` serves one shopper's basket to the next. Cache static and anonymous content only, and let the API send `Cache-Control: private`.
- **The host header.** App Service routes by host name; if Front Door sends the wrong one, the origin answers 404. Set the origin host header deliberately.
- **Stacking for comfort.** Front Door, then Application Gateway, then Load Balancer, "just in case" - three bills, three hops of latency and three places to debug a 502.
- **Expecting instant DNS failover.** Traffic Manager moves new lookups within a minute; clients holding an old answer follow when it expires.

## Map it to what you know

| You already know | On Azure |
|---|---|
| An F5 or HAProxy balancing TCP to two servers | Azure Load Balancer |
| Nginx or IIS ARR as a reverse proxy with path rules | Application Gateway |
| Cloudflare, or Vercel's edge network, in front of the site | Azure Front Door |
| GeoDNS or DNS round robin | Traffic Manager |
| ModSecurity with the OWASP rule set | The WAF on Front Door or Application Gateway |
| A `/healthz` your load balancer polls ([lesson 2.2](lesson:2.2)) | Health probes, now choosing between regions |

## Guiding your team

> [!TEAM]
> When a design has a load balancer in it, ask:
>
> 1. **Is this traffic HTTP?** If yes, the choice is Front Door or Application Gateway; if no, Load Balancer or Traffic Manager.
> 2. **Is anyone outside one region, or must we survive a region failing?** That points global: Front Door for HTTP, Traffic Manager for anything else.
> 3. **Where is the WAF, and can an attacker go around it?** Show how the origin only accepts traffic from the front door.
> 4. **What does the health probe actually check?** "It returns 200" is not an answer.
> 5. **Which responses are cached, and could any be personal?** Anything with a user in it is `private`.

## Key takeaways

- Two questions sort the four: layer 4 (TCP/UDP) or layer 7 (HTTP), and regional or global.
- Load Balancer: regional layer 4, cheap, for VMs and non-HTTP traffic. Application Gateway: regional layer 7 in your VNet, with a WAF, for private backends.
- Front Door: global layer 7 at the edge - TLS, caching, WAF and cross-region failover in one. The default for a public web app.
- Traffic Manager: DNS-based, not in the request path, failover limited by DNS caching; for non-HTTP or whole-stack steering.
- Health probes choose where traffic goes; make them check what matters and nothing more.
- A WAF only protects traffic that passes through it. Lock the origin to your front door.
