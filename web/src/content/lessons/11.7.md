## Why this matters

> [!SCENARIO] The laptop that ships the app
> When App Center's build service shut down in March 2025, a contractor moved the mobile builds to their own MacBook "for now". Eighteen months later, Leo inherits it. The iOS distribution certificate, the Android keystore and its password all live on that laptop, and the certificate expires in three weeks. CodePush died with App Center, so every fix waits for store review. Crash reports still go to App Center Diagnostics, which closes for good at the end of March 2027.
>
> Then version 3.2 crashes on launch for some Android users. It went to every Play user at once, and the stack trace reads `index.android.bundle:1:482113`. Nobody can say which line of TypeScript that is.
>
> Priya asks Leo for a release process that does not depend on one laptop, and that says what broke.

## Where App Center's jobs went

**[Visual Studio App Center](gl:visual-studio-app-center)** retired on 31 March 2025. Only Analytics and Diagnostics were extended, now to 31 March 2027.

Where each job went (Microsoft's suggestion first, then common alternatives):

- **Build:** Azure Pipelines; also GitHub Actions or EAS Build.
- **Distribute:** TestFlight and Google Play testing tracks; also Firebase App Distribution.
- **CodePush:** a standalone CodePush server you host; or EAS Update.
- **Diagnostics:** Azure Monitor through OpenTelemetry (preview), or Datadog, Dynatrace or New Relic; also Sentry, Crashlytics or BugSnag.

**[Expo Application Services](gl:expo-application-services)** (EAS) is the closest single replacement: hosted builds, store submission and over-the-air updates. It works with bare React Native projects too.

## Build and sign without a laptop

Building is the easy half: iOS needs a macOS runner, Android builds on Linux. The hard half is **[code signing](gl:code-signing)**, which proves to the stores and the phone that the binary came from Northline unaltered.

- **iOS** needs a distribution certificate and private key (renewed yearly), a provisioning profile, and an App Store Connect API key for uploads.
- **Android** needs an upload key and a Google service account for Play uploads. With **Play App Signing**, Google holds the real app signing key, and a lost upload key can be reset. Lose a self-managed signing key and the app can never be updated.

The keys go in [Key Vault](gl:key-vault). The [GitHub Actions](gl:github-actions) workflow fetches them per build through [workload identity federation](gl:workload-identity-federation) ([lesson 7.4](lesson:7.4)) into a temporary keychain that dies with the runner. Azure Pipelines does the same with secure files. [Secret scanning](gl:secret-scanning) catches a keystore password pasted into `gradle.properties`.

==Signing keys belong to the organisation, not a laptop: keep them in Key Vault, fetch them for each build, and let Google hold the Android app signing key.==

**[Fastlane](gl:fastlane)** is the open-source tool most teams script this with: lanes that build, sign and upload. EAS Build is the hosted alternative and can hold the credentials for you, which is simpler, but then Expo holds your keys.

Builds land on a **[beta testing track](gl:beta-testing-track)** first: TestFlight, or Play's internal and closed testing. Up to 100 internal TestFlight testers get a build at once; up to 10,000 external testers wait for Beta App Review.

## Over-the-air updates, inside the rules

An **[over-the-air update](gl:over-the-air-update)** replaces the JavaScript bundle and assets in an installed app without a store release. Native code needs a new binary. Each update targets a **runtime version**, the native build it fits; send it to a binary missing a module it calls and the app crashes on launch.

The stores allow this within limits. Apple's developer agreement (section 3.3.1(B)) permits downloaded interpreted code only if it does not change the app's primary purpose, create a storefront or bypass signing and sandboxing, and review guideline 2.5.2 bars downloaded code that adds or changes features. Google Play forbids self-updating outside Play but exempts code run by an interpreter, which is how JavaScript bundles are generally treated. Fixes are fine; a feature that skips review is not.

Microsoft's **standalone CodePush server** repository was archived in May 2025, and the original client never supported React Native's New Architecture, the default since 0.76 and the only option from 0.82. **EAS Update** works in bare React Native through `expo-updates`, with runtime versions, percentage rollouts and rollback by republishing an earlier update. It is priced on monthly active users receiving updates plus bandwidth.

==Use over-the-air updates to fix code that already passed review; ship new features in a store build, behind a feature flag.==

## Watching the installed base

**[Crash reporting](gl:crash-reporting)** catches crashes on the phone, groups them by cause and counts the users each one hits. It needs **[symbolication](gl:symbolication)**: turning addresses and bundle offsets back into file, function and line. A React Native build makes three maps, iOS dSYMs, an Android R8 mapping file and the Hermes source map, and each must be uploaded for its exact build or update. Leo's `482113` was a missing source map.

[Application Insights](gl:application-insights) does part of the job. Northline's React Native plugin records uncaught JavaScript exceptions, device models and custom events, joined to the API's traces ([lesson 6.3](lesson:6.3)). It does not catch native crashes, group crashes or read dSYMs and mapping files. Azure Monitor's App Center migration path is in preview: community [OpenTelemetry](gl:opentelemetry) SDKs through a gateway you run.

So teams pair Application Insights with a crash reporter. **Firebase Crashlytics** is free and strong on native crashes, but does not decode JavaScript stacks from source maps for you. **Sentry** handles both, takes symbols from CI and reports crash-free sessions per release, charging by event volume. **BugSnag** is similar.

Releases go out in rings ([ring-based deployment](gl:ring-based-deployment), [lesson 7.7](lesson:7.7)). App Store **phased release** reaches automatic-update users over seven days, 1% to 100%, though anyone can download manually. Google Play's **staged rollout** uses percentages you set; halting stops new users, but those who have it keep it. Neither store can recall a build: the fix is a new, higher version.

==A store build cannot be recalled from phones, so every risky change needs a lever that works after install: a halted rollout, a flag or an update.== New features sit behind a [feature flag](gl:feature-flag) in [Azure App Configuration](gl:azure-app-configuration), served through the [backend for frontend](gl:backend-for-frontend), never via a key in the app. A [minimum supported app version](gl:minimum-supported-app-version) moves everyone past a build beyond saving.

## In practice

- **Build.** A `v3.3.0` tag ([semantic versioning](gl:semantic-versioning)) starts iOS and Android jobs. Fastlane signs with keys from `kv-mobile-sign`, uploads to the beta tracks and sends all three maps to Sentry.
- **Rings.** Staff for three days, 2,000 beta customers, then the stores' rollouts. Each step needs crash-free sessions at least as good as the last release.
- **Updates.** EAS Update for JavaScript-only fixes, 10% first.
- **Telemetry.** Sentry for crashes; Application Insights for traces and business events, with [sampling](gl:sampling) on noisy screens.

Decoded, 3.2's crash was a null address on Android 12. The flag on the new address screen went off within the hour, and 3.2.1 went out at 1%.

**What it costs.** macOS runner minutes, Sentry event volume and EAS Update's active users.

**What breaks.**

- **A certificate expiring on release day.** Give every expiry date an owner.
- **No symbols for an update.** Every new bundle has a new source map.
- **An update for the wrong runtime version.** It crashes on launch.
- **Personal data in crash breadcrumbs.** It is another copy of customer data.

## Map it to what you know

| You already know | Now |
|---|---|
| App Center Build | GitHub Actions or Azure Pipelines on macOS runners, or EAS Build |
| CodePush deployments | EAS Update channels and runtime versions |
| App Center Diagnostics | Sentry, Crashlytics or BugSnag, with symbols from CI |
| Signing files on a shared drive | Key Vault, or fastlane match |

## Guiding your team

> [!TEAM]
> Before the next mobile release, ask:
>
> 1. **Who could release the app if Leo left tomorrow?** Keys on one machine are a single point of failure.
> 2. **Is Play App Signing on?** It is the difference between a reset upload key and a dead app.
> 3. **Are symbols uploaded for every build and update?** An unreadable stack costs hours on the worst day.
> 4. **Would this update survive App Review?** Fixes pass; new features do not.
> 5. **What moves the rollout to the next ring, and what is the kill switch?** Phones cannot be rolled back.

## Key takeaways

- App Center retired on 31 March 2025; Analytics and Diagnostics end on 31 March 2027.
- Sign in CI with keys from Key Vault fetched over OIDC, and let Google hold the Android app signing key.
- Over-the-air updates change only JavaScript and assets for one runtime version, and store rules limit them to fixes. EAS Update is the maintained option.
- Application Insights sees JavaScript exceptions joined to the API; a crash reporter with uploaded symbols handles native crashes.
- Release in rings, gated on crash-free sessions, with feature flags as the lever after install.
