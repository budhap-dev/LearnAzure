## Why this matters

> [!SCENARIO] "It's slow" - but every log says 200
> Shoppers in Sydney say product pages take eight seconds. The API's HTTP logs show nothing but `200 OK` in 300 milliseconds. Mobile users report checkout errors that never appear in any server log. And last week's release doubled checkout time for everyone, which nobody noticed until the complaints arrived four days later.
>
> Each piece of the shop can describe itself. None of them can describe a shopper's request as it moves from the React app through Front Door, the API, SQL, Service Bus and the warehouse function. Priya wants to follow one request from the browser to the last function it touched.

## What Application Insights records

[Application Insights](gl:application-insights) is Azure Monitor's application performance monitoring. It collects telemetry from inside your code and stores it in the Log Analytics workspace ([lesson 6.1](lesson:6.1)), where it is queryable with KQL ([lesson 6.2](lesson:6.2)).

| Telemetry | What it is | Table |
|---|---|---|
| **Requests** | Every request your app served: name, duration, result | `AppRequests` |
| **Dependencies** | Every call your app made: SQL, HTTP, Service Bus, Redis, with duration and result | `AppDependencies` |
| **Exceptions** | Errors with stack traces, grouped by type | `AppExceptions` |
| **Traces** | Your log messages | `AppTraces` |
| **Page views and browser timings** | What the user's browser did and how long it took | `AppPageViews`, `AppBrowserTimings` |
| **Custom events and metrics** | Business signals you choose: `CheckoutCompleted`, basket value | `AppEvents`, `AppMetrics` |
| **Availability results** | Synthetic checks from around the world | `AppAvailabilityResults` |

## Instrumenting the shop

**The server.** For Node, .NET, Java and Python, the recommended route is the **Azure Monitor [OpenTelemetry](gl:opentelemetry) distro**: one package and one call at start-up, before anything else loads. It automatically records incoming requests and outgoing HTTP, SQL, Redis and Service Bus calls. OpenTelemetry is the vendor-neutral standard, so the same instrumentation could point at another backend later. The app is told where to send data with a **connection string**, kept in an app setting. App Service can also attach instrumentation without code changes for some runtimes.

**The browser.** The Application Insights JavaScript SDK, with its React plugin, records page views and route changes in a single-page app, fetch calls, browser timings and unhandled exceptions. A React Native plugin does the same for the mobile app. Those errors that "never appear in any server log" were failing *before* they reached the server: timeouts on slow mobile networks, and a JavaScript exception in one Android WebView.

## Distributed tracing: one request, end to end

**[Distributed tracing](gl:distributed-tracing)** connects all that telemetry into one story. When a request starts, it gets a trace ID. Every call it makes passes that ID on in the W3C `traceparent` header, or in a message property when it goes through Service Bus, and every piece of telemetry along the way records it as the **operation ID**.

==Use one Application Insights resource per environment for every component of the system, and make sure trace context crosses every boundary; a trace that breaks at the first hop is just more logs.==

The views that use it:

- **[Application map](gl:application-map)**: every component and dependency as a graph, with call rates, failure rates and latency on each connection. The first place to look when *something* is slow.
- **End-to-end transaction details**: one operation as a timeline, every hop with its duration.
- **Failures** and **Performance**: exceptions and failed dependencies grouped by type; each operation's 50th, 95th and 99th percentile duration.
- **Live metrics**: requests, failures and CPU in near real time, for watching a release go out.

For the Sydney complaint, the application map showed the catalogue API making 42 SQL calls per product page, one per variant. That is invisible from London at 300 milliseconds, and eight seconds from Sydney once each call pays the round trip. One query replaced the 42.

## Making it useful: releases, business events, availability

- **Release annotations.** The pipeline marks each deployment on the charts. A step change in checkout's p95 right after Tuesday's release is obvious in minutes, not four days.
- **Custom events and dimensions.** Record `CheckoutCompleted` with the basket value and payment provider, and failures can be read as lost revenue by provider, not just error counts.
- **[Availability tests](gl:availability-test).** *Standard tests* request a URL from five or more locations around the world every few minutes and check the status and certificate. They catch "the site is down from Australia" before shoppers report it. The older URL ping tests are being retired, so use standard tests. For multi-step journeys, write a custom test that reports its result from a timer function.

## Cost and privacy

Application Insights costs the same as other workspace data, about $2.30-2.80 per GB. A busy API can generate a lot. **[Sampling](gl:sampling)** keeps a representative fraction of telemetry - say 25% of requests - and keeps each trace whole, so every sampled request still has its dependencies and exceptions. Counts are scaled up in the portal. Sample where volume is high and individual requests are unremarkable, like the catalogue. Keep checkout at 100%.

Telemetry is data about people. Client IP addresses are masked by default. Do not put names, emails, card details or tokens into custom properties or log messages; scrub them in a telemetry processor if a library does.

## In practice

The shop's setup: `appi-shop-prod` and `appi-shop-nonprod`, workspace-based on the environment workspaces. The Node API and the Functions use the OpenTelemetry distro, configured by connection string. The React app uses the JS SDK with the React plugin, and the React Native app uses its plugin. Trace context is allowed through CORS, and Service Bus messages carry it. The catalogue API is sampled at 25%; checkout is not sampled. Standard availability tests hit the home page, `/health` and a synthetic checkout from five regions. The pipeline adds release annotations, and `CheckoutCompleted` is a custom event with value and provider.

**What breaks.**

- **One Application Insights per microservice.** The map shows islands and traces stop at every boundary. Use one per environment.
- **CORS stripping trace headers.** Browser traces never join the server's. Allow `traceparent` through.
- **Instrumentation loaded late.** Modules loaded before the distro are not instrumented. Initialise it first.
- **Debug logging in production.** Every `console.log` becomes billable trace telemetry. Log at Information and above.
- **Personal data in telemetry.** It is now in a second system with its own retention and access rules.

## Map it to what you know

| You already know | In Application Insights |
|---|---|
| New Relic, Datadog APM or Dynatrace | Application Insights with OpenTelemetry |
| The Network tab waterfall in Chrome DevTools | End-to-end transaction details, across servers |
| Sentry for front-end errors | Browser exceptions from the JS SDK, in the Failures view |
| SQL Server Profiler watching an app's queries | SQL dependency tracking, including N+1 patterns |
| `console.time` around a slow call | Automatic dependency durations with percentiles |
| Pingdom or UptimeRobot | Standard availability tests |

## Guiding your team

> [!TEAM]
> For every service before it ships, ask:
>
> 1. **Is it instrumented, and does its telemetry go to the environment's one Application Insights resource?**
> 2. **Pick a request: can we see it from the browser to the last function, in one timeline?**
> 3. **Is each release marked on the charts, and do we compare p95 before and after?**
> 4. **Which availability tests would tell us the site is down from Australia?**
> 5. **What is sampled, and is any personal data leaving in telemetry?**

## Key takeaways

- Application Insights records requests, dependencies, exceptions, traces, page views and custom events into the Log Analytics workspace.
- Instrument servers with the Azure Monitor OpenTelemetry distro, initialised first, and browsers and mobile apps with the JS SDK and its plugins.
- Distributed tracing carries one operation ID across HTTP and Service Bus, so one request becomes one timeline. Use one resource per environment.
- The application map, end-to-end transactions, performance percentiles and live metrics find the slow and failing hop. Release annotations catch regressions the day they ship.
- Standard availability tests watch from outside; sampling controls cost; personal data stays out of telemetry.
