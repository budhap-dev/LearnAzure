## Why this matters

> [!SCENARIO] The dependency App Service will not install
> Ana's Node API at Priya's retailer has grown a thumbnailing endpoint. It needs ImageMagick and a specific version of a native image library, installed at the operating-system level. On her MacBook it works. On the build agent it works, because someone once ran `apt-get install` on it by hand and nobody has rebuilt that agent since. On [App Service](gl:app-service) it does not work at all, because you do not get to install system packages on a platform Microsoft patches for you.
>
> Dev suggests a [virtual machine](gl:virtual-machine). Ana suggests a container. Priya wants to know what that actually changes, who patches what afterwards, and what it costs.

Ana is right, and this lesson is why - plus the three ways to run that container on Azure without anyone saying "Kubernetes".

## What a container actually changes

A [container](gl:container) is your application plus its runtime and the operating-system libraries it needs, packaged as one immutable **[container image](gl:container-image)** built from a **[Dockerfile](gl:dockerfile)**. When it runs, it shares the host's kernel with every other container on that host. That is the whole trick: it is not a virtual machine, there is no guest OS booting, and a cold start is a process start rather than a machine start.

If you have run Docker Compose on a laptop you know the shape. What changes on Azure is the responsibility line from [lesson 1.2](lesson:1.2).

| Layer | VM (IaaS) | Container on Azure | App Service (PaaS) |
|---|---|---|---|
| Host hardware and hypervisor | Microsoft | Microsoft | Microsoft |
| Host operating system | **You** | Microsoft | Microsoft |
| Base image and its CVEs | **You** | **You** | Microsoft |
| Runtime version (Node 24, .NET 10) | **You** | **You** | Microsoft |
| Application code and data | You | You | You |

Read the middle column against the other two. Compared with a VM you drop the host and the OS - a real saving. Compared with App Service you take *back* the base image and the runtime, and with them the security bulletins. ==A container buys you control of the runtime, and the price is that base image patching becomes your job, forever.==

## The registry: where images live

An image has to live somewhere both your build and your platform can reach. That is a registry, and on Azure it is **[Azure Container Registry](gl:azure-container-registry)** (ACR) - a private Docker registry as a resource in your [resource group](gl:resource-group).

Two things to get right on day one:

**Tags versus digests.** An **[image tag](gl:image-tag)** such as `api:1.4.2` is a mutable label; a digest such as `sha256:9c1f…` is the content itself. Anyone with push rights can point a tag at different bytes, so `:latest` in production means "whatever was pushed most recently, by anyone, for any reason" - a deployment you cannot reproduce and a rollback target that no longer exists. Tag with the Git commit SHA, and deploy by digest.

**Identity, not passwords.** ACR ships with an admin user: a single shared username and password that appears in pipeline logs and never rotates. Turn it off. Give the build pipeline and the runtime a [managed identity](gl:managed-identity) with `AcrPush` and `AcrPull` respectively, and there is no credential to leak.

| Tier | Roughly | What it adds |
|---|---|---|
| Basic | ~£4/month | 10 GB included, one region. Fine for dev and small teams. |
| Standard | ~£15/month | 100 GB, more throughput. The normal production choice. |

**[Azure Container Instances](gl:azure-container-instances)** is a single container with an IP address and a billing meter. No load balancer, no rolling deploy, no health-based restart across instances. It shines for the thing that runs for four minutes at 2 a.m. and then stops costing money. It is the wrong home for a web API that must stay up.

**[Azure Container Apps](gl:azure-container-apps)** is the default answer. It is serverless containers on a managed Kubernetes you never see and never patch. You get **[revisions](gl:revision)** and traffic splitting, HTTPS [ingress](gl:ingress) with a free managed certificate, **scale to zero** (the same idea [lesson 2.4](lesson:2.4) covers for Functions), event-driven scaling through **[KEDA](gl:keda)** on queue length or HTTP concurrency, **[Dapr](gl:dapr)** for service-to-service calls and pub/sub, and jobs for scheduled work. If a container has to serve traffic in production, start here.

**App Service for Containers** is the same [App Service plan](gl:app-service-plan) from [lesson 2.2](lesson:2.2), with an image instead of a zip. It keeps your slots, your VNet integration and your existing runbooks. Pick it when the team is already on App Service and the only thing that changed is the deploy unit.

## Revisions and traffic splitting

A revision is an immutable snapshot of a container app: this image, these environment variables, this scale rule. Deploy a new one and both exist; you decide the split. Ten per cent to revision 13 for an hour, watch the error rate in [Application Insights](gl:application-insights), then go to a hundred - or back to zero, which is your rollback.

This is the [deployment slot](gl:deployment-slot) idea from [lesson 2.2](lesson:2.2) with a different mechanism. A slot swap is binary and instant; a revision split is gradual and percentage-based. Slots warm a whole app instance; revisions are just labels on running containers.

## In practice: cost, and what containers do not fix

ACI bills per second of vCPU and memory, so a job using 1 vCPU and 2 GB for ten minutes a night costs pennies a month. Container Apps has a monthly free grant (roughly 180,000 vCPU-seconds and 2 million requests, illustrative) and then charges per request and per resource-second, so with scale to zero a quiet internal service can bill nothing overnight. The registry is a flat per-day tier charge plus storage above the included quota.

> [!WARNING] What a container does not fix
> - It does not make an app **scalable**. A singleton with in-memory session state is still a singleton in a container.
> - It does not make it **resilient or observable**. You still add health probes, retries and telemetry.
> - It moves the dependency problem into your build. "Works on my machine" becomes "works with that base image", and someone must upgrade it.
> - Base images need patching on a schedule, with a pipeline that rebuilds and redeploys. Put it in the sprint, not in someone's head.
> - It is **not** a reason to adopt Kubernetes. That is [lesson 2.6](lesson:2.6), and the honest answer there is usually no.

## Map it to what you know

| You already do | On Azure |
|---|---|
| `docker build` on your laptop | The same build in a pipeline, pushed to Azure Container Registry |
| `docker run -p 3000:3000` | A container app revision with ingress and a certificate |
| Docker Compose for API plus Redis plus worker | A Container Apps environment holding several apps that talk internally |
| npm packages pinned in a lockfile | Base images pinned by digest - same discipline, bigger blast radius |
| A private npm registry for internal packages | Azure Container Registry for internal images |
| `pm2 reload` for a zero-downtime restart | A new revision, then shifting traffic to it |

## Guiding your team

> [!TEAM]
> When someone proposes containerising a service, ask:
>
> 1. **What does the container give us that App Service does not?** A native dependency or a runtime Microsoft does not offer is a good answer. "It is more modern" is not.
> 2. **Who rebuilds the base image when a CVE lands?** Name the person and the schedule before you ship.
> 3. **What is our tag policy?** If anyone says `:latest`, stop and fix it now - commit SHA in, deploy by digest.
> 4. **Is the admin user disabled on the registry?** Managed identity for push and pull, no exceptions.
> 5. **Does this need to stay up?** If yes, it is Container Apps, not Container Instances.

## Key takeaways

- A container is your app plus its runtime and OS libraries, sharing the host kernel - not a VM.
- It drops the OS and host compared with IaaS, but takes back the base image and runtime from PaaS. You now own those CVEs.
- Azure Container Registry holds the images; tag by commit SHA, deploy by digest, never `:latest`, and authenticate with a managed identity rather than the admin user.
- Container Instances for jobs and bursts, Container Apps for almost everything that serves traffic, App Service for Containers when you are already there.
- Revisions plus traffic splitting are deployment slots done by percentage, and scale to zero means a quiet service can cost nothing.
- Containers do not make an app scalable, resilient or observable - and they are not a reason to adopt Kubernetes.
