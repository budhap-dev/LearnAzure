## Why this matters

> [!SCENARIO] Six engineers and three services
> Ana's team has containerised the Node API from [lesson 2.5](lesson:2.5) and two small workers. At the sprint review, a senior developer proposes moving all three onto **Azure Kubernetes Service**. The reasons offered are that it is the industry standard, that every job advert asks for it, and that it would stop them being locked into Azure.
>
> Priya turns to Ana: "You are the lead. Yes or no, and why?" The team is six people. Nobody has run a cluster before. There is no platform engineer, and the on-call rota is three of those six.
>
> Ana needs to answer without sounding like she is dodging the modern thing.

This lesson gives you both halves: enough Kubernetes to hold your own in the conversation, and an honest test for when the answer should be no. Most teams reaching for AKS do not need it - and saying so is a leadership skill, not a technical opinion.

## Kubernetes in plain words

**[Kubernetes](gl:kubernetes)** is a cluster of machines plus a control loop. You declare the desired state - "six copies of this image, reachable on port 3000" - and the cluster continuously works to make reality match. Nothing is imperative: you do not start containers, you describe how many should exist.

The vocabulary is small and worth knowing exactly:

| Term | One sentence |
|---|---|
| **[Pod](gl:pod)** | The smallest unit that runs: one container (occasionally a few that must share a network and disk). |
| **[Node](gl:node)** | A virtual machine in the cluster that pods are placed on. |
| **[Node pool](gl:node-pool)** | A group of identical nodes, backed by a [virtual machine scale set](gl:virtual-machine-scale-set), scaled and upgraded together. |
| **Deployment** | The declaration "keep N pods of this image running", which handles rolling updates and replacement. |
| **Service** | A stable internal name and IP for a set of pods, because pods come and go. |
| **[Ingress controller](gl:ingress-controller)** | The reverse proxy that maps public hostnames and paths to services. |
| **[Kubernetes namespace](gl:kubernetes-namespace)** | A logical partition inside one cluster, used for team or environment separation and quotas. |

One naming trap. The **[Kubernetes control plane](gl:kubernetes-control-plane)** - the API server, scheduler and etcd that run the control loop - is not the [control plane](gl:control-plane) from [lesson 1.5](lesson:1.5), which means Azure Resource Manager. Two different things, one phrase. In a mixed room, always say which one you mean.

| Microsoft runs | You run |

The control plane being free is the detail that misleads people. AKS itself has no meaningful price tag; the cluster costs what its nodes cost, and the nodes are ordinary virtual machines billed by the hour whether or not a single pod is scheduled on them.

## Node pools, and where the money goes

Every cluster has a **system node pool** for CoreDNS and the platform add-ons, plus one or more **user node pools** for your workloads. Pools are where the practical decisions live:

- **VM size** sets the shape of what fits. Pods request CPU and memory; a node with 4 vCPU cannot hold six pods each requesting 1 vCPU. Too small and nothing schedules, too large and you pay for headroom nobody uses.
- **[Spot virtual machine](gl:spot-virtual-machine) pools** run interruptible work at a heavy discount, with the catch that Azure can evict a node at two minutes' notice. Fine for batch, wrong for the checkout API.
- **The [cluster autoscaler](gl:cluster-autoscaler)** adds nodes when pods cannot be placed and removes them when nodes sit empty for long enough. It is not the same as the Horizontal Pod Autoscaler, which adds *pods*; you generally need both, and each has its own lag.

Illustrative UK South figures, subject to change: three D4s v5 nodes for a user pool plus two smaller system nodes lands around £550-700 a month before storage, egress or the Uptime SLA tier - and that is the bill at 3 a.m. with zero traffic. Compare that with a container app that scaled to zero at midnight. **Paying for idle nodes is the single biggest source of AKS waste**, and it is structural: the cluster cannot go to zero, because something has to be running to notice that work arrived.

## How work gets in

You describe the desired state in YAML manifests and apply them with **[kubectl](gl:kubectl)**, the command-line client that talks to the Kubernetes API server. Real teams do not hand-write a manifest per environment: they package the chart once and template the differences with **[Helm](gl:helm)**, which is roughly npm plus a templating engine for Kubernetes. An ingress controller such as NGINX or Application Gateway for Containers handles HTTP routing, TLS termination and certificates. Images come from [Azure Container Registry](gl:azure-container-registry), pulled with a [managed identity](gl:managed-identity) exactly as in [lesson 2.5](lesson:2.5).

In production the apply step is usually not a person at all: a GitOps agent watches a repository and reconciles the cluster to whatever is committed. [Module 7](module:7) covers that properly.

## The job you are signing up for

The monthly node bill is the visible cost. The invisible one is a standing commitment of engineering time.

| The work | Roughly what it takes |
|---|---|
| Kubernetes version upgrades | Every few months; versions fall out of support on a fixed cadence, so this never stops |
| Node image patching | Monthly, with drain and surge capacity planned so nothing goes down |
| Capacity planning | Ongoing: pod requests and limits, node sizes, autoscaler thresholds |
| RBAC and network policy | Set up once, then reviewed whenever a team or namespace is added |
| Secrets and certificates | A vault integration, plus rotation that actually runs |
| Observability | Metrics, logs and traces wired up per cluster - none of it arrives by default |
| On-call knowledge | Somebody who can debug a CrashLoopBackOff, a pending pod or an evicted node at 2 a.m. |

For Ana's six people, that table is most of a full-time role. For a platform team of four serving thirty services, it is the job they already do.

## The honest test

Score your situation. These are the questions that actually predict whether AKS pays for itself:

1. **More than roughly ten services**, with genuinely different scaling shapes and deployment rhythms?
2. **An existing Kubernetes investment** - charts, operators, people who have run clusters before?
3. **Portability across clouds** as a real, funded requirement someone has budgeted for, rather than a slide?
4. **A specific need Container Apps cannot meet**: custom schedulers, a service mesh beyond what Dapr offers, GPU scheduling, strict multi-tenancy, or Kubernetes operators you depend on?
5. **A named person who owns the platform**, with time protected for it in the plan?

Two or three clear yeses, and AKS is a reasonable decision. ==If most of your answers are no, Container Apps from [lesson 2.5](lesson:2.5) gives you most of the benefit for a fraction of the burden.==

Ana's answer to the sprint review is therefore no, with reasons: three services, no cluster experience, no funded portability requirement, nothing Container Apps cannot host, and no platform owner. The lock-in argument is the weakest of the three offered - Kubernetes portability is real for manifests, but the load balancers, storage classes, identity and monitoring underneath are cloud-specific anyway. [Lesson 2.7](lesson:2.7) picks that argument apart.

## The alternatives ladder

| Option | What it adds | What it costs you |
|---|---|---|
| ![App Service](az:app-service) App Service | Zip or image deploy, slots, autoscale | Little; least control over the runtime |
| ![Container Apps](az:container-apps) [Container Apps](gl:azure-container-apps) | Revisions, KEDA scaling, scale to zero, Dapr | No cluster access, no custom schedulers or operators |
| ![AKS Automatic](az:aks-automatic) AKS Automatic | A real cluster with node management, scaling and defaults preconfigured | Real Kubernetes skills still needed to debug it |
| ![AKS](az:aks) AKS standard | Full control: any operator, mesh, scheduler or networking model | The whole table above, permanently |

Move up a rung only when you can name the thing the rung below cannot do.

## Map it to what you know

| You already know | The Kubernetes equivalent |
|---|---|
| `pm2` or systemd restarting a crashed process | A Deployment and its ReplicaSet keeping N pods alive - across machines |
| A Docker Compose file | A set of manifests: Deployment, Service, Ingress |
| npm and package.json | Helm and a chart, with values files per environment |
| Nginx reverse-proxying to Node processes | An ingress controller routing to services |
| A VPS you sized once | A node pool, except the autoscaler resizes it and you pay per node-hour |
| "The ops team will look after it" | A platform team - and if you cannot name it, that is your answer |

## Guiding your team

> [!TEAM]
> When AKS is proposed, ask these in the room:
>
> 1. **What can Kubernetes do that Container Apps cannot?** Insist on a specific capability, not a category.
> 2. **Who owns the cluster on the day someone leaves?** A name, with time in the plan.
> 3. **What will idle nodes cost us each month?** Get the number before the decision, not after the first invoice.
> 4. **Is portability funded?** If no one has budgeted to prove it, it is not a requirement.
> 5. **Can our on-call debug a pending pod at 2 a.m.?** If not, that training is part of the proposal.

## Key takeaways

- Kubernetes is a declarative control loop over a cluster: pods run on nodes, nodes are grouped in node pools, and namespaces partition one cluster.
- Say "Kubernetes control plane" explicitly - "control plane" alone means Azure Resource Manager.
- AKS gives you a free, managed Kubernetes control plane; you still own node pools, upgrades, networking, observability and the bill.
- Nodes bill by the hour whether pods use them or not, which is why idle capacity is the biggest source of AKS waste.
- The real cost is people: upgrades, patching, capacity planning, RBAC, secrets and someone who can debug a cluster at 2 a.m.
- Apply the honest test. Fewer than about ten services, no existing investment and no platform owner means Container Apps, not AKS.
