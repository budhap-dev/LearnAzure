## Why this matters

> [!SCENARIO] A workflow copied from a blog post
> The API has moved to GitHub ([lesson 7.1](lesson:7.1)), and Ana's first workflow works on the first try. It was copied from a blog post. It deploys to production on every push to *any* branch. It signs in to Azure with a publish profile stored as a repository secret. It uses a third-party action pinned to `@master`. And it runs with a token that can write to everything in the repository.
>
> Dev asks the obvious question: if someone opened a pull request that changed this file, what could they do? The honest answer is "almost anything".
>
> Priya wants GitHub Actions to deliver what Azure Pipelines does in [lesson 7.3](lesson:7.3) - built once, gated, no secrets - and to be hard to misuse.

## Anatomy of a workflow

**[GitHub Actions](gl:github-actions)** runs CI/CD from files in `.github/workflows/`. A **[workflow](gl:github-actions-workflow)** has:

- **Triggers** (`on:`) - a push, a pull request, a manual run, a schedule, a release.
- **Jobs** that run in parallel unless one `needs` another, each on a **[runner](gl:runner)**.
- **Steps** in each job, which either `run` a shell command or `use` an **action** - a reusable building block such as `actions/checkout` or `azure/login`.

The API's workflow builds once, deploys to a staging slot automatically, and waits for approval before production:

```yaml
name: shop-api
on:
  push:
    branches: [main]

permissions:
  contents: read                      # least privilege by default

concurrency: { group: shop-api-deploy, cancel-in-progress: false }

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@<pinned-commit-sha>
      - uses: actions/setup-node@<pinned-commit-sha>
        with: { node-version: 24, cache: npm }
      - run: npm ci && npm test && npm run build
      - uses: actions/upload-artifact@<pinned-commit-sha>
        with: { name: api, path: dist }

  deploy-staging:
    needs: build
    runs-on: ubuntu-latest
    environment: staging
    permissions: { id-token: write, contents: read }
    steps:
      - uses: actions/download-artifact@<pinned-commit-sha>
        with: { name: api }
      - uses: azure/login@<pinned-commit-sha>            # OIDC: no secret
        with:
          client-id: ${{ vars.AZURE_CLIENT_ID }}
          tenant-id: ${{ vars.AZURE_TENANT_ID }}
          subscription-id: ${{ vars.AZURE_SUBSCRIPTION_ID }}
      - uses: azure/webapps-deploy@<pinned-commit-sha>
        with: { app-name: app-shop-api, slot-name: staging, package: . }

  deploy-production:
    needs: deploy-staging
    runs-on: ubuntu-latest
    environment: production                            # required reviewers, main only
    permissions: { id-token: write, contents: read }
    steps:
      - uses: azure/login@<pinned-commit-sha>
        with:
          client-id: ${{ vars.AZURE_CLIENT_ID }}
          tenant-id: ${{ vars.AZURE_TENANT_ID }}
          subscription-id: ${{ vars.AZURE_SUBSCRIPTION_ID }}
      - run: az webapp deployment slot swap -g rg-shop-prod -n app-shop-api --slot staging
```

Real workflows pin each action to a full commit SHA - `<pinned-commit-sha>` above stands in for one. The slot swap is covered in [lesson 7.7](lesson:7.7).

## Signing in to Azure without a secret

`azure/login` with OpenID Connect uses **[workload identity federation](gl:workload-identity-federation)** ([lesson 4.5](lesson:4.5)). The job asks GitHub for a signed token (that is what `id-token: write` permits), and Entra ID exchanges it for an Azure token. It does so only if the token's **subject** matches a federated credential you configured - for example `repo:shop/shop-api:environment:production`.

==Bind each Azure identity to a GitHub environment, so only jobs running in that environment, after its protection rules have passed, can act as that identity.== The production identity then cannot be used by a pull request, a feature branch or any other workflow.

## Environments and protection rules

A **[GitHub environment](gl:github-environment)** plays the same role as an Azure Pipelines environment. It holds its own variables and secrets, and **protection rules** that must pass before a job using it starts:

- **Required reviewers**: named people or teams approve the deployment.
- **Deployment branches and tags**: only `main` - or only release tags - may deploy here. Without this, `workflow_dispatch` from a feature branch could reach production.
- **Wait timer**: a pause before deployment, for a final check.
- **Custom protection rules**: an external check, such as Azure Monitor showing the target healthy.

## Runners

| Runner | What it is | Good for |
|---|---|---|
| **GitHub-hosted** | A fresh VM per job, patched by GitHub | Most builds and deployments to public endpoints |
| **Larger runners** | More CPU and memory, static IPs, and Azure private networking in your VNet | Heavy builds; reaching private endpoints without owning machines |
| **Self-hosted** | Your own machines or Kubernetes (Actions Runner Controller) | Special hardware, on-premises targets |

Minutes are included in each plan. Windows minutes count double and macOS ten times, so the iOS build is the expensive one. Never attach self-hosted runners to public repositories, where anyone's pull request could run code on them.

## Keeping workflows safe

A workflow file is code that runs with your credentials. Treat it that way:

- **Least-privilege `GITHUB_TOKEN`.** Set `permissions: contents: read` at the top and grant more per job only where needed.
- **Pin third-party actions to a commit SHA**, not `@master` or a movable tag. In 2025 a popular action was compromised and its tags re-pointed at malicious code that dumped secrets into build logs across thousands of repositories. Dependabot can keep pinned SHAs up to date.
- **Never trust pull request content in scripts.** Pull request titles and branch names inserted straight into `run:` commands allow script injection. Pass them through environment variables instead, and avoid `pull_request_target` with untrusted code.
- **CODEOWNERS on `.github/workflows/`** ([lesson 7.2](lesson:7.2)), so pipeline changes get platform review.
- **`concurrency`** groups, so two deployments to the same environment never overlap.

Share workflow logic with **[reusable workflows](gl:reusable-workflow)** (`workflow_call`) in a platform repository, and **composite actions** for groups of steps. Organisation rulesets can require specific workflows to run on every repository.

## From Azure Pipelines to GitHub Actions

| Azure Pipelines | GitHub Actions |
|---|---|
| Stage and job | Job, ordered with `needs` |
| Task | Action |
| Agent and pool | Runner and runner group |
| Environment with approvals and checks | Environment with protection rules |
| Service connection (federated) | `azure/login` with OIDC and a federated credential |
| Template and extends template | Reusable workflow and required workflows |
| Variable group linked to Key Vault | Environment and repository variables and secrets, or Key Vault at run time |

## In practice

The shop's API, web app and infrastructure repositories now share one reusable deploy workflow from `shop/platform`. Pull requests run build, tests and scanning as required checks. Merges to `main` build one artefact, deploy it to the staging slot, and wait for an operations reviewer before the production swap. Each environment has its own federated identity scoped to its resource group, and no Azure secret exists in GitHub. Actions are pinned by SHA and updated by Dependabot, the default token is read-only, and workflow files need platform-team review.

**What it costs.** GitHub Team includes 3,000 Linux minutes a month; the shop's web and API use about half. The iOS builds are the ones to watch.

**What breaks.**

- **Publish profiles and client secrets in repository secrets.** Use OIDC federation.
- **Deploying from every branch.** Deployment branch rules on each environment.
- **Unpinned third-party actions.** A tag can be moved to malicious code overnight.
- **A write-all default token.** One compromised step can push code or tamper with releases.
- **Self-hosted runners on public repositories.** Anyone's pull request becomes code running inside your network.

## Map it to what you know

| You already know | In GitHub Actions |
|---|---|
| Azure Pipelines YAML | Workflows - see the table above |
| Jenkins, CircleCI or GitLab CI | Workflows with jobs, runners and a large action marketplace |
| npm packages you import | Actions you `use` - with the same supply-chain risks, so pin them |
| A deployment approval email | An environment's required reviewers |

## Guiding your team

> [!TEAM]
> For every workflow that deploys, ask:
>
> 1. **Which branches can reach production, and which environment rules enforce that?**
> 2. **Is there any Azure secret in GitHub, or is it OIDC federation bound to environments?**
> 3. **What can the `GITHUB_TOKEN` do in each job?**
> 4. **Are third-party actions pinned to commit SHAs, and who reviews workflow changes?**
> 5. **Is deploy logic shared through reusable workflows, or copied between repositories?**

> [!TIP] Exam link
> AZ-400 covers GitHub Actions for Azure deployments, environments and OIDC. The GitHub Actions certification (GH-200) goes deeper into workflows, runners, reusable workflows and security.

## Key takeaways

- A workflow is triggers, jobs on runners, and steps that run commands or use actions; `needs` orders jobs.
- Sign in to Azure with OIDC federation, with one identity per GitHub environment, so production credentials exist only in jobs that passed production's protection rules.
- Environments carry required reviewers and deployment branch rules - the gates that stop feature branches reaching production.
- Treat workflows as privileged code: read-only token by default, actions pinned to SHAs, untrusted input kept out of scripts, CODEOWNERS on workflow files.
- Share logic with reusable workflows; every Azure Pipelines concept has a direct equivalent.
