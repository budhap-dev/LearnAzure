## Why this matters

> [!SCENARIO] The integration is a person called Mei
> Every night at 22:00, Mei in finance downloads the marketplace's settlement file from an SFTP server, pastes it into Excel, emails a summary to accounting, and keys the refunds into the ERP by hand. A supplier sends stock updates as email attachments, which someone forwards to the warehouse. Ops would like a Teams message whenever an order over £2,000 arrives.
>
> Ana offers to write a Node service for each, with the SFTP client, the Excel parsing, the Outlook API and the Teams API. Meanwhile finance built a Power Automate flow last year for refund approvals. It stopped working in March, because it ran under the account of someone who has since left.
>
> Priya's question is not how to write these integrations. It is whether they should be written at all.

## Workflows, triggers and connectors

**[Azure Logic Apps](gl:azure-logic-apps)** runs **workflows**: a [trigger](gl:trigger) - a schedule, an HTTP call, a new email, a Service Bus message, a file on SFTP - followed by **actions**: conditions, loops, parallel branches, and calls to other systems. Workflows are built in a visual designer and stored as JSON, so they can live in source control.

The value is in the **[connectors](gl:connector)**. Logic Apps has well over a thousand: Azure services, Microsoft 365, SFTP, SQL Server, Salesforce, ServiceNow, SAP and more. Each one knows how to authenticate, page through results and handle its API's quirks. ==For glue between systems that already have connectors, configuring a workflow is usually faster, safer and easier to operate than writing a service.==

Every run is recorded with the inputs and outputs of every step. When the settlement import fails at step 4 on Tuesday night, anyone can see what arrived, what failed and why, and resubmit that run.

## Consumption or Standard

| | Consumption | **[Logic Apps Standard](gl:logic-apps-standard)** |
|---|---|---|
| Hosting | Shared, serverless | Single-tenant, on a plan you size |
| Billing | Per action executed | A fixed plan price, from roughly $150-200 a month |
| Workflows | One per resource | Many per app |
| Networking | Public endpoints | VNet integration and private endpoints |
| Developer experience | Portal designer, deployed by templates | VS Code projects, local runs, deployed by pipeline |
| Best for | A few low-volume workflows | Many workflows, private resources, steady volume |

Consumption is cheap for a nightly job - fractions of a cent per action - but it grows with every loop iteration. A `for each` over 50,000 rows is 50,000 or more billed actions. Standard costs the same however busy it is.

## Which tool for which job

Several Azure tools run "a sequence of steps". They suit different people and problems:

| Tool | Built by | Fits |
|---|---|---|
| **Logic Apps** | Developers and integration engineers | System-to-system glue with connectors, visible run history, managed in source control |
| **[Power Automate](gl:power-automate)** | Business users, in Microsoft 365 | Personal and team automations: approvals, emails, spreadsheets. Same engine as Logic Apps |
| **Azure Functions** | Developers, in code | Custom logic, heavy computation, high throughput per event |
| **[Durable Functions](gl:durable-functions)** | Developers, in code | Long-running orchestrations where the logic is complex enough to deserve tests |

The honest rule is that **[low-code](gl:low-code)** wins where connectors do most of the work and the logic is simple, and code wins where the logic is the product. A workflow with forty nested conditions has become a program without the tools programs deserve.

## Doing low-code properly

Low-code still needs engineering discipline:

- **Identity.** Connections to Azure services use the workflow's [managed identity](gl:managed-identity). Connections that need a user, such as Outlook or Teams, use a service account owned by the team - never a person, because a person leaves. That is what broke the refund approvals flow.
- **Secrets** come from Key Vault at run time, not typed into the workflow.
- **Failure handling.** Set retry policies on actions, wrap steps in a scope with a *run after failure* branch - Logic Apps' try/catch - and send what cannot be processed to a queue for a person.
- **Environments and source control.** Parameterise connection details, keep workflow JSON in Git, and deploy dev, test and prod through a pipeline. Editing production in the portal is how a Friday evening fix becomes Monday's outage.
- **Monitoring.** Alert on failed runs, send diagnostics to Log Analytics, and give every workflow an owner.

For Power Automate, the Power Platform admin centre sets **data loss prevention** policies - which connectors may be combined, so nobody pipes customer data into a personal Dropbox - and separates environments for experiments and production.

## In practice

The shop gets one Logic App Standard, `la-shop-integration`, with VNet integration so it can reach private resources. Three workflows:

- **Settlement import**, nightly: SFTP, archive to Blob storage, each refund queued on Service Bus for the ERP integration, and a summary to finance in Teams.
- **Supplier stock updates**: triggered by a new email in a shared mailbox; parses the attachment and publishes stock changes to Service Bus.
- **High-value orders**: a subscription on `order-events` filtered to totals over £2,000, which posts to the ops channel.

All three live in a VS Code project in Git and deploy through the pipeline, with alerts on failed runs. Finance keeps Power Automate for approvals, rebuilt under a service account and covered by a DLP policy. Mei gets her evenings back.

**What it costs.** Roughly $150-200 a month for the Standard plan, against three Node services to build, host, patch and debug.

**What breaks.**

- **Flows owned by people.** A leaver's account takes the integration with it. Use managed identities and service accounts.
- **Production edited in the portal.** No review, no history, no way back. Deploy from Git.
- **Loop explosions on Consumption.** Per-action billing turns a large `for each` into a large bill; batch, or use Standard.
- **Connector limits.** SaaS connectors are throttled. Big data moves belong in Data Factory, not a workflow.
- **Logic that outgrew the designer.** When conditions nest five deep, move the logic to a function and call it from the workflow.

## Map it to what you know

| You already know | On Azure |
|---|---|
| SSIS packages and SQL Agent jobs moving files | Logic Apps workflows, or Data Factory for bulk data |
| BizTalk Server | Logic Apps plus an integration account for EDI and B2B |
| Zapier or IFTTT | Power Automate, and Logic Apps for the engineered version |
| A Node cron script importing five SDKs | One workflow with five connectors |
| An Excel macro someone runs every morning | A Power Automate flow, owned by the team |

## Guiding your team

> [!TEAM]
> Before anyone writes an integration service, ask:
>
> 1. **Do connectors already exist for every system involved?** If yes, start with a workflow.
> 2. **Whose identity does it run as, and what happens when that person leaves?**
> 3. **Where is the workflow's source, and how does a change reach production?**
> 4. **Who is alerted when a run fails, and how is it resubmitted?**
> 5. **Is the logic still simple?** When it is not, move it into code and call that.

## Key takeaways

- Logic Apps runs workflows of a trigger and actions, with well over a thousand connectors and a full run history for every execution.
- Consumption bills per action and suits a few light workflows; Standard is a fixed-price, single-tenant plan with VNet access, many workflows and VS Code projects.
- Low-code fits connector-heavy glue with simple logic; code fits complex logic. Power Automate is the same engine for business users.
- Run workflows as managed identities or team service accounts, never a person; secrets from Key Vault; errors handled with retries and scopes.
- Keep workflows in source control, deploy through pipelines, and alert on failed runs - low-code still needs engineering.
