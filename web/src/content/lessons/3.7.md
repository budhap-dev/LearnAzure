## Why this matters

> [!SCENARIO] Three databases for one shop
> On Monday a contractor's architecture pack proposes [Cosmos DB](gl:cosmos-db) for the whole shop, "because it scales globally". On Wednesday Ana asks for a document store for the product catalogue, because the React team would rather work in JSON than through an ORM. On Friday Dev asks whether reporting can point Power BI straight at the orders database, and finance asks why the estimate now shows three databases for a shop that ran on one SQL Server for eight years.
>
> Each proposal is defensible alone. Together they give Priya three [backup policies](gl:backup-policy), three security reviews and three things to get paged for, holding data that still looks like orders, customers and products.
>
> Priya needs one framework that gives the same answer whoever asks, and says out loud what would have to be true for the answer to change.

Six lessons have each argued their own corner. This one is the arbitration: one tree, one order of questions, one cost comparison, and a script for the review.

The tree has a centre of gravity, not a menu. ==Default to Azure SQL for transactional data your team already knows how to model; add a store only when a named requirement - shape, scale, latency, cost or analytics - forces it, and name who owns each one.== A [data store](gl:data-store) is not a line on a diagram; it runs, fails, gets backed up and gets audited for as long as the product exists.

## The six questions, in order

| # | Ask | If yes | Why it sits here |
|---|---|---|---|
| 1 | Is it a file or an object - an image, a PDF, an export? | [Blob Storage](gl:blob-storage) ([lesson 3.1](lesson:3.1)) | [Object storage](gl:object-storage) is pennies per GB and scales without thought. A file in a database is the dearest way to store bytes and the quickest way to slow a backup. It is the commonest mistake, so it comes first. |
| 2 | Is it a record with relationships that must stay consistent - an order, a customer, a payment? | [Azure SQL](gl:azure-sql) ([lesson 3.2](lesson:3.2)); or [PostgreSQL](gl:azure-database-for-postgresql) or MySQL ([lesson 3.5](lesson:3.5)) when the team or ecosystem is already there | Most business data is this, and a [relational database](gl:relational-database) with transactions and joins is the cheapest way to keep it correct. SQL versus Postgres is about people and tooling, not capability. |
| 3 | Do you need reads in several regions at single-digit-millisecond [latency](gl:latency), a schema that differs per item, or write scale beyond one region? | [Cosmos DB](gl:cosmos-db) ([lesson 3.3](lesson:3.3)) | Three named requirements, each with a number. "It might need to scale" is not one. Cosmos DB makes you choose a [partition key](gl:partition-key) and pay in [request units](gl:request-unit) on day one - a cost while the data's shape is still moving. |
| 4 | Is a read too slow or too frequent, or is it [session state](gl:session-state)? | [Azure Cache for Redis](gl:azure-cache-for-redis) in front of the store ([lesson 3.4](lesson:3.4)) | A [cache](gl:cache) goes in front of a database, never instead of one. With the [cache-aside pattern](gl:cache-aside-pattern) the store stays the [single source of truth](gl:single-source-of-truth); empty the cache and nothing is lost. |
| 5 | Are you asking questions over history - trends, cohorts, year-on-year? | A [data warehouse](gl:data-warehouse): Microsoft Fabric, Azure Synapse Analytics, or Azure Data Explorer for telemetry | Reporting is [OLAP](gl:olap) work and fights [OLTP](gl:oltp) work for the same CPU and locks. Copy the data out with [ETL](gl:etl) and query it there. This lesson only points at the door. |
| 6 | Are you searching by meaning - embeddings, "find products like this"? | [pgvector](gl:pgvector) on Postgres, vector search in Cosmos DB, or Azure AI Search ([lesson 8.5](lesson:8.5)) | A [vector database](gl:vector-database) is usually a feature of a store you already run, not a seventh store. Start there; move only when scale or relevance forces it. |

The order is the argument. Question 3 follows question 2 because reaching for Cosmos DB "for scale" is the most common over-reach; a well-indexed Azure SQL database on a few [vCores](gl:vcore) serves more transactions a second than most retailers will ever see. Questions 4 to 6 add stores *beside* the default rather than replacing it.

## OLTP, OLAP, relational, NoSQL - and CAP, honestly

**OLTP** is many small, correct transactions: place an order, change a password. **OLAP** is few large questions over lots of history: revenue by category by month. They want different indexes, different hardware and different hours of the day, which is why pointing Power BI at production is a Friday afternoon outage waiting to happen.

**Relational** stores put structure in the schema and let you join anything to anything; **[NoSQL](gl:nosql)** stores put structure in the application and give you scale and flexibility in return. Neither is newer or better. A [document database](gl:document-database) is wonderful for a product page read as one JSON blob and awful for "which customers bought both of these".

The **[CAP theorem](gl:cap-theorem)** says a distributed store cannot promise both perfect consistency and full availability while its nodes cannot talk to each other. True, and less useful in a review than it sounds: partitions are rare and the trade-off is a dial, not a switch, which is why Cosmos DB has five [consistency levels](gl:consistency-level). The better question is not "AP or CP?" but "what consistency does this screen actually need?" The basket must never show an item the customer removed; a "viewed today" counter can be a minute stale. Answer that per screen and the store follows.

## The cost shapes compared

Four billing shapes, each cheapest in a different place. Figures are rough 2025-2026 list-price ballparks in USD; run the [pricing calculator](gl:azure-pricing-calculator) before you quote one.

| Shape | Used by | What drives the bill | Cheapest when | Expensive when |
|---|---|---|---|---|
| **Per GB-month** | Blob Storage | Bytes stored x [access tier](gl:access-tier), plus operations and [egress](gl:egress) | Almost always: hot is around $0.02 per GB-month, cool about half, archive under a cent | Millions of tiny reads on cool, or archive retrievals in a hurry - retrieval and early-deletion fees drive the surprise |
| **Per vCore-hour** | Azure SQL, PostgreSQL, MySQL | Cores x hours, plus storage per GB-month; [Azure Hybrid Benefit](gl:azure-hybrid-benefit) and [reservations](gl:reservation) cut it | Steady transactional load. A 2-vCore General Purpose database is roughly $350-400 a month before discounts; a burstable Postgres for dev under $20 | Sized for the Black Friday peak all year, or ten databases each on their own compute instead of an [elastic pool](gl:elastic-pool) |
| **Per RU** | Cosmos DB | [Provisioned throughput](gl:provisioned-throughput) in RU/s per hour, or per million RUs on serverless, plus storage | Even or serverless traffic with a good [partition key](gl:partition-key): 1,000 RU/s is around $60 a month | A [hot partition](gl:hot-partition) that forces you to provision for one key, or every query being a cross-partition scan |
| **Per cache-size-hour** | Azure Cache for Redis | Tier x memory x hours, running or not | A small Standard cache, around $100 a month, taking most reads off a database you would otherwise scale up | A Premium cache holding data nobody reads, or a cache treated as the primary store and sized like one |

The crossover people miss is between vCores and RUs. A relational database bills for capacity you reserve and use however you like; Cosmos DB bills for a throughput figure that every query draws down. At low, even load Cosmos DB is often cheaper. At high load with joins, aggregates and cross-partition queries it is often dearer, because each of those costs many RUs. Neither is "the cheap one".

## The six stores side by side

| Store | Data shape | Scale model | Consistency | Cost driver | Backup | Team skill |
|---|---|---|---|---|---|---|
| Blob Storage | Files and objects | Effectively unlimited | Strong within a region | GB stored, tier, egress | [Soft delete](gl:soft-delete), versioning, [immutable](gl:immutable-storage) | Anyone |
| Azure SQL | Tables, joins, transactions | Scale up; [Hyperscale](gl:hyperscale) or [read scale-out](gl:read-scale-out) | Strong | vCores, storage | [PITR](gl:point-in-time-restore) built in, [LTR](gl:long-term-retention) optional | SQL Server people, already on staff |
| PostgreSQL / MySQL | Tables, plus [extensions](gl:postgresql-extension) | Scale up; [read replicas](gl:read-replica) | Strong | vCores, storage | PITR built in | Anyone from the open-source world |
| Cosmos DB | Documents, key-value, graph | Horizontal, by partition | Tunable, five levels | RU/s, storage | Continuous or periodic | Learned: partitioning and RU maths |
| Redis | Key-value and [data structures](gl:redis-data-structures) | Memory size, clustering | Best effort, in memory | Cache size-hours | Optional persistence; treat as none | Node and .NET clients are simple |
| Fabric / Synapse | Wide tables, columnar | Compute pools, capacity units | Eventually, via ETL | Capacity, queries | Copies of other stores | Data engineers, usually new hires |

Read the last two columns together. Every row after Azure SQL adds a backup story your [restore test](gl:restore-test) must cover and a skill your team must hire or learn. That is the real price of **[polyglot persistence](gl:polyglot-persistence)** - the sensible idea of using the right store for each job. It is right as far as it goes; it just never mentions that each store is an on-call rotation, a backup policy and a security review, forever. Two stores with named owners beat four with none.

## Three worked examples

| Workload | Question path | Answer | The line you say in the review |
|---|---|---|---|
| The orders system: orders, customers, payments, stock | Q1 no, Q2 yes. Q3: one region, stable schema, a few hundred writes a second at peak | [Azure SQL Database](gl:azure-sql-database), zone-redundant, PITR on, LTR for finance | "Orders are transactions with relationships. The team has modelled them in SQL Server for eight years, and nothing about UK South changes that. It is the single source of truth." |
| The product catalogue, served to shoppers in five countries | Q1 no, Q2 yes. Q3: reads in five countries, but every write comes from one merchandising team in the UK | Azure SQL plus Redis in front, plus a CDN for images and rendered pages - not Cosmos DB, yet | "The requirement is fast *reads* in five countries, not writes. Cache and edge serve that for a tenth of the cost of [multi-region writes](gl:multi-region-writes). If merchandising ever writes from five regions, or the schema starts varying per category, that is the trigger to move the catalogue to Cosmos DB." |
| Product images and PDF invoices | Q1 yes | Blob Storage: hot for images the site serves; invoices cool after 30 days and archived after a year, [immutable](gl:immutable-storage) for the regulator's retention period | "They are files. A [lifecycle policy](gl:lifecycle-management-policy) moves them down the tiers on a schedule, and the invoices cannot be altered or deleted for seven years, even by an admin." |

Notice that the catalogue is the only contested one, and the argument turns on a single fact: where the writes come from. A proposal that cannot name the fact its answer depends on has not finished its argument.

## When to revisit

Data store choices are less reversible than compute choices: moving a schema is a project, not a sprint. Write the triggers down when you decide, so the revisit is a scheduled review rather than an argument.

- **Writes must originate in a second region**, or a latency target cannot be met from one region even with a cache and a CDN.
- **The schema starts varying per record** - a wide sparse table of nullable columns is the smell.
- **Reporting queries appear in the OLTP database's slow-query log.** Move them to a warehouse before they move your checkout out of its SLA.
- **A single database hits its ceiling** - vCores, storage or log throughput - and Hyperscale or sharding is on the table.
- **The [cache hit ratio](gl:cache-hit-ratio) falls** below what justified the cache, or a cache has quietly become the only copy of something.
- **The owner of a store leaves.** A store nobody understands is a risk, whatever the diagram says.

## Map it to what you know

| You already decide | The Azure equivalent |
|---|---|
| Storing uploads on disk versus as a `varbinary` column | Blob Storage versus a blob in the database - and the answer has not changed |
| SQL Server for the app; a reporting replica for the analysts | Azure SQL for OLTP; Fabric or Synapse for OLAP, fed by ETL |
| A `Map` in front of a slow function | Redis in front of a database, with a TTL and a plan for a miss |
| Choosing MongoDB for a side project because the front end speaks JSON | Cosmos DB - the same trade, at global scale, with a partition key you must get right |
| `git` as the source of truth; `node_modules` as a derived copy | The database as the single source of truth; caches and warehouses as derived copies |

## Guiding your team

> [!TEAM]
> Five questions that make a data-store proposal justify itself:
>
> 1. **Which question in the tree moved you off Azure SQL?** Name the requirement and its number - regions, milliseconds, writes per second. "It might need to scale" is not a requirement.
> 2. **Which store is the single source of truth, and which are derived copies?** Every cache and warehouse should be something you could delete and rebuild.
> 3. **What consistency does each screen need?** Basket, stock and payment need strong; a view counter does not. Decide per screen, not per system.
> 4. **Who owns each store - backup policy, restore test, on-call, security review?** A name per store. A store with no name is not a store, it is a liability.
> 5. **What would make us change this?** Write the trigger - a second write region, a schema that will not sit still, reporting in the slow-query log - into the design document today.

## Key takeaways

- Default to Azure SQL for transactional data the team can already model. Move only when a named requirement forces it, and name who owns whatever you add.
- Six questions, in order: a file; a consistent record; global latency, flexible schema or write scale; read latency or session state; analytics over history; search by meaning.
- Four cost shapes: per GB-month, per vCore-hour, per RU, per cache-size-hour. RUs are cheap at even, simple load and dear for cross-partition queries; vCores are the reverse.
- OLTP and OLAP want different stores. Reporting on the orders database is an outage on a timer.
- CAP is true and rarely the useful question. Ask what consistency each screen needs.
- Polyglot persistence is a cost, not a virtue: each store is a backup policy, a restore test, a security review and an on-call rotation. One single source of truth per fact.
