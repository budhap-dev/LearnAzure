## Why this matters

> [!SCENARIO] Merge day
> The API repository has a `develop` branch, three `release/` branches, two `hotfix/` branches and Ana's `feature/new-checkout`, which is six weeks old and 4,000 lines behind. Every other Thursday is *merge day*: an afternoon of conflicts, followed by a release nobody fully understands.
>
> Last month someone pushed straight to `main` by mistake and broke the build for a day. Pull request reviews are a thumbs-up within thirty seconds. And when the app store asked which version of the mobile app contained a fix, nobody could say.
>
> Moving the code to GitHub ([lesson 7.1](lesson:7.1)) is the moment to fix how it flows, not just where it lives.

## Two ways to branch

| | GitFlow | **[Trunk-based development](gl:trunk-based-development)** |
|---|---|---|
| Branches | `main`, `develop`, `release/*`, `hotfix/*`, long-lived `feature/*` | `main` plus short-lived branches that merge within a day or two |
| Integration | At merge time, often painful | Continuously, in small pieces |
| Unfinished work | Hidden on a long branch | Merged behind a [feature flag](gl:feature-flag) ([lesson 4.6](lesson:4.6)) |
| Releases | Cut from `release/*` branches | From `main`, which is always releasable, marked with a tag |
| Suits | Boxed products with several supported versions in the field | Web apps and APIs deployed continuously |

GitFlow was designed for software shipped on disks, with several versions supported at once. A web API has exactly one version in production. ==For anything deployed continuously, use trunk-based development: short-lived branches, small pull requests, `main` always releasable, and feature flags for anything not ready.==

Mobile apps are the one common exception, because app-store review takes days. A short `release/` branch is cut from `main` for each store submission, and only fixes are cherry-picked onto it.

## Pull requests that are worth reviewing

A **[pull request](gl:pull-request)** (PR) proposes merging a branch, and it is where automation and people check a change before it reaches `main`. Good ones share four traits:

- **Small.** Under about 400 changed lines, reviewers find real problems. Past that, they skim and approve.
- **Explained.** A description of *why*, a link to the work item, and screenshots for UI changes.
- **Machines first.** Build, tests, lint and security scans run on every push, so people spend their attention on design, naming and risk, not formatting.
- **Reviewed quickly.** A same-day review expectation keeps branches short-lived. A PR that waits three days turns into a long-lived branch.

Most teams **squash-merge**: each PR becomes one commit on `main` with a clear message, and the branch is deleted. The history then reads as a list of changes rather than a record of everyone's work-in-progress commits.

## Policies that enforce it

Good habits need rules the platform enforces. Both toolchains have them. Azure Repos calls them **[branch policies](gl:branch-policy)**; GitHub calls them **branch protection rules** or **rulesets**.

| Rule | Azure Repos | GitHub |
|---|---|---|
| Changes only through pull requests | Branch policy on `main` | Require a pull request before merging |
| Minimum approvals | Minimum number of reviewers | Required approving reviews |
| Build and tests must pass | Build validation | Required status checks |
| Specific people for specific paths | Automatically included reviewers | **[CODEOWNERS](gl:codeowners)** file |
| Comments resolved | Comment resolution | Require conversation resolution |
| Linked work item | Check for linked work items | Via a check or convention |
| No history rewriting | Restrict force push | Block force pushes and deletion |

A **CODEOWNERS** file maps paths to the people or teams who must review changes to them:

```
# .github/CODEOWNERS
/infra/               @shop/platform
/.github/workflows/   @shop/platform
/src/auth/            @shop/security
*                     @shop/api-team
```

Changes to infrastructure, pipelines and authentication then cannot merge without the right people. That matters, because a change to a workflow file can change what gets deployed, and with what permissions.

Apply the rules to **administrators too**. A protected branch that admins bypass "just this once" protects nothing on the day it matters. The repository this course is built from works this way: `main` accepts only pull requests, and only after the build-and-verify check passes.

## Versions people can talk about

**[Semantic versioning](gl:semantic-versioning)** - `MAJOR.MINOR.PATCH` - says what kind of change a release is: `2.4.1` to `2.4.2` is a fix, to `2.5.0` adds features compatibly, to `3.0.0` breaks something. Tag releases on `main` (`v2.5.0`), generate release notes from the merged pull requests, and stamp the version and commit into the build, so any running system can say exactly what it is. The app store's question then has an answer.

## In practice

The shop's rules, applied to every repository - `shop-web`, `shop-api`, `shop-mobile` and `shop-infra`:

- `main` protected: pull requests only, no force pushes or deletion, rules apply to administrators.
- Required checks: build, unit tests, lint and code scanning ([lesson 7.6](lesson:7.6)).
- One approval for application code; two for `shop-infra`. CODEOWNERS for infrastructure, workflows and authentication.
- Squash merges; branches deleted after merge.
- Branches expected to live under two days; bigger features merge behind flags.
- Releases tagged `vX.Y.Z` from `main`; the mobile app cuts a short release branch per store submission.

Two months later, merge day no longer exists. The median pull request is about 180 lines, and first reviews arrive within four hours.

**What breaks.**

- **Long-lived branches.** Conflicts grow with time; integration pain is paid all at once.
- **Rubber-stamp reviews.** Thirty-second approvals on 3,000-line changes. Keep PRs small, and let checks handle the mechanical parts.
- **Admin bypass.** Rules that the most privileged people skip.
- **Flaky required checks.** When a test fails randomly, people start overriding checks. Fix or quarantine flaky tests fast.
- **Rules in one repository only.** Use organisation-level rulesets so every repository starts protected.

## Map it to what you know

| You already know | In Git on Azure DevOps or GitHub |
|---|---|
| TFVC with check-in policies | Git with branch policies or protection rules |
| SVN trunk | Trunk-based development - the same idea, with short-lived branches |
| Code review meetings | Pull requests with required reviewers |
| A release branch per sprint | Tags on `main`, with feature flags for unfinished work |
| Assembly version numbers | Semantic versions stamped into the build |

## Guiding your team

> [!TEAM]
> For every repository, ask:
>
> 1. **Can anyone push to `main` directly - including admins?**
> 2. **How long do branches live, and how big is the median pull request?**
> 3. **Which checks must pass, and are any of them flaky?**
> 4. **Who must review infrastructure, workflow and security changes?**
> 5. **Can any running system tell us its exact version and commit?**

## Key takeaways

- Trunk-based development - short-lived branches, small pull requests, `main` always releasable, feature flags for unfinished work - suits anything deployed continuously. GitFlow suits multi-version boxed software.
- Good pull requests are small, explained, checked by machines first, and reviewed the same day.
- Branch policies in Azure Repos and protection rules in GitHub enforce pull requests, approvals and required checks - for administrators too.
- CODEOWNERS routes infrastructure, workflow and security changes to the people who must review them.
- Semantic versions, release tags and a version stamped into every build answer "what is running?"
