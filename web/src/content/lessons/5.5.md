## Why this matters

> [!SCENARIO] Fifty requests a second, all weekend
> The shop now has more API consumers than it planned for: its own web and mobile apps, four delivery partners checking order status, the warehouse integration, and a new marketplace that wants the product catalogue and live stock. Each API handles the rest itself. Partner API keys live in a table Ana wrote, there are no rate limits, and the documentation is a Word file sent by email.
>
> Last weekend one partner's buggy script called the stock API fifty times a second from Friday night to Monday. Checkout slowed, because the stock API shares a database with orders, and nobody could say which partner it was until Dev searched the logs.
>
> The marketplace wants a self-service portal with documentation and keys. Priya wants one front door for every API, where keys, limits, versions and documentation are handled once.

## What an API gateway does

Every API needs the same things around its business logic: who is calling, are they allowed, how much may they call, which version do they get, how is it documented, and what is it being used for. Written into each API, those concerns are duplicated, inconsistent and easy to forget.

An **[API gateway](gl:api-gateway)** handles them in one place, in front of the APIs. **[Azure API Management](gl:azure-api-management)** (APIM) is Azure's: a **gateway** that every call passes through, a **management plane** where APIs and rules are defined, and a **[developer portal](gl:developer-portal)** where consumers read documentation, try calls and get keys.

## The building blocks

- **APIs and operations.** Import an API from its **[OpenAPI](gl:openapi)** description - the Node API can generate one - and APIM knows every operation, parameter and response.
- **Backends.** Where each API really lives: an App Service, a Container App, a Function, or an address inside your VNet.
- **[Products](gl:api-product).** The packages consumers sign up for. One or more APIs, a set of rules and optionally an approval step: *Partners*, *Marketplace*, *Mobile*.
- **Subscriptions and [subscription keys](gl:subscription-key).** A consumer subscribes to a product and receives a key, sent in the `Ocp-Apim-Subscription-Key` header. The key identifies the caller for limits and analytics.
- **Versions and revisions.** A *version* is a new contract that consumers opt into (`/orders/v2`); a *revision* is a non-breaking change you can test and then make current.

## Policies: the rules on every call

The behaviour lives in **[API Management policies](gl:api-management-policy)**: small XML pipelines that run *inbound* (before the backend), *backend*, *outbound* (on the response) and *on-error*. They can be set globally, per product, per API or per operation, and each scope inherits from the one above. A partner policy might read:

```xml
<policies>
  <inbound>
    <base />
    <validate-jwt header-name="Authorization" failed-validation-httpcode="401">
      <openid-config url="https://login.microsoftonline.com/{tenant}/v2.0/.well-known/openid-configuration" />
      <audiences><audience>api://shop-partner-api</audience></audiences>
    </validate-jwt>
    <rate-limit-by-key calls="10" renewal-period="1" counter-key="@(context.Subscription.Id)" />
    <quota-by-key calls="1000000" renewal-period="2592000" counter-key="@(context.Subscription.Id)" />
    <authentication-managed-identity resource="api://shop-orders-backend" />
  </inbound>
</policies>
```

It validates the partner's Entra token, allows ten calls a second and a million a month per subscription, and calls the backend with APIM's own managed identity. **[Rate limiting](gl:rate-limiting)** is what would have stopped the weekend: the eleventh call in a second gets `429 Too Many Requests`, with a `Retry-After` header, and never reaches the stock API. Other policies cache responses, rewrite URLs, add or strip headers, mock an operation that is not built yet, and turn backend errors into consistent responses.

==Keep policies to cross-cutting rules - identity, limits, routing, caching, shape of errors - and keep business logic in the API, where it can be tested.==

## Keys identify; tokens authenticate

A subscription key is a long-lived shared string. It is good for knowing *which consumer* is calling, but it is not proof of identity: it leaks into logs, scripts and mobile app bundles. For anything that matters, pair it with a token - OAuth 2.0 client credentials for partners, External ID tokens for the mobile app ([lesson 4.4](lesson:4.4)) - and validate the token in the policy. Mobile apps should not carry subscription keys at all; their product can require a token and no key.

Then close the back door, as in [lesson 4.2](lesson:4.2). Backends accept only APIM: through private networking, access restrictions to APIM's addresses, or a managed-identity token that only APIM holds. An API that is still reachable directly makes every policy optional.

## Tiers, and where APIM sits

| Tier | For | Rough price |
|---|---|---|
| **Consumption** | Small or spiky APIs; serverless | Pay per call, with a free monthly allowance |
| **Developer** | Trying things out | About $50 a month, **no SLA** - never production |
| **Basic v2** | Production APIs with public backends | About $150 a month |
| **Standard v2** | Production, reaching private backends through a VNet | About $700 a month |
| **Premium** | Multiple regions, full network isolation, high scale | From about $2,800 per unit a month |

APIM is not a WAF and not a CDN. Front Door with its WAF sits in front of it for the internet-facing edge; APIM applies API-specific rules - consumers, keys, quotas, versions - behind it. For HTTP traffic the usual chain is **Front Door → API Management → backends**.

## In practice

Priya's setup: `apim-shop-prod` on Standard v2, because the warehouse API is only reachable inside the VNet, behind Front Door. Three products:

- **Partners**: key plus Entra client-credentials token; 10 calls a second and a million a month each.
- **Marketplace**: self-service sign-up in the developer portal with approval; 5 calls a second.
- **Mobile**: External ID token required, no key.

The Node API's OpenAPI file is imported by the pipeline on every release. Breaking changes ship as `/v2` while `/v1` keeps working for six months. APIM logs to Application Insights, so every call is attributed to a subscription. The Word document is retired.

**What it costs.** About $700 a month for Standard v2. That buys consistent auth, limits and documentation across every API, and the weekend outage would not have happened.

**What breaks.**

- **Keys treated as passwords.** They identify; tokens authenticate. Rotate keys, and never ship them in a mobile app.
- **Backends still public.** Callers skip APIM and its limits entirely.
- **Logic in XML.** A 300-line policy doing pricing rules is untestable. Move it back into the API.
- **The gateway as a single point of failure.** Every API now depends on it. Use a tier with an SLA, zone redundancy where offered, and multi-region on Premium if the business needs it.
- **Developer tier in production.** No SLA, one unit, and one bad day.
- **Breaking changes without a version.** Partners find out in production. Version the contract, revise the implementation.

## Map it to what you know

| You already know | On API Management |
|---|---|
| Kong, Apigee or AWS API Gateway | API Management |
| Express middleware for auth, `express-rate-limit` and CORS | Policies, applied the same way to every API |
| Swagger UI served from the API | The developer portal, with sign-up and keys |
| An `api_keys` table and a check in each controller | Products, subscriptions and keys |
| Nginx rewriting `/v1/...` paths to different upstreams | Versions, backends and `rewrite-uri` |

## Guiding your team

> [!TEAM]
> For every API with an outside consumer, ask:
>
> 1. **Which product is this consumer on, and what are its rate limit and quota?**
> 2. **What authenticates them - a token we validate, or only a key?**
> 3. **Can anyone reach the backend without going through APIM?**
> 4. **What is the versioning rule, and how long does an old version live?**
> 5. **Is anything in the policies business logic that belongs in the code?**

## Key takeaways

- An API gateway handles the cross-cutting concerns every API needs - auth, limits, versions, documentation, analytics - once, in front of all of them.
- API Management's building blocks: APIs imported from OpenAPI, backends, products, subscriptions and keys, versions and revisions, and a developer portal.
- Policies are XML pipelines (inbound, backend, outbound, on-error) at global, product, API and operation scope. Use them for cross-cutting rules, not business logic.
- Rate limits and quotas per subscription protect shared backends from any one consumer.
- Subscription keys identify callers; tokens authenticate them. Lock backends so APIM is the only way in.
- Pick a tier with an SLA for production; Standard v2 or Premium when APIM must reach private backends. Front Door sits in front for the WAF.
