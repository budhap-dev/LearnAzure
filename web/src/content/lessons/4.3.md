## Why this matters

> [!SCENARIO] Private, and then nothing worked
> The penetration test's second finding said the orders database must not be reachable from the internet. Dev created a [private endpoint](gl:private-endpoint) for Azure SQL on Friday afternoon and switched off public network access.
>
> The API failed within a minute: it still looked up `sql-shop-prod.database.windows.net`, got the public address, and was refused. Dev fixed that on Monday. Then the finance analysts in the office could not open their reports, because the office DNS server had never heard of the private address. And the warehouse system, still in the office rack, needed a route into Azure at all.
>
> Priya needs the database private, the API and the office able to find it, and a decision on how the office connects.

## Private endpoints: one resource, one private address

A **private endpoint** is a network interface in one of your subnets, with a private IP such as `10.20.2.4`, that leads to **one specific resource**: this database server, this storage account's blob service, this key vault. The technology underneath is **[Private Link](gl:private-link)**, and traffic to the endpoint never leaves Microsoft's network.

Two things surprise people. First, creating the endpoint does **not** close the public one; you must set **public network access** to *Disabled* yourself. Second, an endpoint maps to one resource, not a whole service, so a compromised VM cannot use it to copy data into an attacker's storage account in the same region.

Private endpoints cost about $7 a month each plus a cent per GB each way. The older alternative is a **[service endpoint](gl:service-endpoint)**:

| | Service endpoint | Private endpoint |
|---|---|---|
| What it does | Lets a subnet reach the service over Microsoft's backbone, and the service's firewall trust that subnet | Gives one resource a private IP in your subnet |
| The resource's public address | Still there, still the address used | Can be switched off |
| Reachable from the office over VPN | No | Yes |
| Scope | The whole service, every customer's accounts | One resource |
| Cost | Free | About $7 a month plus data |

==Use private endpoints for anything holding data, then disable public network access; a private endpoint that leaves the public one open has bought a bill, not privacy.==

## DNS is the hard part

Nobody changes connection strings. The API still connects to `sql-shop-prod.database.windows.net`. What changes is the answer DNS gives.

When you create the endpoint, Azure makes that public name a **CNAME** to `sql-shop-prod.privatelink.database.windows.net`. Anyone on the internet following the chain reaches the public address, which now refuses them. Inside your network, a **[private DNS zone](gl:private-dns-zone)** called `privatelink.database.windows.net`, **linked** to the VNet, answers the second name with `10.20.2.4`.

Three rules keep DNS sane:

- **One zone per service type, created once and linked to every VNet** - usually held in the hub, so prod, dev and the hub all resolve the same way.
- **Every service has its own zone name**: `privatelink.blob.core.windows.net` for blobs, `privatelink.vaultcore.azure.net` for Key Vault, and so on. A storage account with blobs and a data lake needs two endpoints and two zones.
- **Never create a zone called `database.windows.net`**. That hijacks every Azure SQL name in the world for your network, including partners' databases.

The office is the last gap. Azure's own resolver, at `168.63.129.16`, answers only from inside Azure. **[Azure DNS Private Resolver](gl:azure-dns-private-resolver)** puts an inbound endpoint with an ordinary private IP in the hub; the office DNS server gets a **conditional forwarder** that sends every `privatelink` name there. It costs roughly $180 a month per endpoint, and it replaces the pair of DNS-forwarder VMs that teams used to build.

## Joining the office to Azure

**[VPN Gateway](gl:vpn-gateway)** connects networks over encrypted IPsec tunnels across the internet. A **site-to-site** VPN joins the office router to the hub; **point-to-site** gives individual laptops a VPN client, with Entra ID sign-in. Gateways live in a subnet called `GatewaySubnet` and start around $140 a month; bandwidth ranges from a few hundred megabits to several gigabits by SKU. It takes a day to set up, and it is only as steady as the office's internet line.

**[ExpressRoute](gl:expressroute)** is a private circuit from your premises or data centre to Microsoft, bought through a connectivity provider. It never touches the internet, gives predictable latency and bandwidth from 50 Mbps to 10 Gbps and beyond, and carries a 99.95% SLA. It also costs from a few hundred to thousands a month, plus the provider's charge, and takes weeks to provision. It is not encrypted by default; add MACsec or run a VPN over it if policy requires.

For most businesses the order is: site-to-site VPN first; a second tunnel or a second gateway for resilience; ExpressRoute when a named requirement arrives - sustained bandwidth, latency-sensitive replication, or a regulator that forbids the internet path - with the VPN kept as its backup.

## In practice

Priya's plan for the shop: private endpoints for Azure SQL, the storage accounts, Redis and Key Vault, each with public network access disabled. The private DNS zones live in the hub, linked to the hub, prod and dev VNets. A DNS Private Resolver in the hub, with the office forwarding `privatelink` names to it. A site-to-site VPN from the office. No ExpressRoute: a hundred megabits of report traffic does not justify it.

The public API stays public, behind Front Door ([lesson 4.2](lesson:4.2)). A private endpoint *on the app itself* is for internal apps nobody on the internet should reach, or for Front Door Premium to reach the origin over Private Link.

**What it costs.** About $7 per endpoint per month, so perhaps $30 for the shop; DNS zones cost pennies; the resolver about $180; the VPN gateway about $140. Roughly $350 a month to take data off the internet.

**What breaks.**

- **DNS still returns the public address.** The zone exists but is not linked to the VNet the caller uses. Test with `nslookup` from inside the network before disabling public access.
- **Public access left on.** The endpoint works, the scanner still finds the database. Disable it, and let Azure Policy ([lesson 4.7](lesson:4.7)) check it stays that way.
- **The pipeline cannot deploy.** GitHub's hosted runners are on the internet, so data-plane steps - running migrations, uploading blobs - fail once public access is off. Use a self-hosted runner in the VNet, or keep those steps to the Azure control plane ([Module 7](module:7)).
- **Duplicate zones.** Each team creates its own `privatelink` zone in its own spoke; names resolve differently depending on where you ask.
- **Overlapping addresses.** The office VPN cannot be built if the office and a VNet share a range ([lesson 4.1](lesson:4.1)).

## Map it to what you know

| You already know | On Azure |
|---|---|
| SQL Server on the office LAN, reachable only inside the building | A private endpoint with public network access disabled |
| A `hosts` file entry pointing a name at an internal IP | A private DNS zone, done properly and for everyone |
| A conditional forwarder in Windows DNS | Exactly the same, pointing at DNS Private Resolver |
| The office-to-data-centre VPN | Site-to-site VPN Gateway |
| The developer VPN client on your laptop | Point-to-site VPN with Entra ID sign-in |
| An MPLS line or leased circuit | ExpressRoute |

## Guiding your team

> [!TEAM]
> Before anyone says "it is private now", ask:
>
> 1. **Is public network access disabled, and what enforces it?** A private endpoint alone closes nothing.
> 2. **Where do the `privatelink` zones live, and is every VNet linked?** One zone per service type, one owner.
> 3. **How does the office resolve these names?** If the answer is a hosts file, it is not an answer.
> 4. **How does the pipeline reach private resources?** Decide before the first failed deploy.
> 5. **VPN or ExpressRoute, and which requirement decided it?** "It feels more enterprise" is not one.

## Key takeaways

- A private endpoint gives one resource a private IP in your subnet over Private Link. It does not close the public endpoint; disabling public network access does.
- Service endpoints are free but leave the public address in use and do not reach the office; prefer private endpoints for data.
- DNS makes or breaks it: one `privatelink` zone per service type, linked to every VNet, and never a zone for the public domain.
- The office needs DNS Private Resolver and a conditional forwarder, plus a network path.
- Site-to-site VPN is the default hybrid link; ExpressRoute is for named bandwidth, latency or policy requirements, with VPN as backup.
- Plan how pipelines reach private resources before public access goes off.
