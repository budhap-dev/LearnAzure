## Why this matters

> [!SCENARIO] "Why not just use the SQL Server we already have?"
> Priya has hired a small team to build the shop's new reviews and recommendations service. They came from a PostgreSQL shop, they want Postgres, and they want the **pgvector** extension so "customers who liked this also liked" can run on embeddings rather than hand-written rules.
>
> Dev, the ops lead, pushes back: the shop already runs [Azure SQL](gl:azure-sql), the backups are sorted, and nobody on his side has ever tuned Postgres. Finance asks whether "open source" means the database is free.
>
> Priya has to answer all three in one review: is a second engine sensible, what does Azure add beyond a VM with Postgres on it, and what does it really cost?

## Flexible Server: what Azure adds to the engine

![PostgreSQL](az:postgresql) **[Azure Database for PostgreSQL](gl:azure-database-for-postgresql)** and ![MySQL](az:mysql) **[Azure Database for MySQL](gl:azure-database-for-mysql)** are the community **[open-source database](gl:open-source-database)** engines run as a [managed service](gl:managed-service). Both come in one shape, **[Flexible Server](gl:flexible-server)**; the older "Single Server" is retired, so ignore any article that mentions it.

You pick a compute tier, a storage size and a major version. Microsoft patches the OS and the engine, takes the backups and hands you a hostname.

| Tier | Built for | Rough monthly compute (USD) |
|---|---|---|
| **[Burstable](gl:burstable-tier)** (B1ms, B2s...) | Dev, test, light spiky use | B1ms around $13 |
| **General Purpose** (2-64 vCores) | Most production workloads | 2 vCores around $130-150 |
| **Memory Optimised** | Large working sets, heavy analytics | Roughly double General Purpose |

Storage is billed separately at roughly ten cents per GB-month and can grow but never shrink; IOPS scale with the storage size and can be raised further if the disk, not the CPU, is the bottleneck. A server can be **stopped** for up to 30 days, paying only for storage, so dev databases should sleep at night. A **[major version upgrade](gl:major-version-upgrade)** (PostgreSQL 15 to 17, say) is done in place from the portal, not by dump and restore.

==Flexible Server is PostgreSQL or MySQL exactly as the community ships it, with the operations you would otherwise do yourself - patching, backups, failover - sold by the hour.==

## Staying up: standby, replicas and backups

Three features look similar and do different jobs.

**Zone-redundant high availability** keeps a synchronous standby in a second [availability zone](gl:availability-zone). If the primary fails, Azure fails over automatically within a minute or two and the connection string does not change. The price is blunt: ==HA doubles the compute bill==, and the standby cannot be read from - it is insurance, not capacity. With HA the [SLA](gl:sla) is 99.99%; without it, 99.9%.

A **[read replica](gl:read-replica)** is a separate, readable server fed asynchronously from the primary. You can have several, and they can live in another region. Point reports and the recommendations batch job at one to keep the checkout fast. Because replication is asynchronous, a replica runs seconds (under load, minutes) behind - never read your own write from it. Promoting a replica is a manual [disaster recovery](gl:disaster-recovery) step, not a failover.

**Automated backups** run daily with continuous log backup, kept for 7 to 35 days, so you can [restore to a point in time](gl:point-in-time-restore) as a new server. Backup storage up to your provisioned size is included; geo-redundant backup is a checkbox worth ticking for production.

## Connections, extensions and identity

**Connection pooling** is the thing Node teams get wrong first. Every PostgreSQL connection is a server process with its own memory, and a 2-vCore server allows only a few hundred. The `pg` library's pool holds, say, 20 per Node process. Six App Service instances hold 120; a spike that autoscales to thirty asks for 600, and the database starts refusing logins. Flexible Server ships **[PgBouncer](gl:connection-pooling)** built in on port 6432: the app keeps its pools, PgBouncer multiplexes them onto a handful of real connections. Turn it on before the first load test.

**[PostgreSQL extensions](gl:postgresql-extension)** are why teams pick Postgres: PostGIS for geography, `pg_cron` for scheduled jobs, `pg_stat_statements` for slow queries, and **[pgvector](gl:pgvector)** for storing embeddings and running similarity search. That last one turns the reviews database into a small [vector database](gl:vector-database) without adding a service - the pattern [Module 8](module:8) builds on. Extensions are allow-listed per server; MySQL has no equivalent.

**Identity**: both engines accept [Microsoft Entra ID](gl:microsoft-entra-id) logins, so the API connects with a [managed identity](gl:managed-identity) and there is no database password to leak. Keep a local admin for break-glass, in [Key Vault](gl:key-vault).

## In practice

In `rg-shop-prod`: one Flexible Server (`pg-shop-reviews-prod`, General Purpose, 2 vCores, 128 GB, zone-redundant HA, geo-redundant backup, PgBouncer and Entra authentication on), a read replica if reporting needs it, and a private endpoint so it is off the internet ([Module 4](module:4)). A Burstable server for dev, stopped outside working hours.

Cost shape: dev around $13 plus storage; production compute around $140, doubled to roughly $280 by HA, plus about $13 of storage, plus any replica's own compute. No licence line, ever - and that is the honest answer for finance: ==open source removes the licence, not the bill.==

What breaks:

- **Case sensitivity.** SQL Server's default collation is case-insensitive; PostgreSQL's is not. `WHERE email = 'Ana@Shop.com'` silently returns nothing, unquoted identifiers fold to lower case, and `LIKE` becomes `ILIKE`. MySQL on Linux is the reverse: comparisons are case-insensitive, table names are not.
- **Burstable credits.** B-series servers bank CPU credits while idle and spend them under load; a sustained import empties the bank and the server crawls.
- **Replica lag**, surfacing as "the report is missing today's orders".
- **Expecting the standby to add read capacity.** Only replicas do.
- **Storage never shrinks**, so a runaway log table costs you for good.

Against Azure SQL, honestly:

| | [Azure SQL Database](gl:azure-sql-database) | PostgreSQL / MySQL Flexible Server |
|---|---|---|
| Licence | In the price, or reduced by [Azure Hybrid Benefit](gl:azure-hybrid-benefit) | None |
| Dialect | T-SQL and the stored procedures you own | Standard SQL; Postgres adds a richer type system and extensions |
| Tooling | SSMS, Azure Data Studio | psql, pgAdmin, DBeaver; VS Code extensions for both |
| Node ORMs | Prisma, Sequelize, Knex, TypeORM | The same list; Prisma's Postgres support is its strongest |
| HA | Built into zone-redundant tiers | Doubles compute |
| Skills | Your team's, today | The new team's; Dev's ops team must learn |

Moving an existing database either way goes through ![Database Migration Service](az:database-migration) **[Azure Database Migration Service](gl:azure-database-migration-service)**, which bulk-copies and can keep source and target in sync until cutover. Between engines it moves data, not stored procedures - those are a rewrite.

## Map it to what you know

| You already know | On Flexible Server |
|---|---|
| A SQL Server instance you patch and back up | A Flexible Server: the same engine, patching and backups done for you |
| An Always On availability group with a synchronous secondary | Zone-redundant HA - but the standby is not readable |
| A log-shipped reporting server | A read replica, asynchronous, possibly in another region |
| `Max Pool Size` in a .NET connection string | The `pg` pool, multiplied by instances, tamed by PgBouncer |
| Collation `..._CI_AS` | Case-sensitive by default; decide in the schema |
| CLR or SQL Agent | Extensions such as pg_cron, PostGIS, pgvector |

## Guiding your team

> [!TEAM]
> Before a second database engine lands in production, ask:
>
> 1. **Why this engine rather than the one we run?** "The team knows it" and "we need pgvector" are good answers; "it is free" is not.
> 2. **Who operates it at 3am?** A second engine means a second set of runbooks, dashboards and restore tests.
> 3. **Is HA on, and is the doubled compute in the budget?** Decide with finance, not after the first outage.
> 4. **Pool size times maximum instance count - what is the number?** If it scares you, turn PgBouncer on.
> 5. **Have we rehearsed a point-in-time restore and a replica promotion?** [Lesson 3.6](lesson:3.6) explains why an untested backup is not a backup.

## Key takeaways

- Azure Database for PostgreSQL and MySQL run the community engines as PaaS; Flexible Server is the only current shape.
- Burstable for dev and light spiky use; General Purpose for production; Memory Optimised for big working sets. Storage bills separately and never shrinks.
- Zone-redundant HA gives automatic failover and 99.99%, doubles compute, and the standby is unreadable. Read replicas are asynchronous, readable and can cross regions.
- Node pools multiplied by App Service instances exhaust connections; the built-in PgBouncer fixes it.
- Extensions, especially pgvector, are the reason to choose Postgres; case-sensitive collation is the surprise coming from SQL Server.
- Open source removes the licence, not the bill, and adds a second engine the ops team must learn.
