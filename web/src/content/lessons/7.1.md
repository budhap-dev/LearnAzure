## Why this matters

> [!SCENARIO] Friday, 17:40, from a laptop
> The shop has shipped a lot in six modules, and almost none of it the same way twice. The Node API is published by right-clicking in VS Code. The React build is zipped and uploaded by hand. Infrastructure was created in the portal. The API's code lives in Azure DevOps, a leftover from the .NET years; the React Native app lives in GitHub, where Ana's team prefers to work.
>
> Last Friday at 17:40, Dev deployed a fix from his laptop with an uncommitted change in it. Checkout was down for two hours, and nobody could say what had been deployed, because nothing recorded it.
>
> The new CTO asks two questions: how often do we deploy, and how do we know what is running? Nobody can answer either. And the team is arguing about whether to standardise on Azure DevOps or GitHub.

## What DevOps actually is

**[DevOps](gl:devops)** is not a team or a tool. It is a way of working in which the people who build software also run it, and changes flow to production in small, frequent, automated steps, with feedback from production shaping what comes next. Four practices carry most of the weight:

- **[Continuous integration](gl:continuous-integration)** (CI): every change is merged often and automatically built, tested and scanned, so problems show up in minutes, not at release time.
- **[Continuous delivery](gl:continuous-delivery)** (CD): every change that passes the pipeline produces a versioned artefact that *can* be deployed to production at the push of a button. *Continuous deployment* goes one step further and deploys it automatically.
- **[Infrastructure as code](gl:infrastructure-as-code)**: environments are defined in files and created by the pipeline, not clicked together in the portal ([lesson 7.5](lesson:7.5)).
- **Feedback**: monitoring, SLOs and incidents ([Module 6](module:6)) feed the backlog, so the next change is informed by the last one.

==The rule that makes all of it work: the pipeline is the only way to production. No laptops, no portal edits, no FTP.== Everything else follows from it: repeatable deployments, a record of what ran and when, and a way back.

## The two toolchains

Microsoft offers two complete DevOps platforms, and both deploy to Azure equally well.

**[Azure DevOps](gl:azure-devops)** is the successor to Team Foundation Server. It is a suite of five services, usable separately:

- **[Azure Boards](gl:azure-boards)**: work items, backlogs, sprints and delivery plans.
- **Azure Repos**: Git repositories.
- **Azure Pipelines**: CI/CD in YAML ([lesson 7.3](lesson:7.3)).
- **Azure Test Plans**: manual and exploratory testing.
- **[Azure Artifacts](gl:azure-artifacts)**: private package feeds for npm, NuGet, Maven and Python.

**GitHub** is where most of the world's code lives. It offers repositories, pull requests, **GitHub Actions** for CI/CD ([lesson 7.4](lesson:7.4)), Issues and Projects for planning, Packages, Codespaces, Copilot, and Advanced Security for code and secret scanning ([lesson 7.6](lesson:7.6)). Microsoft owns both, and most of its new developer investment - particularly AI-assisted development and security scanning - lands in GitHub first.

| | Azure DevOps | GitHub |
|---|---|---|
| Strongest at | Enterprise work tracking, test management, fine-grained permissions, on-premises Server option | Developer experience, open-source ecosystem, Actions marketplace, security scanning, Copilot |
| CI/CD | Azure Pipelines: mature, strong environments and approvals | GitHub Actions: huge marketplace, native to Static Web Apps and many Azure services |
| Pricing shape | First 5 users free, then per user; pipelines priced per parallel job | Free, Team and Enterprise per user; Actions minutes included, then per minute |
| Good fit | Established .NET estates, regulated organisations with heavy process | New teams, JavaScript and open source, anyone already on GitHub |

They also mix. Azure Boards links to GitHub repositories and pull requests, and Azure Pipelines can build code that lives on GitHub. A mixed estate is fine when each tool has a clear job. It is not fine when every team has a second copy of everything.

## Choosing, for real

A simple rule helps the argument: **start new work where the code already is, and migrate only when running both costs more than moving**. Moving repositories is easy. Moving years of work items, test plans and pipeline history is not. Nobody should migrate just to be modern.

## In practice

Priya's decisions for the shop:

- **GitHub** for all application code, moving the API's repository across. The React Native app is already there, Static Web Apps deploys from Actions, and the team prefers it.
- **GitHub Actions** for the web app, the API and the infrastructure, deploying with workload identity federation, so there are no secrets in GitHub ([lesson 4.5](lesson:4.5)).
- **Azure Pipelines kept** for the warehouse integration, which deploys to the on-premises server through a self-hosted agent. It works, and moving it buys nothing yet.
- **Azure Boards kept** for the business-facing backlog, linked to GitHub pull requests.
- **One rule, enforced**: production changes only through a pipeline. Engineers hold Reader on production and activate Contributor through PIM for emergencies only ([lesson 4.5](lesson:4.5)).

**What it costs.** For a team of ten: GitHub Team at about $4 per user per month plus included Actions minutes; Azure Boards free for the first five users and a few dollars each after. Tooling is the cheapest part of DevOps. The Friday outage cost more.

**What breaks.**

- **A "DevOps team" as a new silo** that owns the pipelines nobody else understands. DevOps is how every team works.
- **Tools without practice.** A pipeline that deploys once a month in a big batch is a slower laptop.
- **The pipeline as a second way in.** If portal edits continue, environments drift from code and the next deployment undoes the fix.
- **Two of everything.** Two repositories, two pipelines, two backlogs for one product.
- **No feedback.** Shipping faster without watching production just breaks things faster.

## Map it to what you know

| You already know | On Azure |
|---|---|
| Team Foundation Server (TFS) and VSTS | Azure DevOps - the same product line, renamed |
| Right-click *Publish* in Visual Studio | A pipeline job, triggered by a merge |
| Jenkins, TeamCity or Octopus Deploy | Azure Pipelines or GitHub Actions |
| Jira | Azure Boards, or GitHub Issues and Projects |
| A private npm registry or a NuGet server | Azure Artifacts, or GitHub Packages |
| A deployment runbook in a Word document | A YAML pipeline in the repository |

## Guiding your team

> [!TEAM]
> Before arguing about tools, ask:
>
> 1. **Is the pipeline the only way to production?** If not, fix that before anything else.
> 2. **How often do we deploy, and how do we know exactly what is running?**
> 3. **Where does each kind of work live - code, work items, pipelines, packages - and is there one home for each?**
> 4. **What would moving cost, and what does running both cost?** Migrate only when the second is larger.
> 5. **How does production feedback reach the backlog?**

## Key takeaways

- DevOps is a way of working - small, frequent, automated changes owned by the people who run them - not a team or a product.
- Continuous integration builds and tests every change; continuous delivery keeps every passing change deployable; continuous deployment ships it automatically.
- The pipeline is the only way to production. No laptops, portal edits or FTP.
- Azure DevOps (Boards, Repos, Pipelines, Test Plans, Artifacts) and GitHub (repositories, Actions, Advanced Security, Copilot) both deploy to Azure; they can be mixed with a clear job for each.
- Start where the code already is, and migrate only when running two toolchains costs more than moving.
