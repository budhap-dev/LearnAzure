## Why this matters

> [!SCENARIO] Fourteen months to leave the data centre
> The lease on Northline's data centre ends in fourteen months. Inside it are 140 virtual machines, 22 SQL Server instances, the old order-management system (a .NET Framework monolith), a nightly file-based integration with the ERP, 18 internal web apps, and the warehouse systems, which must keep working when the internet link drops.
>
> The CFO wants the exit on time and a lower bill afterwards. Dev wants to rewrite everything as cloud-native first. The infrastructure manager wants to copy every VM exactly as it is. Priya has to turn three opinions into one plan with a date on it.

## A strategy per workload

There is no single migration strategy, only a decision per workload. The Cloud Adoption Framework lists the options, and each **[migration strategy](gl:migration-strategy)** trades speed against benefit:

| Strategy | What it means | Speed | Northline example |
|---|---|---|---|
| **Retire** | Switch it off | Fastest | 30 VMs that nobody has logged into for a year |
| **Retain** | Keep it where it is, for now | - | Warehouse systems that must run on site |
| **Rehost** ([lift and shift](gl:lift-and-shift)) | Move the VM as it is | Fast | 80 application and utility VMs |
| **Replatform** | Move to a managed service with small changes | Medium | Web apps to App Service; SQL Server to Managed Instance |
| **Refactor / rearchitect** | Change the code or structure to use the cloud properly | Slow | The order system, piece by piece, after the move |
| **Replace** | Buy SaaS instead | Varies | The ERP file integration becomes a Logic Apps workflow |

==When there is a deadline, migrate first and modernise second. Replatform where it is cheap and removes real operational work; refactor only where the benefit is proven.== Rewriting everything first is how data-centre exits miss their date by years.

## Azure Migrate

**[Azure Migrate](gl:azure-migrate)** is the free hub for the whole process:

1. **Discover**: a lightweight appliance on site inventories servers, databases and web apps, and collects performance data for weeks.
2. **Assess**: readiness per target (Azure VMs, Azure SQL, App Service, AKS), right-sized recommendations from real utilisation, monthly cost estimates, and a business case comparing staying with moving.
3. **Map dependencies**: **[dependency analysis](gl:dependency-analysis)** shows which servers talk to which, on what ports. This is how you find the hard-coded IP address and the forgotten nightly FTP job before cutover, not during it.
4. **Migrate**: servers are replicated to Azure and cut over. Databases move with the [Database Migration Service](gl:azure-database-migration-service) or the Managed Instance link. Web apps move with the App Service migration tooling.

## Waves and cutover

Workloads move in **[migration waves](gl:migration-wave)**: groups that depend on each other move together, so nothing is split across the WAN in the middle of the plan. The first wave is a low-risk pilot that proves the process. Each workload then follows the same routine:

- **Replicate** it continuously to Azure.
- **Test-migrate** into an isolated network and let the app's owner check it.
- **Cut over** in an agreed window, with the go/no-go criteria and the rollback plan written down in advance.
- **Hypercare**: watch closely for a couple of weeks.
- **Decommission** the old server. Until then you pay twice.

A landing zone ([lesson 9.2](lesson:9.2)) comes before the first wave, not after.

## Modernising after the move

The order system moves first as it is, then modernises with the **[strangler fig pattern](gl:strangler-fig-pattern)**. A façade, API Management in front of the old app, routes each capability to either old or new code. Returns are rebuilt first as a new service on Container Apps, and the route switches. The old system shrinks one capability at a time until it can be switched off, with a rollback that is just a routing change.

## What stays behind

Not everything moves. **[Azure Arc](gl:azure-arc)** brings servers, Kubernetes clusters and SQL Server instances outside Azure, on site or in other clouds, under the same management: Azure Policy, Defender for Cloud, Azure Monitor, update management and RBAC. The warehouse servers stay on site for latency and resilience, but they are governed like everything else.

## In practice

- **Discovery ran for six weeks** before any decisions. It found the 30 retirement candidates and showed that most VMs used under 30% of their CPU. Right-sized, the rehosted estate needs about 40% less compute than the on-site specifications.
- **Licensing**: [Azure Hybrid Benefit](gl:azure-hybrid-benefit) applies the existing Windows Server and SQL Server licences. End-of-support Windows Server and SQL Server versions get extended security updates at no extra charge on Azure. Reservations are bought after three months of real usage, not from the estimates.
- **SQL**: 22 instances consolidate into three Managed Instances, because SQL Agent jobs and cross-database queries rule out SQL Database for now ([lesson 3.2](lesson:3.2)).
- **Web apps** follow the [Reliable Web App pattern](gl:reliable-web-app-pattern): App Service, managed identity, and retries added where it is cheap.
- **Six waves over ten months**, leaving four months of buffer before the lease ends.

**What breaks.**

- **Lift and shift, then never optimise**, so oversized VMs cost more than the data centre did.
- **Missing dependencies**: hard-coded IP addresses, a nightly FTP job, a licence server nobody knew about.
- **Big-bang cutover** of everything on one weekend.
- **Rewriting before the deadline.**
- **Never decommissioning**, and paying for two estates.
- **No landing zone first**, so every wave invents its own network.

## Map it to what you know

| You already know | In an Azure migration |
|---|---|
| Physical-to-virtual (P2V) or a vMotion migration | Azure Migrate server replication and cutover |
| SQL Server log shipping to a standby | Database Migration Service online migration or the Managed Instance link |
| IIS URL Rewrite routing some paths to a new app | The strangler fig façade |
| System Center managing servers across sites | Azure Arc |
| A release plan in waves | Migration waves grouped by dependency |

## Guiding your team

> [!TEAM]
> For a migration plan:
>
> 1. **What strategy has each workload got, and why?** Who agreed it with the app's owner?
> 2. **How long did discovery run, and what did dependency analysis find?**
> 3. **What is in each wave, and what is the rollback for each cutover?**
> 4. **When is each old server switched off?**
> 5. **What gets optimised in the three months after the move?** Sizing, reservations, licences.

## Key takeaways

- Choose a strategy per workload: retire, retain, rehost, replatform, refactor or replace. With a deadline, migrate first and modernise second.
- Azure Migrate discovers, assesses (right-sizing, cost, business case), maps dependencies and migrates. Run discovery for weeks before deciding.
- Move in dependency-grouped waves, starting with a pilot. Test-migrate, cut over with a rollback plan, then decommission.
- Modernise after the move with the strangler fig pattern, one capability at a time behind a façade.
- Azure Arc governs what stays on site. Hybrid Benefit, free extended security updates and post-migration right-sizing make the numbers work.
