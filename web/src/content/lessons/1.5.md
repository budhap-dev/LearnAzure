## Why this matters

> [!SCENARIO] Two ways in, one drifting estate
> Priya's retailer from [lesson 1.1](lesson:1.1) is on Azure now. Sam built the test environment by clicking through the [Azure portal](gl:azure-portal), tweaking settings as he went. Lee scripted production with the [Azure CLI](gl:azure-cli) from his laptop. Six weeks in, test has a setting prod does not, prod has a firewall rule nobody remembers adding, and a bug that passes in test fails in prod.
>
> Then the security review asks about a virtual machine nobody recognises: "Who created this, from where, with what permissions?"

Both problems share a root: nobody decided *how* the team talks to Azure. This lesson is about the one thing every tool has in common, and how to choose between them.

## One front door: Azure Resource Manager

Every request to create, change, read or delete a resource - from the portal, a script, a template, an SDK or a raw HTTP call - goes through **[Azure Resource Manager](gl:azure-resource-manager)** (ARM). There is no back door, and that is what makes the estate governable.

ARM does the same four things to every request, in order:

1. **Authenticate.** Who is calling? A token from [Microsoft Entra ID](gl:microsoft-entra-id) - a person, a pipeline or an app identity.
2. **Authorise.** May they do this at this [scope](gl:scope)? That is [RBAC](gl:role-based-access-control) from [lesson 1.4](lesson:1.4).
3. **Check policy.** May the result exist? [Azure Policy](gl:azure-policy) can deny a region, demand a tag, or quietly add one.
4. **Hand off.** The [resource provider](gl:resource-provider) that owns the type - `Microsoft.Web`, `Microsoft.Sql`, `Microsoft.Storage` - does the work.

==Because everything goes through ARM, the same identity, permissions, policies and audit trail apply whether someone clicked, scripted or deployed a template.==

That answers the security reviewer. The **[Activity log](gl:activity-log)** records every ARM operation: who, what, when, from which IP address, and whether it succeeded. Sam's clicks and Lee's scripts sit side by side in it, for ninety days by default.

## The tools, and when to use each

The tools differ in ergonomics, not power. Every one of them calls the same ARM REST API.

| Tool | Best for | Watch out for |
|---|---|---|
| ![Portal](az:portal) [Azure portal](gl:azure-portal) | Exploring, one-off checks, reading logs, learning a service | Clicks are not repeatable or reviewable; test drifts from prod |
| ![Cloud Shell](az:cloud-shell) [Azure CLI](gl:azure-cli) | Scripting from Bash and CI, quick queries | Imperative: a script that half-runs leaves a half-built estate |
| ![PowerShell](az:powershell) [Azure PowerShell](gl:azure-powershell) | The same, for teams who want objects rather than JSON | Using both doubles the scripts to maintain |
| ![Templates](az:templates) [Bicep](gl:bicep), [ARM templates](gl:arm-template), [Terraform](gl:terraform) | Repeatable environments from one file in source control | A learning curve; needs a pipeline to pay off |
| ![Code](az:code) SDKs (JavaScript, .NET, Python) | Your app managing resources at run time - a database per customer, say | Infrastructure decisions buried in app code |
| REST API | The layer under everything above | Tokens, retries and paging are your problem |

The CLI is where most engineers start, because it reads like what it does:

```bash
az group create --name rg-shop-test --location uksouth
az appservice plan create --name plan-shop-test --resource-group rg-shop-test --sku B1
az webapp create --name app-shop-api-test --plan plan-shop-test --resource-group rg-shop-test
```

Nothing to install: **[Cloud Shell](gl:cloud-shell)** is a browser terminal inside the portal with the CLI, PowerShell, Git and a small persistent file share, already signed in as you. It is the fastest way to run one command from a phone during an incident.

## Imperative, declarative and idempotent

Lee's scripts are **imperative**: a list of steps. Run one twice and it fails with "already exists", or creates a duplicate. Stop it half-way and you must work out where it got to.

A [Bicep](gl:bicep) file is **declarative**: it describes what should exist, and ARM works out what to create, change or leave alone. Deploying it ten times gives the same result - it is **[idempotent](gl:idempotent)**. That lets one file define test *and* prod with only a parameter changing, which ends the drift in the scenario.

This is **[infrastructure as code](gl:infrastructure-as-code)**, the destination for any team with more than one environment. Module 7 goes deep; the shape of the choice:

| | [ARM template](gl:arm-template) | [Bicep](gl:bicep) | [Terraform](gl:terraform) |
|---|---|---|---|
| Format | Verbose JSON | Concise; compiles to ARM JSON | HCL |
| Reach | Azure only | Azure only | Multi-cloud, plus SaaS like GitHub |
| State | ARM is the record | Same | A state file you must protect |
| Pick when | Rarely by hand now | Azure-only teams; new services on day one | Estates spanning clouds |

==Anything that will exist for more than a week, or in more than one environment, should come from a file in source control, not from a click.==

## Control plane versus data plane

ARM is the **[control plane](gl:control-plane)**: it manages resources. Reading and writing what is *inside* a resource is the **[data plane](gl:data-plane)**, which goes straight to the service's own endpoint and never touches ARM.

| | Control plane (ARM) | Data plane (the service) |
|---|---|---|
| Storage account | Create it, set redundancy, delete it | Upload a blob, list a container |
| Azure SQL | Create the server, set the firewall, change tier | Run a `SELECT`, insert an order |
| Audited in | Activity log | The resource's own diagnostic logs |

The split matters for security. Contributor on a storage account lets you *manage* it, but not *read* the blobs; that needs a data-plane role such as Storage Blob Data Reader, or a key. Equally, an app that only reads secrets needs data-plane rights on the vault and no control-plane rights at all. Grant each plane separately and the blast radius of any one identity halves.

## In practice: providers and registration

Every resource type belongs to a resource provider, and its name sits in the [resource ID](gl:resource-id): `providers/Microsoft.Web/sites/...`. A subscription only knows a provider once it is **registered**. Common ones register on first use, but a template failing with "namespace not registered" is fixed by `az provider register --namespace Microsoft.Sql`. RBAC and Policy can target a provider's types too - which is how "nobody creates VMs here" is expressed.

## Map it to what you know

| You already know | The Azure equivalent |
|---|---|
| An API gateway in front of Express: auth, authz, validation middleware, then the handler | ARM: Entra ID, RBAC, Policy, then the resource provider |
| React: describe the UI, let the renderer reconcile the DOM | Bicep: describe the resources, let ARM reconcile the estate |
| `PUT /orders/42` (safe to retry) versus `POST /orders` (makes another) | Idempotent template deployment versus a script that runs `create` |
| Managing the SQL Server instance versus running queries in a database | Control plane versus data plane |
| `git log` | The Activity log |

## Guiding your team

> [!TEAM]
> When someone shows you a new environment, ask:
>
> 1. **Could you delete it and recreate it from a file?** If not, it will drift.
> 2. **Which tool for which job?** Portal to look, CLI to poke, code to build. Write it down.
> 3. **Who has control-plane rights, and who has data-plane rights?** Different lists.
> 4. **Is the pipeline the only thing that changes prod?** Humans get Reader; the pipeline identity gets Contributor.
> 5. **Can everyone find the Activity log?** It is the first place to look when something changes unexpectedly.

## Key takeaways

- Every management request, from any tool, goes through Azure Resource Manager: authenticate, authorise, check policy, hand to a resource provider.
- Portal to look, CLI and PowerShell to script, Bicep or Terraform for anything repeatable, SDKs for apps. All call the same REST API.
- Declarative, idempotent files in source control end environment drift. That is infrastructure as code, and it is the destination.
- The control plane manages resources; the data plane reads and writes their contents. Grant them separately.
- The Activity log is the audit trail of the control plane: who did what, when, from where.
