## Why this matters

> [!SCENARIO] The dev site took a real payment
> Managed identities removed most of the shop's passwords in [lesson 4.5](lesson:4.5), but not all of them. The payment provider, the email service and the warehouse partner's SFTP server still want an API key or a password. Those sit as plain-text App Service settings, readable by anyone with Contributor, and one of them was committed in a `.env` file in 2023.
>
> Last week the dev environment charged a real card. Dev and prod had drifted: someone copied prod's settings into dev "temporarily", including the live payment key. Meanwhile Ana wants to switch the new checkout on for 10% of shoppers without a deploy, and nobody can say which of the three copies of the settings is the truth.
>
> Priya needs one home for secrets, one home for configuration, and no more copies.

## What goes where

Most "secrets" in a modern Azure app are not secrets any more: a managed identity replaces the database password and the storage key. What is left falls into four kinds:

| Kind | Example | Home |
|---|---|---|
| A credential for someone else's service | The payment provider's API key | Key Vault **[secret](gl:key-vault-secret)** |
| An encryption or signing key | The [customer-managed key](gl:customer-managed-key) from [lesson 3.6](lesson:3.6) | Key Vault **key** |
| A TLS certificate | The partner API's client certificate | Key Vault **certificate**, renewed automatically |
| Ordinary configuration | Timeouts, URLs, feature switches | **[Azure App Configuration](gl:azure-app-configuration)** |

==Secrets go in Key Vault, configuration goes in App Configuration, and anything a managed identity can replace should not exist at all.== And one rule for the React developer: nothing secret goes in the front-end bundle. Every `VITE_` variable ships to every browser.

## Key Vault, done properly

[Key Vault](gl:key-vault) stores secrets, keys and certificates, controls who may read each one, and logs every read. Four habits make it work:

1. **One vault per application per environment** - `kv-shop-prod` and `kv-shop-dev`, in their own resource groups. A shared vault means a dev app can read prod secrets, which is exactly how the dev site took a real payment.
2. **Azure RBAC permission model**, not the older access policies. The API's identity gets **Key Vault Secrets User** on its vault; the pipeline and admins get **Key Vault Secrets Officer**; nobody gets both by default.
3. **Private endpoint and public access off** ([lesson 4.3](lesson:4.3)).
4. **Read at start-up, not on every request.** A vault serves a few thousand operations every ten seconds before it throttles, so a busy API that asks per request will meet `429` long before the shop is busy.

The easiest way to do step 4 is not to call Key Vault at all. A **[Key Vault reference](gl:key-vault-reference)** is an App Service, Functions or Container Apps setting whose value is a pointer:

```
PAYMENT_API_KEY = @Microsoft.KeyVault(SecretUri=https://kv-shop-prod.vault.azure.net/secrets/payment-api-key/)
```

The platform resolves it with the app's managed identity and hands the code an ordinary environment variable. The secret never appears in the portal, the pipeline or a config file. A reference without a version follows the latest value, picked up within a day or on the next restart.

## Deleting, purging and rotating

Two protections stop a bad day becoming a disaster. **[Soft delete](gl:soft-delete)** is always on: a deleted vault or secret is kept for 7 to 90 days (90 by default) and can be recovered, and the vault's name stays reserved meanwhile - so "delete and recreate `kv-shop-dev`" fails until the old one is purged. **[Purge protection](gl:purge-protection)** goes further: nobody, including an Owner or an attacker with an Owner's token, can purge before the retention period ends. It cannot be turned off once on, and it is mandatory before you use a customer-managed key, because a purged key makes every backup encrypted with it unreadable.

**[Secret rotation](gl:secret-rotation)** is what makes a leaked secret a short incident instead of a long one. Give every secret an expiry date. Key Vault publishes a *near expiry* event through Event Grid; a small function asks the provider for a new key and stores it as a new version, and the versionless reference picks it up. Where a provider allows two active keys, rotate them alternately so there is never a moment with no valid key. Certificates from the integrated authorities renew themselves.

And if a secret was ever committed to Git, deleting the file is not enough. It lives in the history; rotate it.

## App Configuration and feature flags

Settings that are not secret still deserve one home. **Azure App Configuration** is a central key-value store shared by every service. **Labels** separate environments (`prod`, `dev`), snapshots record exactly what was live at a release, and values can themselves be Key Vault references, which each app resolves with its own identity.

Its other half is the **[feature flag](gl:feature-flag)**: a named switch the code checks at run time, with filters for a percentage of users, named groups or a time window. Ana's new checkout ships switched off, turns on for 10% of shoppers from the portal, and turns off again in seconds if orders drop - no deploy, no rollback. Module 7 builds release strategies on this.

App Configuration's free tier covers dev; Standard is roughly $36 a month per store plus a small charge for very high request volumes.

## In practice

Priya's layout: `kv-shop-prod` and `kv-shop-dev` in separate resource groups, RBAC model, private endpoints, purge protection on. Three secrets in prod, each with an expiry date and rotation. Every App Service secret setting becomes a Key Vault reference; the plain-text values and the `.env` in history are rotated. One App Configuration store with `prod` and `dev` labels, and a `NewCheckout` flag at 10%.

**What it costs.** Key Vault Standard charges a few cents per 10,000 operations, so a vault read at start-up costs pennies a month; HSM-protected keys on Premium are about $1 per key per month. App Configuration Standard is about $36 a month. A leaked payment key costs more.

**What breaks.**

- **Secrets in the React bundle.** Anything in a `VITE_` variable is public. Move the call behind the API.
- **Throttling.** Per-request vault reads return 429 under load. Use references or cache at start-up.
- **A stale value after rotation.** The reference refreshes within a day or on restart; restart deliberately after rotating.
- **The name you cannot reuse.** A soft-deleted or purge-protected vault holds its name for up to 90 days. Plan names; do not delete and recreate.
- **One vault for everything.** Dev reads prod, and one mistake deletes every environment's secrets.

## Map it to what you know

| You already know | On Azure |
|---|---|
| Connection strings in `web.config` or `appsettings.json` | App Configuration for settings; Key Vault references for secrets; managed identity for most connection strings |
| A `.env` file | Fine for your laptop; never for a deployed environment |
| ASP.NET Core user secrets | Local development only - the cloud equivalent is Key Vault |
| HashiCorp Vault | Key Vault |
| LaunchDarkly or a `features` table | App Configuration feature flags |
| The Windows certificate store | Key Vault certificates, renewed for you |

## Guiding your team

> [!TEAM]
> Before any secret reaches an environment, ask:
>
> 1. **Could a managed identity replace this secret?** If yes, it should not exist.
> 2. **Which vault, and can any other environment read it?** One vault per app per environment.
> 3. **When does it expire, and what rotates it?** "Never" and "someone" are the wrong answers.
> 4. **Is there any secret in the front end, the repo or its history?** If there ever was, rotate it.
> 5. **Which settings are really feature flags?** Anything you might want to switch without a deploy.

## Key takeaways

- Replace secrets with managed identities first; Key Vault holds what is left - third-party credentials, keys and certificates.
- One vault per app per environment, RBAC permissions, private endpoint, and reads at start-up rather than per request.
- Key Vault references keep secrets out of settings and pipelines; the platform resolves them with the app's identity.
- Soft delete is always on and reserves the name; purge protection makes deletion irreversible only after retention, and is mandatory for customer-managed keys.
- Every secret gets an expiry and a rotation path; a secret that was ever in Git is rotated, not just deleted.
- App Configuration is the single home for non-secret settings, with labels per environment and feature flags for switching behaviour without a deploy.
