## Why this matters

> [!SCENARIO] Fourteen boxes for five developers
> Northline is starting two new products: a loyalty programme (points, rewards, a members' area in the app) and a wholesale portal for business customers. Priya now leads the engineering managers of both teams.
>
> The loyalty team's first whiteboard has fourteen microservices on AKS, a service mesh and an event store, for five developers and a launch in four months. The wholesale team has copied a design from a blog post written in 2019. Both designs will take weeks to review, and both reviews will start from zero.
>
> Priya's instruction is short: start from a reference architecture, then argue with it.

## The Azure Architecture Center

The **[Azure Architecture Center](gl:azure-architecture-center)** is Microsoft's free library of architecture guidance, and the best starting point for any design. It holds:

- **[Reference architectures](gl:reference-architecture)**: proven designs for common workloads. Each has a diagram, the reasoning behind every component, the trade-offs for each Well-Architected pillar ([lesson 1.7](lesson:1.7)) and, often, deployable code. The **baseline** versions are production-grade: zone-redundant, private networking, and monitoring included.
- **Architecture styles**: N-tier, web-queue-worker, microservices, event-driven and big data, with when each fits.
- **Technology choice guides**: decision trees for compute, data stores, messaging and more. Modules 2, 3 and 5 followed the same logic.
- **[Cloud design patterns](gl:cloud-design-pattern)**: named solutions to recurring problems, such as retry, cache-aside and strangler fig.

==A reference architecture turns a design review from "is this right?" into "why are we different?"== Every deviation is a decision worth writing down as an [architecture decision record](gl:architecture-decision-record).

## The ones you will meet most

| Reference architecture | Shape | Reach for it when | Covered in |
|---|---|---|---|
| **Web app baseline** | Front Door or Application Gateway with WAF, zone-redundant App Service, Azure SQL and Redis, private endpoints | Almost any business web app or API | [Modules 1-4](module:1) |
| **[Reliable Web App pattern](gl:reliable-web-app-pattern)** | The same baseline plus retries, circuit breakers, caching and managed identity, applied to an existing .NET or Java app | Moving an on-premises web app to the cloud without a rewrite | [9.3](lesson:9.3) |
| **Web-queue-worker / event-driven** | A web front end hands slow work to a queue; Functions or Container Apps process it | Spiky or slow background work: emails, points, imports | [Module 5](module:5) |
| **Microservices on Container Apps or AKS** | Independently deployed services, each with its own data, behind a gateway | Several teams that must ship independently | [Module 2](module:2) |
| **Hub-and-spoke in a landing zone** | Shared network, firewall and identity in a hub; each workload in its own spoke | Any organisation with more than a couple of workloads | [4.1](lesson:4.1), [9.2](lesson:9.2) |
| **Multi-region active-passive** | A second region with replicated data and a tested failover | A regulatory or business RTO that one region cannot meet | [6.5](lesson:6.5) |
| **Baseline chat or RAG app** | App, Foundry, AI Search and an AI gateway, all private | Any generative AI feature | [Module 8](module:8) |

## Microservices are an organisational choice

**[Microservices](gl:microservices)** split a system into small services, each owned by one team, deployed independently and holding its own data. They solve an *organisational* problem: many teams that would otherwise queue behind one release. In exchange they bring *technical* ones: network calls where there were function calls, data consistency across services, versioned contracts, distributed tracing, and a platform to run it all.

==Choose the architecture for the team you have, not the one on the conference slide.== For one team, the better default is a **[modular monolith](gl:modular-monolith)**: one deployable app with strict internal module boundaries (points, rewards, members), each with its own schema. It is simple to run today, and a module can be extracted into a service later if a second team needs to own it.

## Patterns you already know

Most of this course has been cloud design patterns without the label:

| Pattern | Problem it solves | Lesson |
|---|---|---|
| Cache-aside | Slow or expensive reads | [3.4](lesson:3.4) |
| Valet key | Clients uploading large files without going through your API | [3.1](lesson:3.1) |
| Competing consumers, queue-based load levelling | Work arriving faster than it can be done | [5.1](lesson:5.1) |
| Transactional outbox | Saving data and publishing an event reliably | [5.2](lesson:5.2) |
| Gateway routing and offloading | Many clients, many back ends, shared concerns | [5.5](lesson:5.5) |
| Retry, circuit breaker, bulkhead | Transient faults and failing dependencies | [6.5](lesson:6.5) |
| Strangler fig | Replacing an old system piece by piece | [9.3](lesson:9.3) |

Naming them matters in a review. "Where's the outbox?" is a faster question than describing the dual-write problem from scratch.

## In practice

Priya's two designs:

- **Loyalty**: the web app baseline with web-queue-worker, built as a modular monolith by one team. The ADRs record the deviations: a single region for now (RTO of four hours is acceptable) and no AKS. The microservices discussion is parked until there is a second team.
- **Wholesale**: the same baseline, plus Entra External ID for business customers and API Management for partners' systems. The 2019 blog post is retired.
- **Review time** drops from weeks to an afternoon, because the conversation is about six deviations, not forty components.

**What it costs.** Baselines are production-grade, so they cost several times the starter design from [lesson 1.8](lesson:1.8). WAF, zone redundancy, private endpoints and premium tiers all add up. Use the baseline for production and a cut-down version for dev, with the difference written down.

**What breaks.**

- **Copying a reference architecture wholesale**, including components the workload does not need.
- **Microservices for one team**: five developers operating fourteen services.
- **Skipping the trade-off sections**, which is where the real guidance lives.
- **Stale sources**: blog posts and old diagrams instead of the maintained Architecture Center.
- **Deviations with no record**, so the next reviewer argues them all again.

## Guiding your team

> [!TEAM]
> At the start of any new design:
>
> 1. **Which reference architecture is closest?** Link it.
> 2. **Where do we differ from it, and why?** One ADR per deviation.
> 3. **How many teams will own this?** Does that justify more than one deployable?
> 4. **Which design patterns does it rely on?** Name them.
> 5. **What will the production baseline cost, and what does dev cut?**

## Key takeaways

- The Azure Architecture Center has reference architectures, architecture styles, technology choice guides and cloud design patterns. Start every design there.
- Baseline reference architectures are production-grade. The review then becomes a discussion of deviations, each recorded in an ADR.
- The architectures you will meet most: the web app baseline, the Reliable Web App pattern, web-queue-worker, microservices, hub-and-spoke landing zones, multi-region, and baseline RAG.
- Microservices solve a many-teams problem and create technical ones. For one team, a modular monolith is the better default.
- Name the patterns: cache-aside, valet key, competing consumers, outbox, gateway, retry, circuit breaker and strangler fig.
