## Why this matters

> [!SCENARIO] Forty-five minutes of clicking
> Tuesday, 14:10. Shoppers start posting that checkout fails. Dev opens the portal. App Service CPU looks fine. The SQL database's CPU looks fine. He opens each resource's blade in turn, looking at a different chart each time. The App Service log stream shows only the last few minutes. The database never had its diagnostic logs switched on. The warehouse VM's event log was on a disk that autoscale replaced an hour earlier.
>
> Forty-five minutes later he finds it: Front Door's WAF started blocking the payment provider's callback after a managed rule update. That fact was in a log category nobody was collecting.
>
> Priya's summary at the post-mortem: "We don't have observability. We have a portal."

## Monitoring versus observability

**Monitoring** tells you that something you anticipated has gone wrong: CPU above 80%, the error rate above 1%. **[Observability](gl:observability)** is being able to ask a question you did not anticipate - *why are only card payments from one provider failing since 14:02?* - and answer it from the data you already collect.

That depends on three kinds of signal, plus a record of what changed:

| Signal | What it is | Good for | Example |
|---|---|---|---|
| **[Metrics](gl:metric)** | Numbers sampled over time | Trends, thresholds, fast alerts | Requests per second, CPU, queue length |
| **Logs** | Timestamped records with detail | Asking *why*, investigation | A failed request with its status, URL and error |
| **Traces** | One request followed across services | Finding where time and errors happen | Checkout → API → SQL → payment provider |
| **Changes** | What was deployed or reconfigured, and when | The first question in any incident | A WAF rule update at 14:02 |

Metrics are cheap and fast but cannot explain. Logs explain but cost money per GB. Traces connect the two across services ([lesson 6.3](lesson:6.3)).

## Azure Monitor: one platform for all of it

**[Azure Monitor](gl:azure-monitor)** is the umbrella for Azure's observability tools. It has four layers:

- **Collect**: platform metrics and the [activity log](gl:activity-log) arrive automatically; resource logs through diagnostic settings; operating-system data through an agent; application telemetry through Application Insights.
- **Store**: a time-series store for metrics and [Log Analytics workspaces](gl:log-analytics-workspace) for logs and traces.
- **Use**: metrics explorer, log queries ([lesson 6.2](lesson:6.2)), workbooks, dashboards and managed Grafana.
- **Act**: alerts and automated responses ([lesson 6.4](lesson:6.4)).

## What you get free, and what you must switch on

==Out of the box Azure is rich in metrics and poor in logs: most of what you need in an incident is only collected if someone switched it on beforehand.==

| Source | Collected by default? | How to get it |
|---|---|---|
| Platform metrics (CPU, requests, DTU, queue length) | Yes, free, kept for 93 days | Nothing to do |
| Activity log (who changed what in Azure) | Yes, free, kept for 90 days | Send it to the workspace to keep it longer and query it with everything else |
| **[Resource logs](gl:resource-log)** (SQL errors, Key Vault reads, WAF blocks, HTTP logs) | **No** | A **[diagnostic setting](gl:diagnostic-setting)** per resource |
| Guest OS (Windows event log, Linux syslog, performance counters) | **No** | The **[Azure Monitor Agent](gl:azure-monitor-agent)** plus a **[data collection rule](gl:data-collection-rule)** |
| Your application's requests, dependencies and exceptions | **No** | Application Insights ([lesson 6.3](lesson:6.3)) |

A diagnostic setting names the log categories to collect and where to send them: a Log Analytics workspace for querying, a storage account for cheap long-term archive, or Event Hubs for a SIEM or third-party tool. Set them by hand and someone will forget the next resource. At scale, [Azure Policy](gl:azure-policy) has built-in *deploy if not exists* initiatives that add the right diagnostic settings to every new resource automatically.

A data collection rule says what the agent gathers - *Windows Application and System logs at Warning and above, these five performance counters every 60 seconds* - and where to send it. One rule can apply to every VM, so a replaced VM reports exactly like the old one.

## One workspace per environment

Log Analytics workspaces are where logs live, and the design decision is how many. Priya's rule is **one workspace per environment** - `law-shop-prod` and `law-shop-nonprod` - in the shop's main region. One workspace means a single query can join App Service, SQL, Front Door and the VM. Access is controlled per resource, so a team can see its own resources' logs without seeing everyone's. Split further only for a real reason: data residency, a separate security team, or a separate bill.

**What it costs.** Logs are billed per GB ingested - roughly $2.30 to $2.80 per GB on pay-as-you-go, depending on region - with 31 days of retention included. Platform metrics are free. Lesson 6.2 covers the levers: cheaper table plans, retention and commitment tiers. The shop expects about 3 GB a day in production, roughly $200 to $250 a month.

## In practice

Priya's baseline, applied by policy to every production resource:

- **Diagnostic settings to `law-shop-prod`** for App Service (HTTP and console logs), Azure SQL (errors, timeouts, deadlocks), Key Vault (audit events), Front Door (access and **WAF** logs), Service Bus, API Management and Event Grid.
- **The activity log** from every subscription into the same workspace.
- **Azure Monitor Agent** on the warehouse VM with one data collection rule for event logs and key counters.
- **Application Insights** for the APIs, backed by the same workspace.
- **No daily cap** on the production workspace. A cap stops collecting logs exactly when volume spikes, which is during an incident. Use a [cost alert](gl:cost-alert) on the workspace instead.

With that in place, Tuesday's question - *what changed at 14:02, and what is blocking the payment callback?* - is one query across Front Door's WAF log and the activity log.

**What breaks.**

- **Logs you did not collect.** They do not exist, however urgent the incident. Collect before you need them.
- **Collecting everything.** Storage read logs or verbose HTTP logs at scale can cost more than the workload. Pick categories deliberately.
- **A daily cap in production.** Data stops at the worst moment.
- **A workspace per team.** Nobody can correlate across services during an incident.
- **Logs only on the machine.** Autoscale and rebuilds delete them. Ship them off with the agent.

## Map it to what you know

| You already know | In Azure Monitor |
|---|---|
| Windows Event Viewer and perfmon | Azure Monitor Agent plus a data collection rule |
| The SQL Server error log and Profiler | Azure SQL resource logs and Query Store |
| `console.log` in Node, read with `pm2 logs` | App Service console logs, or Application Insights traces |
| An ELK stack or Splunk | Log Analytics workspaces |
| Prometheus and Grafana | Azure Monitor managed Prometheus and Azure Managed Grafana |
| Datadog or New Relic | Azure Monitor with Application Insights |

## Guiding your team

> [!TEAM]
> Before the next incident, ask:
>
> 1. **For each production resource, which log categories are collected, and where?** "None" is a common answer.
> 2. **Is that enforced by policy, or does it depend on someone remembering?**
> 3. **Can one query join the front door, the API, the database and the activity log?** If not, there are too many workspaces.
> 4. **What do we collect that nobody has ever queried?** That is cost without value.
> 5. **Is there a daily cap on production, and would we notice when it hits?**

## Key takeaways

- Monitoring answers expected questions; observability lets you answer new ones. It needs metrics, logs, traces and a record of changes.
- Azure Monitor collects, stores, visualises and alerts on all of it. Metrics and the activity log are automatic; resource logs, guest OS data and app telemetry are not.
- Diagnostic settings send resource logs to a workspace, storage or Event Hubs. Enforce them with Azure Policy.
- The Azure Monitor Agent with data collection rules collects VM logs, so they survive the VM.
- Use one Log Analytics workspace per environment so queries can span every service. Watch the cost with a budget alert, not a daily cap.
