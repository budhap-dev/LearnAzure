## Why this matters

> [!SCENARIO] Two moves, one good and one expensive
> Northline's nightly stock sync is a Windows service on a server that exists for that job alone ([lesson 1.2](lesson:1.2)). It wakes at 02:00, pulls a supplier file, updates 40,000 rows and sleeps for 23 hours and 56 minutes. Dev rewrites it as a timer-triggered function. The server goes away, the bill goes to roughly nothing, and nobody misses it.
>
> Encouraged, the team moves the orders API to the same Consumption plan. Latency gets worse, the first request after a quiet spell takes six seconds, and the monthly bill comes back **higher** than the App Service plan it replaced. Same technology, opposite result.

Serverless is not a better way to run everything. It is a very good way to run some things, and this lesson is about telling them apart.

## The model

[Azure Functions](gl:azure-functions) is Azure's implementation of [serverless](gl:serverless): you write a function, declare what should start it, and the platform runs it when that happens and bills for what it used. There is no instance to size, no OS to patch, no process to keep alive. When nothing is happening, nothing is running - **[scale to zero](gl:scale-to-zero)** - and when a thousand things happen at once, the platform creates instances to match, which is **[event-driven scaling](gl:event-driven-scaling)**.

## Triggers and bindings

A **[trigger](gl:trigger)** is the one thing that starts a function. A **[binding](gl:binding)** is declarative plumbing to a service: declare an output binding to a queue and you return an object instead of writing SDK code, connection handling and retries.

| Trigger | Use it for |
|---|---|
| HTTP | An API endpoint or a webhook receiver |
| Timer (CRON) | The nightly sync, the hourly report, the cleanup job |
| Queue Storage / Service Bus | Work that must happen exactly once, in order, with retries and a dead-letter queue |
| Blob | Reacting to an uploaded file - a thumbnail, a virus scan, an import |
| Event Grid | Reacting to something happening in Azure, at low latency and high fan-out |
| Event Hubs | High-volume telemetry streams processed in batches |
| Cosmos DB change feed | Reacting to documents that changed, without polling |
| Durable orchestration | A multi-step workflow that must remember where it got to |

## Hosting plans

The plan decides your latency, your maximum run time and your bill. Figures are current at the time of writing and change; confirm before quoting.

| Plan | Scales to zero | [Cold start](gl:cold-start) | Max [timeout](gl:function-timeout) | VNet integration |
|---|---|---|---|---|
| **[Consumption](gl:consumption-plan)** | Yes | Seconds, on every idle app | 5 min default, 10 max | No |
| **[Flex Consumption](gl:flex-consumption)** | Yes | Reduced; always-ready instances available | 30 min default, configurable | Yes |
| **[Premium](gl:functions-premium-plan)** | No (min 1 warm) | None | 30 min default, can be unbounded | Yes |
| **Dedicated (App Service)** | No | None with Always On | Unbounded | Yes |
| **Container Apps** | Yes (min 0 replicas) | Seconds from zero | Unbounded | Yes |

| Plan | Billing shape | Pick it when |
|---|---|---|
| Consumption | Per execution plus GB-seconds, with a monthly free grant | Spiky, low-volume, latency-tolerant work |
| Flex Consumption | GB-seconds plus any always-ready baseline | The same, but you need a VNet or fewer cold starts |
| Premium | Per vCPU and GB-hour of pre-warmed instances, roughly £120+ a month | Steady traffic, private networking, no cold starts allowed |
| Dedicated | The [App Service plan](gl:app-service-plan) you already pay for | You already run a plan ([lesson 2.2](lesson:2.2)) with headroom |
| Container Apps | Per vCPU-second and request | Functions live beside other containers ([lesson 2.5](lesson:2.5)) |

On Container Apps, use the current Functions hosting model: the original version, V1, stops running on 29 September 2027.

## Cold starts

An idle Consumption app has no instances. The first request has to wait for the platform to allocate one, start the language worker, load your dependencies and run your initialisation - typically one to several seconds, and worse for heavy dependency trees. Users experience it as an app that is fast all day and mysteriously slow first thing.

Four mitigations, in order of how much they actually help:

1. **Premium always-ready instances** - keep one or more instances warm permanently. Reliable and the reason Premium exists.
2. **Flex Consumption always-ready instances** - the same idea with per-second billing and a smaller floor.
3. **Keep it warm** - a timer function pinging every few minutes. Cheap, partial, and useless the moment scale-out adds a second instance.
4. **Do not use serverless there** - for a synchronous path with a latency budget, a plan that is always on is the honest answer.

## Durable Functions

[Durable Functions](gl:durable-functions) adds state to a stateless model. An **orchestrator** function describes a workflow in code and is replayed from an event history, so it must be deterministic - no `DateTime.Now`, no random values, no direct I/O. **Activity** functions do the actual work. **Entity** functions hold a small piece of addressable state.

Three patterns are worth naming in a design review: **function chaining** (step A then B then C, with each step's result durable), **fan-out/fan-in** (process 5,000 files in parallel, then aggregate), and **human interaction** (wait for an approval for up to three days, with a timeout branch). All of that without a workflow table in your database.

## The cost curve

This is the whole argument. Consumption charges per execution and per GB-second of memory-time, with a monthly free grant of roughly one million executions and 400,000 GB-seconds. Illustrative monthly figures for the same code on two plans:

| Workload | Consumption | Two P1v3 instances |
|---|---|---|
| Nightly sync: 30 runs, 4 min, 512 MB | £0 - inside the free grant | ~£150 |
| Modest API: 5M calls, 200 ms, 256 MB | ~£1-5 | ~£150 |
| Busy API: 130M calls, 500 ms, 512 MB | ~£400+ | ~£150-180 |

Notice what moves the number: not just call volume but duration times memory. A function that runs for half a second at 512 MB costs five times one that returns in 200 ms at 256 MB, for the same traffic. ==Spiky, low-duty-cycle work favours consumption; steady, high-volume work favours a fixed plan.==

That is exactly the mistake in the scenario. The nightly job runs for two hours a month and costs nothing. The orders API runs constantly, so per-execution billing kept charging while a fixed plan would have sat there absorbing the traffic for a flat fee.

> [!WARNING] What serverless is bad at
> - **Long-running work.** A 40-minute import does not belong on Consumption's 10-minute ceiling; use Durable Functions, Premium, or a container job.
> - **Predictable low latency.** Cold starts and per-request scaling make p99 unpredictable.
> - **Chatty synchronous chains.** Function calling function calling function multiplies latency and cost, and each hop can cold-start.
> - **Heavy dependencies and local state.** Big packages slow every start; nothing on the local disk survives.
> - **Lock-in.** Triggers and bindings are Azure-specific. The business logic ports; the plumbing does not - see [vendor lock-in](gl:vendor-lock-in) in [lesson 2.7](lesson:2.7).

## Map it to what you know

| You already do | On Azure Functions |
|---|---|
| A cron entry or a Windows service that sleeps | A timer trigger with a CRON expression, and nothing running between runs |
| An Express route handler | An HTTP-triggered function - same handler, no server to start |
| A Node worker looping over a queue | A queue trigger: one message, one invocation, retries and dead-lettering included |
| `setTimeout` in a process that might restart | A durable timer that survives restarts and can wait for days |
| AWS Lambda plus EventBridge | Functions plus Event Grid; bindings are the extra idea Lambda has no direct equivalent for |
| Retry loops written by hand | Binding-level retry and a dead-letter queue you did not write |

## Guiding your team

> [!TEAM]
> When someone proposes a function, ask:
>
> 1. **What starts it?** If the answer is "a request, and it must return in 200 ms every time", question the plan before the code.
> 2. **What is the duty cycle?** Busy all day is a fixed plan; a few thousand bursts a day is Consumption.
> 3. **How long can it run?** Anything near ten minutes needs Durable Functions or a different plan today, not after the first timeout in production.
> 4. **Does it need a VNet or a private endpoint?** That rules out plain Consumption immediately.
> 5. **What happens on the second delivery?** Queue triggers retry, so the work must be [idempotent](gl:idempotent).

## Key takeaways

- A function is code with a trigger; the platform runs it on the event and bills for the time it used.
- Bindings remove SDK plumbing for queues, blobs and Cosmos DB, at the cost of Azure-specific code.
- Consumption scales to zero and cold-starts; Premium and Dedicated stay warm; Flex Consumption sits between them with VNet support.
- Consumption's timeout ceiling is minutes, not hours - design for it before production finds it.
- Cost follows executions times duration times memory, so a busy, long-running API can cost more than an always-on plan.
- Serverless suits spiky, asynchronous, short work; it is a poor fit for low-latency synchronous paths and long jobs.
