## Why this matters

> [!SCENARIO] "Could someone poison our build?"
> A contractor pastes the live payment provider key into a test file and pushes it. It sits in the repository's history for three weeks before anyone notices. Dependabot, switched on for the first time, reports 48 vulnerable dependencies, including a critical one in the image-processing library. And after reading about a build-system breach at another company, the board asks Priya a question she cannot yet answer: *could someone poison what we ship?*
>
> Lessons 7.3 to 7.5 made pipelines the only way to production. That also makes them the most valuable thing an attacker could compromise.

## The pipeline is production's front door

Whoever controls the pipeline controls production: it holds deployment identities, builds the artefacts customers run, and pulls in thousands of dependencies written by strangers. Attacks on that path - **[supply chain attacks](gl:supply-chain-attack)** - have hit well-known organisations. SolarWinds' build system was altered to ship a backdoor in signed updates. A popular npm package was taken over and given a payload. A widely used GitHub Action was re-pointed at code that dumped secrets into build logs. In 2024 the `xz` compression library nearly shipped a backdoor planted over two years.

## Secrets: aim for none

The best pipeline secret is one that does not exist.

- **Deploying to Azure**: workload identity federation for Azure Pipelines and GitHub Actions ([lessons 7.3](lesson:7.3) and [7.4](lesson:7.4)), with one identity per environment, scoped to its resource group.
- **Apps reaching Azure services**: managed identities ([lesson 4.5](lesson:4.5)).
- **Third-party keys the app needs**: Key Vault, read at run time through Key Vault references ([lesson 4.6](lesson:4.6)), never baked into the artefact.
- **What remains in the pipeline itself**: environment-scoped secrets in GitHub or Key Vault-linked variable groups in Azure DevOps, masked in logs and available only to the job that needs them.

**[Secret scanning](gl:secret-scanning)** finds credentials committed to repositories - hundreds of token formats, including Azure keys and connection strings. With **push protection** turned on, a push containing a recognised secret is blocked before it lands.

==When a secret leaks, rotate it first and clean up afterwards: removing it from the latest commit does nothing, because it lives on in history, forks and clones.== The payment key took 20 minutes to rotate, and only then did history get rewritten.

## Dependencies you did not write

A typical Node API ships far more third-party code than its own. **[Dependency scanning](gl:dependency-scanning)** keeps that manageable:

- **Lockfiles and `npm ci`** make builds install exactly the reviewed versions, never whatever is newest that day.
- **Dependabot alerts** report known vulnerabilities; **Dependabot updates** open pull requests to fix them. Group them weekly and auto-merge patch updates that pass tests, so the flood stays manageable.
- **Dependency review** on pull requests blocks changes that add a vulnerable or disallowed-licence package.
- A **private feed with upstream sources** (Azure Artifacts or GitHub Packages) gives one controlled place where public packages enter the organisation.
- Watch for **typosquatting** (`lodahs` instead of `lodash`) and install scripts that run code at `npm install`.

Set a response time by severity - critical within 48 hours, high within two weeks - and track it.

## Scanning your own code

**[Code scanning](gl:code-scanning)** - static analysis such as **CodeQL** - reads the source for vulnerability patterns: SQL injection, path traversal, unsafe deserialisation, missing authorisation checks. Run it on every pull request as a required check that blocks high-severity findings. Developers then see and fix issues in the same pull request that introduced them, when fixing is cheapest. Triage false positives once, with a reason, so the check keeps its credibility.

## Artefacts you can trust

- A **[software bill of materials](gl:software-bill-of-materials)** (SBOM) lists every component and version in a build, in a standard format such as SPDX or CycloneDX. When the next Log4Shell-style vulnerability is announced, "are we affected, and where?" takes one search instead of a week.
- **Provenance attestations** record, and sign, which workflow built which artefact from which commit. GitHub artifact attestations follow the SLSA framework. Container images can be signed too.
- **Deploy only what you built**: the registry accepts pushes only from the pipeline's identity, deployments use immutable image digests rather than `latest` ([lesson 2.5](lesson:2.5)), and the deploy job verifies the attestation before release.

## Securing the pipeline itself

Apply the earlier lessons to the pipeline as a system: branch protection and CODEOWNERS on pipeline files ([7.2](lesson:7.2)); least-privilege tokens and pinned actions ([7.4](lesson:7.4)); approvals on environments and service connections ([7.3](lesson:7.3)); ephemeral runners, never self-hosted runners on public repositories. And separate duties: the **build** job runs untrusted code - dependencies and tests - and holds no production credentials; the **deploy** job holds credentials and runs no untrusted code.

## Tools

- **[GitHub Advanced Security](gl:github-advanced-security)** now comes as two products: **Secret Protection** (secret scanning and push protection) and **Code Security** (CodeQL code scanning, dependency review and security campaigns). Each is priced per active committer - together about $50 per committer per month for private repositories, and free for public ones. **GitHub Advanced Security for Azure DevOps** brings the same scanning to Azure Repos. Dependabot alerts and updates are free.
- **Microsoft Defender for Cloud**'s DevOps security connects to GitHub and Azure DevOps. It gathers findings across repositories and links them to the running resources they affect ([lesson 4.7](lesson:4.7)), so a vulnerable package can be traced to the App Service that runs it.

## In practice

The shop's controls, applied to every repository: push protection on (it blocked three pushes in the first month); Dependabot with grouped weekly updates and a 48-hour target for criticals, now met; dependency review and CodeQL as required checks; SBOMs and provenance attestations for every API image; a registry that accepts only the pipeline identity's pushes; deploy jobs that verify attestations and deploy by digest; and the Defender for Cloud DevOps connector. The board's question now has an answer: here is how each stage is protected, and here is how we would know.

**What it costs.** Roughly $50 per active committer per month for GitHub Secret Protection and Code Security on private repositories; Dependabot is free. One leaked production key or a poisoned build costs far more.

**What breaks.**

- **"Deleted" secrets.** Still in history, forks and caches. Rotate first.
- **Ignored Dependabot floods.** Group updates, auto-merge safe ones, and give criticals a deadline.
- **Build jobs with production credentials.** Any compromised dependency then has the keys.
- **Mutable tags.** `latest` means production runs whatever was pushed last.
- **Scanning nobody acts on.** Findings without gates or owners become background noise.

## Map it to what you know

| You already know | In the pipeline |
|---|---|
| `npm audit` | Dependabot alerts, updates and dependency review, continuously |
| Snyk or SonarQube | Code scanning with CodeQL, dependency scanning |
| Authenticode signing of .NET assemblies | Signing artefacts and container images, plus provenance attestations |
| `web.config` transforms that inject passwords at deploy time | Federation, managed identities and Key Vault references - no passwords to inject |
| A licence and component spreadsheet | A software bill of materials generated by every build |

## Guiding your team

> [!TEAM]
> For every repository and pipeline, ask:
>
> 1. **What secrets does the pipeline hold, and could federation or a managed identity remove them?**
> 2. **Is push protection on, and what is our playbook when a secret leaks?**
> 3. **What is our response time for critical dependency and code scanning findings, and are we meeting it?**
> 4. **Can we say, in an hour, whether a newly announced vulnerable component is running anywhere?**
> 5. **Does the build job hold production credentials, and can production run anything the pipeline did not build?**

## Key takeaways

- The pipeline holds the keys to production; supply chain attacks target builds, dependencies and pipeline tools.
- Aim for no pipeline secrets: federation for deployments, managed identities and Key Vault for apps. Secret scanning with push protection stops the rest, and a leaked secret is rotated first.
- Scan dependencies and code on every pull request as required checks, with response times by severity.
- Produce an SBOM and signed provenance for every artefact, deploy by digest, and allow only pipeline-built artefacts into production.
- Keep untrusted code and production credentials in different jobs, and protect the pipeline with the same controls as production.
