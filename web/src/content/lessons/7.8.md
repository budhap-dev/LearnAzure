## Why this matters

> [!SCENARIO] "Are we actually getting better?"
> After a quarter of pipeline work, the CTO asks a fair question: are we getting better, or just busier? The only numbers anyone has are story points.
>
> Meanwhile the test suite takes 45 minutes, most of it browser tests that fail at random, so people re-run them until they pass. A coverage target of 60% was met by tests that assert nothing. And a checkout bug reached production even though every test was green, because every test mocked the payment provider.
>
> Priya needs tests that catch real problems quickly, gates that people trust, and four numbers that show whether delivery is improving.

## The test pyramid

The **[test pyramid](gl:test-pyramid)** says to have many fast, focused tests at the bottom and few slow, broad ones at the top:

| Level | Proves | Speed | Runs |
|---|---|---|---|
| **Unit** | One function or component behaves correctly | Milliseconds | Every push and pull request |
| **Integration** | Code works with real dependencies - a database, a queue, blob storage | Seconds | Every pull request |
| **Contract** | The API and its clients agree on requests and responses | Seconds | Every pull request, on both sides |
| **End-to-end** | A critical user journey works through the whole system | Minutes | Before release, against a deployed environment |
| **[Smoke](gl:smoke-test)** | A new deployment is basically alive | Seconds to a minute | Straight after each deployment |
| **Load** | It holds at and beyond peak ([lesson 6.5](lesson:6.5)) | Minutes to hours | Before big events |

The shop had built the opposite shape - the *ice-cream cone*: a few unit tests and a mountain of slow browser tests. It is slow, flaky and poor at pointing to the cause.

**Integration tests with real dependencies** catch what mocks hide. The payment bug lived in how the API handled the provider's real error response, which no mock returned. Run real dependencies in containers during the build: SQL Server through Testcontainers, **Azurite** for storage ([lesson 3.1](lesson:3.1)), the Service Bus and Cosmos DB emulators. Keep a small set of tests against the provider's sandbox. **Contract tests** let the React app, the React Native app and the API each check their side of the agreement without deploying everything together.

## Quality gates

A **[quality gate](gl:quality-gate)** is a check that must pass before a change moves forward. The shop's gates:

- **Pull request**: build, unit, integration and contract tests, lint, CodeQL and dependency review ([lesson 7.6](lesson:7.6)). Coverage on *changed lines* must not fall - a floor on new code rather than a vanity target for the whole codebase.
- **After deploying to the staging slot**: smoke tests - `/health`, sign-in, add to basket and a checkout with a test card - plus eight end-to-end journeys in Playwright.
- **Canary**: the SLO comparison from [lesson 7.7](lesson:7.7).
- **After release**: availability tests ([lesson 6.3](lesson:6.3)) and the SLO alerts ([lesson 6.4](lesson:6.4)).

==A gate is only worth having if it is fast enough not to be bypassed and reliable enough to be believed: fix or quarantine a flaky test within days, because a check people learn to re-run until green has stopped checking anything.==

## Four numbers for delivery

Story points measure effort estimates, not outcomes. The **[DORA metrics](gl:dora-metrics)**, from years of research into software delivery, measure outcomes. They come in pairs, so speed and stability cannot be traded without it showing:

| Metric | Measures | Where the data comes from |
|---|---|---|
| **Deployment frequency** | How often changes reach production | Pipeline runs to production |
| **[Lead time for changes](gl:lead-time-for-changes)** | Time from commit to running in production | Commit and deployment timestamps |
| **[Change failure rate](gl:change-failure-rate)** | Share of deployments that cause a failure needing a fix, rollback or hotfix | Deployments linked to incidents and rollbacks |
| **Time to restore service** | How long it takes to recover when a deployment fails | Incident start and resolution times |

The first two measure throughput; the second two measure stability. The research's consistent finding is that the best teams are better at both at once: small, frequent, well-tested changes are faster *and* safer than big, rare ones.

Collect them automatically from GitHub or Azure DevOps and incident records, show them on a workbook, and look at trends, not single weeks. Use them to improve the team's system, never to rank individuals or teams against each other - a metric turned into a target gets gamed, exactly as the coverage figure was. They sit alongside the SLOs and error budget from [lesson 6.4](lesson:6.4), which say whether users are happy with the result.

## In practice

The shop rebuilt its tests around the pyramid: about 1,200 unit tests (40 seconds), 90 integration tests against real SQL, Azurite and the Service Bus emulator (4 minutes), contract tests between the apps and the API, and eight Playwright journeys that run as smoke and end-to-end tests on the staging slot (3 minutes). That replaced the 45-minute browser suite. Flaky tests are quarantined automatically and must be fixed within two days. A DORA workbook reads from GitHub and the incident log.

A quarter later: deployments went from weekly to several a day, lead time from nine days to under one, change failure rate from about one in five to about one in twenty, and time to restore from three hours to twenty minutes. The CTO's question has an answer.

**What breaks.**

- **The ice-cream cone.** Slow, flaky browser tests at the centre of the pipeline. Push checks down the pyramid.
- **Mocks all the way down.** Tests that cannot fail the way production does. Use real dependencies in integration tests.
- **Coverage as a target.** Tests that execute code without asserting anything. Gate on changed lines, and review test quality.
- **Flaky tests tolerated.** Re-runs until green teach everyone to ignore red.
- **Metrics as league tables.** Numbers compared between teams get gamed; trends within a team get improved.

## Map it to what you know

| You already know | In the pipeline |
|---|---|
| NUnit or xUnit in Visual Studio | Jest or Vitest for Node and React, run on every pull request |
| Selenium suites run overnight | A few Playwright journeys as smoke tests after each deployment |
| SQL Server LocalDB for tests | SQL Server in a container through Testcontainers |
| A release sign-off meeting | Automated gates plus an approval on the production environment |
| Velocity and story points | DORA metrics for delivery; SLOs for the user's experience |

## Guiding your team

> [!TEAM]
> Each month, ask:
>
> 1. **How long does the pull request pipeline take, and which tests are flaky?**
> 2. **Which failures reached production that a test should have caught - and at which level of the pyramid?**
> 3. **Do our integration tests use real dependencies where it matters?**
> 4. **What are our four DORA metrics, and which way are they trending?**
> 5. **Is any metric being used as a target that people have learnt to game?**

## Key takeaways

- Follow the test pyramid: many fast unit tests, integration and contract tests with real dependencies, and a few end-to-end journeys run as smoke tests after deployment.
- Gates must be fast and trustworthy. Fix or quarantine flaky tests quickly, and gate coverage on changed lines rather than a whole-codebase target.
- The DORA metrics - deployment frequency, lead time for changes, change failure rate and time to restore - measure delivery speed and stability together.
- The best teams improve both at once, through small, frequent, well-tested changes.
- Use metrics to improve the system, not to rank people; pair them with SLOs for the user's view.
