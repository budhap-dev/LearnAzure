## Why this matters

> [!SCENARIO] The first full month
> The assistant is live for every shopper, and it is popular. Then the first full month arrives.
>
> The bill is $18,000 against an estimate of $4,000. At lunchtime on a Tuesday, a new batch job used the whole tokens-per-minute quota, and shoppers got "Sorry, something went wrong" for forty minutes. A security review finds that the dev Foundry resource accepts keys from the public internet. And an email warns that a model version is retiring in 60 days. Nobody can say which apps use it.
>
> None of these is an AI problem. They are platform problems that AI makes expensive quickly. Priya needs to run AI like the rest of production.

## Where the money goes

A conversation's cost is simple arithmetic: **model calls per turn × (input tokens × input price + output tokens × output price)**. The bill grows through each term:

- **The model**: the flagship where a small model would pass ([lesson 8.2](lesson:8.2)).
- **Input size**: a long system prompt, ten retrieved chunks and the whole chat history, resent on every call.
- **Calls per turn**: an agent's tool loop multiplies everything ([lesson 8.6](lesson:8.6)).
- **Output length**: output tokens cost several times as much as input.
- **Hidden traffic**: retries, evaluation runs and dev load tests in the prod subscription.

| Lever | How | Trade-off |
|---|---|---|
| Route by difficulty | A small model handles simple questions; hard ones go to a larger model | A routing step to build and evaluate |
| Trim the input | Fewer, better chunks (the semantic ranker helps); summarise older turns | Needs an evaluation to prove quality holds |
| Cap the output | Set a maximum number of output tokens, and ask for concise answers | Truncated answers if set too low |
| Prompt caching | Put the unchanging part of the prompt first; repeated prefixes are billed at a discount | None, beyond ordering the prompt |
| [Semantic caching](gl:semantic-caching) | Return a stored answer to a question that means the same as an earlier one | Only safe for answers that are not personal and not time-sensitive |
| Batch and PTUs | Batch at half price for work that can wait; PTUs for a steady baseline | Latency for batch; commitment for PTUs |

==Measure cost per conversation, not cost per month.== A monthly total says the bill went up. Cost per conversation, by app and by feature, says why.

API Management's AI policies do the work:

- **Token limits per consumer**: the batch job gets a tokens-per-minute ceiling, so it can never starve the assistant again.
- **Token metrics**: prompt and completion tokens are recorded per app, team and deployment, which is the basis for chargeback.
- **Semantic caching**, backed by Redis.
- **Load balancing** across deployments and regions, with priorities and a circuit breaker.
- **Content safety checks**, applied once for every app.

Apps authenticate to the gateway with managed identities, and the gateway authenticates to Foundry with its own. No app holds a model key.

## Security

The controls are the Module 4 controls, applied to a new kind of resource:

- **Identity**: managed identities everywhere and key-based access disabled. Azure Policy denies Foundry resources with local authentication switched on.
- **Network**: [private endpoints](gl:private-endpoint) and public network access disabled, with agents running inside your virtual network where it matters.
- **Data**: choose deployment types for residency. Know what is stored (uploaded files, agent threads, fine-tuning data) and add [customer-managed keys](gl:customer-managed-key) where policy requires them. Understand **[abuse monitoring](gl:abuse-monitoring)**: prompts and outputs flagged as possible abuse can be kept for up to 30 days for review by authorised Microsoft staff, unless you are approved for modified monitoring.
- **Threat detection**: Microsoft Defender for Cloud's AI threat protection flags jailbreak attempts, data exposure and unusual use.
- **Governance**: Azure Policy restricts which models and deployment types are allowed, and tags and budgets apply as they do to everything else.

## Operations: GenAIOps

**[GenAIOps](gl:genaiops)** is DevOps and MLOps for generative AI: every prompt, model version, tool and index is versioned, evaluated, deployed through the pipeline and monitored. The AI-specific part is **[model retirement](gl:model-retirement)**. Model versions are retired on a published schedule. When one retires, deployments still using it stop working or move to a newer version. Either way, behaviour changes.

So keep an **inventory**: which app uses which deployment, model and version, recorded in Bicep, not in someone's head. Start evaluating the replacement as soon as a retirement date is announced. Choose each deployment's upgrade policy deliberately.

Watch these signals on a dashboard, with alerts on each:

- Tokens and cost per conversation.
- Time to first token and total latency.
- The rate of 429s.
- Content filter blocks.
- Sampled groundedness and thumbs-down.

Keep a **kill switch**, a [feature flag](gl:feature-flag) that falls back to plain search, for when quality or a provider fails.

## In practice

Priya's month-two changes:

- **Gateway first**: every app goes through API Management. The batch job is capped at 30% of TPM and moved to Global Batch.
- **Cost per conversation fell from 4.1 cents to 1.3 cents**. A small model now answers the two-thirds of questions a classifier marks as simple. Three reranked chunks replace eight. History is summarised after six turns. The system prompt comes first so it is cached. Returns-policy FAQs are served from the semantic cache, with a 12% hit rate and never for order-specific questions.
- **Budgets** in Cost Management alert at 80% and 100% of the monthly figure, with app tags on every AI resource.
- **Security**: private endpoints on every environment. Local auth is disabled everywhere and Policy denies it. Defender's AI threat protection is on.
- **Operations**: the model inventory lives in Bicep. Retirement notices create a backlog item with an evaluation run 90 days ahead. The kill switch is tested quarterly.

**What breaks.**

- **Apps calling models directly**, each with its own key and no limits.
- **One monthly AI bill with no breakdown** by app or feature.
- **Caching personal or time-sensitive answers.**
- **Public endpoints and key auth left on in dev**, because "it's only dev".
- **Finding out about a model retirement from a failed request.**

## Map it to what you know

| You already know | For AI workloads |
|---|---|
| An API gateway in front of microservices | The AI gateway in front of model endpoints |
| Per-client API quotas | Token limits per app |
| An output cache or a CDN | Semantic caching, for non-personal answers |
| SQL Server end of support | Model retirement: a date, a replacement, and testing before it |
| Application Insights dependency metrics | Token, latency, 429 and quality metrics per app |

## Guiding your team

> [!TEAM]
> For an AI workload in production:
>
> 1. **What does one conversation cost, and which lever would cut it most?**
> 2. **Does every call go through the gateway, with a token limit per app?**
> 3. **Are keys disabled and public access closed, in every environment?**
> 4. **Which model versions do we run, and when do they retire?**
> 5. **What is the kill switch, and when did we last test it?**

## Key takeaways

- Cost is calls × tokens × price. Route by difficulty, trim input, cap output, cache prompts and repeated answers, batch what can wait, and measure cost per conversation.
- An AI gateway in API Management gives token limits per app, metering, semantic caching, load balancing with spillover, and safety checks in one place.
- Secure AI like any platform: managed identity with keys disabled, private endpoints, the right data zone, abuse monitoring understood, Defender and Policy.
- GenAIOps versions, evaluates, ships and monitors prompts, models, tools and indexes together. Track model retirements and test the replacement early.
- Keep a kill switch that falls back to a non-AI path.
