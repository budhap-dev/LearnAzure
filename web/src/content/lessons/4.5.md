## Why this matters

> [!SCENARIO] Fourteen Owners and a secret in GitHub
> The access review Priya ordered after the contractor incident takes one afternoon and ruins her week. Fourteen people hold **Owner** on the production subscription, because "deploying needed it" once. The GitHub Actions pipeline signs in as a service principal with Owner on the whole subscription, using a client secret pasted into GitHub two years ago. The Node API reads product images with the storage account key and connects to SQL with a SQL login.
>
> Dev tries to do the right thing. He gives the API's managed identity Owner on the storage account and removes the key from the config. The API gets `403 AuthorizationPermissionMismatch`.
>
> Priya wants least privilege without making every deploy a ticket.

## One sentence: who, what, where

[Role-based access control](gl:role-based-access-control) in Azure comes down to one object. A **[role assignment](gl:role-assignment)** says: this **[security principal](gl:security-principal)** holds this **role** at this **[scope](gl:scope)**.

- **Who** - a security principal: a user, a group, a [service principal](gl:service-principal) or a [managed identity](gl:managed-identity). Assign to groups for people and to identities for code.
- **What** - a role definition: a list of allowed actions, such as `Microsoft.Storage/storageAccounts/read`.
- **Where** - a scope: a management group, a subscription, a resource group or a single resource. **Permissions flow downwards**: Reader on the subscription is Reader on everything in it.

## Built-in roles, and the two planes

Most assignments use a **[built-in role](gl:built-in-role)**. Four matter everywhere:

| Role | Can | Cannot |
|---|---|---|
| **Owner** | Everything, including granting access to others | Nothing - which is the problem |
| **Contributor** | Create, change and delete resources | Grant access |
| **Reader** | See resources and settings | Change anything |
| **User Access Administrator** | Grant access | Change resources |

Hundreds more are service-specific, and they come in two families because Azure has two planes. The [control plane](gl:control-plane) is Azure Resource Manager: creating the storage account, changing its settings. The [data plane](gl:data-plane) is the service itself: reading a blob, fetching a secret, sending a message. ==Control-plane roles such as Owner and Contributor do not read your data; data-plane roles such as Storage Blob Data Reader and Key Vault Secrets User do.==

That is Dev's 403. Owner lets the identity manage the storage account, not read blobs through Entra ID. The fix is **Storage Blob Data Contributor** on the `product-images` container, and nothing on the account itself. One trap runs the other way: Owner and Contributor can list the storage account *keys*, which read everything. That is why [lesson 3.1](lesson:3.1) disables shared-key access.

A few services keep their own data-plane permissions. Azure SQL uses database users - `CREATE USER [app-shop-api] FROM EXTERNAL PROVIDER` and a database role - and Cosmos DB has its own data-plane role assignments. The principle is the same; the place you grant it differs.

When no built-in role is narrow enough, a **[custom role](gl:custom-role)** lists exactly the actions you need. Reach for one rarely: every custom role is something to maintain as services add actions.

## Least privilege without the tickets

**[Least privilege](gl:least-privilege)** means every principal holds the smallest role at the smallest scope that lets it do its job, and nobody holds power they are not using. Three habits make it practical:

1. **Groups, not people.** Grant `grp-shop-devs` Contributor on `rg-shop-dev`; joining and leaving the group is the whole access process.
2. **Resource group scope for teams and pipelines.** A pipeline for one workload needs Contributor on that workload's resource group, not the subscription.
3. **No standing admin rights.** **[Privileged Identity Management](gl:privileged-identity-management)** (PIM) makes Owner *eligible* rather than active: an admin activates it for a few hours with MFA and a reason, optionally with approval, and it expires by itself. Every activation is logged. It needs Entra ID P2.

## Managed identities: code with no secret

A managed identity is a service principal whose credential Azure creates, rotates and never shows you. Code asks the platform for a token, and there is nothing to store, leak or let expire. Two kinds:

| | System-assigned | **[User-assigned](gl:user-assigned-managed-identity)** |
|---|---|---|
| Lifecycle | Created and deleted with its resource | A resource of its own |
| Shared | One resource only | Across several resources |
| Pre-granting | Only after the resource exists | Before the resource exists - handy for infrastructure as code |
| Use it for | One app, one set of permissions | Several instances or apps with the same access; identities that must survive a rebuild |

In Node, `DefaultAzureCredential` from `@azure/identity` picks the right credential by itself: your `az login` on a laptop, the managed identity in Azure. The same code runs in both places, and the connection string holds a host name and nothing else.

Code outside Azure uses **[workload identity federation](gl:workload-identity-federation)**. GitHub Actions already issues each workflow run a signed OIDC token. You tell Entra ID to trust tokens from one repository, branch or environment, and the workflow exchanges its GitHub token for an Azure one. No secret ever enters GitHub.

## In practice

Priya's new assignments for production:

| Principal | Role | Scope |
|---|---|---|
| `grp-shop-admins` | Owner, **eligible** through PIM | `sub-shop-prod` |
| `grp-shop-devs` | Reader | `mg-shop`; Contributor on `rg-shop-dev` only |
| `id-deploy-prod` (user-assigned, federated with GitHub `environment:prod`) | Contributor | `rg-shop-prod` |
| Node API (system-assigned) | Storage Blob Data Contributor; Key Vault Secrets User | `product-images`; `kv-shop-prod` |
| Node API | `db_datareader`, `db_datawriter` | The orders database, as a database user |
| Emergency access accounts ([lesson 4.4](lesson:4.4)) | Global Administrator, permanent | The Entra ID tenant, alerted on every sign-in |

**What it costs.** RBAC and managed identities are free. PIM needs Entra ID P2, about $9 per user per month, for the people who activate roles.

**What breaks.**

- **The wrong plane.** Owner granted, 403 returned. Grant the data role.
- **Propagation.** A new role assignment can take several minutes to apply everywhere; a test that fails immediately after granting may pass five minutes later.
- **The rebuilt resource.** A system-assigned identity dies with its resource; recreate the app and every grant is gone. Use user-assigned identities for things you rebuild.
- **Ghosts.** Deleting an identity leaves its assignments showing as "Identity not found". Clean them up in the access review.
- **Subscription-wide convenience.** Contributor on the subscription "so the pipeline never fails" is how one leaked token deletes production *and* the backups.

## Map it to what you know

| You already know | On Azure |
|---|---|
| The local Administrators group on a server | Owner - and the same reason to keep it nearly empty |
| `GRANT SELECT ON SCHEMA::sales TO reporting_role` | A data-plane role assignment at a scope |
| `sudo` with a time-limited ticket | PIM: eligible, activated, expires |
| A Windows group managed service account (gMSA) | A managed identity |
| AWS IAM roles trusted by GitHub's OIDC provider | Workload identity federation |
| A service account password in `web.config` | Exactly what managed identities remove |

## Guiding your team

> [!TEAM]
> In every access review, ask:
>
> 1. **Who holds Owner permanently, and why is it not eligible through PIM?**
> 2. **Is every role assigned to a group or an identity, not a person?**
> 3. **What is the widest scope any pipeline holds?** One workload, one resource group.
> 4. **Which code still uses a key, a password or a client secret?** Each one is a migration to a managed identity or federation.
> 5. **Does each app have data-plane roles only on what it touches?** One container, one vault - not the account, not the subscription.

> [!TIP] Exam link
> AZ-900 wants scopes, inheritance and the Owner, Contributor and Reader roles. AZ-104 is heavy on role assignments, custom roles and managed identities. AZ-204 covers `DefaultAzureCredential` and data-plane access; AZ-500 and SC-300 cover PIM.

## Key takeaways

- A role assignment is a principal, a role and a scope, and permissions flow down from the scope.
- Owner, Contributor and Reader are control-plane roles; reading data needs data-plane roles such as Storage Blob Data Reader or Key Vault Secrets User. SQL and Cosmos DB grant data access their own way.
- Least privilege in practice: groups not people, resource-group scope for pipelines, and PIM so no one holds Owner until they need it.
- Managed identities remove secrets from code in Azure: system-assigned for one resource, user-assigned to share or survive rebuilds. `DefaultAzureCredential` runs the same code locally and in Azure.
- Workload identity federation lets GitHub Actions deploy with no secret in GitHub.
