## Why this matters

> [!SCENARIO] Seven calls and a renamed field
> Leo times the mobile app's home screen on a train out of Bengaluru. It makes seven API calls over 4G (profile, basket, points, recommendations, banners, orders and stock) and takes three seconds to settle.
>
> On Tuesday Ana renamed `deliveryDate` to `estimatedDelivery` in the orders API. She shipped it as an API Management revision, not a new version, because it was "only a rename". Version 2.4 of the app, which 18% of customers still run, now crashes on order history. Nobody can force an update.
>
> Priya asks for a backend that suits each client, and a rule that stops this happening again.

Phones differ from browsers in four ways. Every round trip is expensive. The connection drops in tunnels. You cannot recall an installed app. And anything in the bundle is public, as the signed URL in [lesson 3.1](lesson:3.1) showed.

## The backend for frontend

A **[backend for frontend](gl:backend-for-frontend)** (BFF) is a thin API built for one client's screens and owned by that client's team. Leo's home screen becomes one call, `GET /mobile/v2/home`. The BFF calls the seven services in parallel inside Azure, where a hop takes milliseconds, drops the fields the phone never shows, and returns one small payload.

Keep the split from [lesson 5.5](lesson:5.5): [API Management](gl:azure-api-management) validates tokens, applies [rate limits](gl:rate-limiting) and routes; domain APIs keep business rules. ==The BFF holds only what is specific to the client: aggregation, trimming, paging sized for a phone, and the old contracts installed apps still expect.== It runs on ![App Service](az:app-service) or ![Functions](az:function-apps), and only ![API Management](az:api-management) can reach it.

**Worth it** when clients really differ, mobile screens are chatty, or old installs must keep working. **Not worth it** for one client, or clients that ask for the same things: a BFF is another service to run. Build one per experience, not per platform; iOS and Android share screens. Northline builds a mobile BFF only.

**[GraphQL](gl:graphql) is the other answer**: the client asks for exactly the fields a screen needs, in one request. APIM supports it in every tier, passed through to a GraphQL server or as synthetic GraphQL with resolvers over REST, Cosmos DB or Azure SQL (subscriptions on synthetic APIs are in preview). The costs: queries are `POST`s to one URL, so HTTP caching mostly stops working, and you must cap query depth with the validation policy. A fair choice for a team that knows Apollo; Northline stays with REST.

## Versions you cannot recall

==A web shop is fixed by the next deploy; an installed app is fixed only when its owner chooses to update.==

**[API versioning](gl:api-versioning)** lets one API serve both. APIM can carry the version in the path, a header or the query string. Northline uses the path (`/mobile/v1`), partly because APIM's CORS policy does not work at API scope with header versioning. Renaming or removing a field, changing its type or making it required is breaking. So is a new enum value, if the app's `switch` has no default. Breaking changes need a new version; revisions are only for changes that break nobody.

With a BFF, old contracts live in one place. `/mobile/v1/orders` maps `estimatedDelivery` back to `deliveryDate`, the Orders API keeps one model, and 2.4 works again. Database changes follow expand and contract ([lesson 7.7](lesson:7.7)). Retire old versions by data: [Application Insights](gl:application-insights) splits users by app version ([lesson 6.3](lesson:6.3)).

Then add a **[minimum supported app version](gl:minimum-supported-app-version)**. The BFF serves `GET /mobile/config` with `minSupported` and `latest`, read from [App Configuration](gl:azure-app-configuration) so ops can raise them without a deploy. On launch the app compares its own [semantic version](gl:semantic-versioning) and, below the minimum, shows a full-screen "please update". Google Play's immediate in-app update flow does this on Android; on iOS the app draws its own screen. The catch: only versions that contain the check obey it, and 2.4 does not. Ship it in your first release.

## Offline-first, and retries that do not double-charge

**[Offline-first](gl:offline-first)** means the app reads from a store on the device and syncs in the background. The basket and order history suit it; checkout, which must confirm payment and stock, does not. **[Optimistic UI](gl:optimistic-ui)** goes with it: "Add to basket" updates at once and queues the request, and if the server later says the item sold out, the app rolls back and says why.

Queued requests get retried, and retries create duplicates. An **[idempotency key](gl:idempotency-key)** prevents them. The app sends a unique ID per user action in an `Idempotency-Key` header; the API stores each key with its result in Azure SQL and answers a repeat with the stored result, not a second order. `POST` becomes [idempotent](gl:idempotent) in practice.

Azure has no offline-sync SDK for React Native: Azure Mobile Apps is retired, and its successor, the Datasync Community Toolkit, targets .NET. You build the device store and queue, and the server's "changed since" endpoints.

## In practice

Northline after the incident:

- **`app-mobile-bff`**: Node on the existing App Service plan, behind APIM's Mobile product. On Leo's train the home screen now settles in under a second.
- **Versions**: v1 keeps 2.4 alive for at least twelve months, and until under 2% of active devices use it.
- **Minimum version**: the check ships in 2.8.
- **Offline**: basket and order history cached on the device; checkout online-only; every app `POST` carries an idempotency key, kept 24 hours.
- **[CORS](gl:cross-origin-resource-sharing)**: the shop is same-origin through Front Door and needs none. The wholesale portal, on another host name, is listed by exact origin in APIM's `cors` policy. Native apps ignore CORS: it is a browser rule, not authentication.

**What it costs.** Little compute on a plan with headroom. The real cost is people: one more service, and every old version to maintain.

**What breaks.**

- **Business rules creeping into the BFF**, so discounts differ between web and app.
- **The web team calling the mobile BFF**, which becomes a general API with two masters.
- **A breaking change shipped as a revision.** That was Tuesday.
- **Retries without idempotency keys.** A tunnel plus a retry means two orders.

## Map it to what you know

| You already know | Here |
|---|---|
| Next.js API routes shaping data per page | A BFF on App Service or Functions behind APIM |
| Apollo Server or Hasura | APIM synthetic GraphQL with resolvers |
| The `cors()` middleware in Express | APIM's `cors` policy, or same origin through Front Door |
| A forced-update flag in Firebase Remote Config | Minimum version in App Configuration, served by the BFF |
| Stripe's `Idempotency-Key` header | The same header on your own API |

## Guiding your team

> [!TEAM]
> In a design review for anything a client calls, ask:
>
> 1. **Which client is this endpoint for, and who owns it?** A BFF without one owner drifts back into a general API.
> 2. **Does this change break any installed app version?** If it does, it is a new version, not a revision.
> 3. **What is the oldest version we serve, and why?** Retire versions by usage data, not guesswork.
> 4. **What happens if this request arrives twice?** Mobile networks retry, so every `POST` needs an idempotency key.
> 5. **What does this screen do with no signal?** Decide per feature: cached, queued or online-only.

## Key takeaways

- Clients need more than an API: delivery, sign-in, push, real-time, files and release, in lessons 11.2-11.7.
- A backend for frontend is a thin, client-owned API that turns many round trips into one. Use it when clients really differ.
- APIM keeps tokens, limits and routing; domain APIs keep business rules; the BFF keeps client shaping and old contracts.
- Any rename, removal or type change is a new API version, kept until usage data says it can go.
- Ship a minimum-version check in the first release: it only works in apps that contain it.
- Offline-first with optimistic UI needs idempotency keys, so retries never place a second order.
