## Why this matters

> [!SCENARIO] Twelve thousand product images and one expired link
> Product images for the shop live on the API server's disk. On [App Service](gl:app-service) that disk is shared and slow ([lesson 2.2](lesson:2.2)), so Ana wants the React app to upload straight to a [storage account](gl:storage-account) and never send a 4 MB JPEG through the Node API again.
>
> Dev has 6 TB of old file-server backups to bring along and finance wants them "somewhere cheap". And last Tuesday the React Native app stopped loading images at 09:00 sharp: a contractor had put a signed URL in the mobile build with a one-year expiry, a year ago.
>
> Priya needs one decision on how the shop stores files, and a team that understands the four services hiding behind one resource.

## One account, four services

A **storage account** is a container resource, not a service. Inside it sit four services sharing a name, a region, a redundancy setting and a bill.

| Service | What it holds | Use it for | Not for |
|---|---|---|---|
| **[Blob storage](gl:blob-storage)** | Objects of any size in flat **[containers](gl:storage-container)** | Images, documents, backups, logs, static assets | Anything needing a file system or locking |
| **[Azure Files](gl:azure-files)** | SMB and NFS file shares | [Lift-and-shift](gl:lift-and-shift) of a file server, apps that need a drive letter | High-throughput app data |
| **[Queue storage](gl:queue-storage)** | Messages up to 64 KB | Simple decoupling: "resize this image later" | Ordering, topics, dead-lettering - that is Service Bus ([Module 5](module:5)) |
| **[Table storage](gl:table-storage)** | Schemaless rows keyed by partition and row key | Cheap key-value lookups | Joins, secondary indexes, ad-hoc queries |

Blobs are the one you will use most. A **[block blob](gl:block-blob)** is uploaded in blocks and can reach around 190 TiB; page blobs back VM disks; append blobs suit logs. ==Blob storage is an object store: a flat key space with slashes in the names, not a file system with directories.==

## Kinds, redundancy and tiers

**Account kind.** **Standard general-purpose v2** is the default: HDD-backed, all four services, every redundancy option and access tier. **Premium** accounts are SSD-backed and single-purpose - premium block blobs for low-latency, transaction-heavy work, or premium file shares for a lifted file server that needs steady SMB performance. Premium costs several times more per GB but far less per operation.

**[Redundancy](gl:storage-redundancy)** is set per account and decides what a failure can take from you.

| Option | Copies | Survives | Watch out |
|---|---|---|---|
| **LRS** | 3 in one data centre | Disk and rack failures | A data-centre outage means downtime, maybe loss |
| **ZRS** | 3 across [availability zones](gl:availability-zone) | Loss of a data centre | About 25% dearer; not in every region |
| **GRS** | LRS plus 3 in the [region pair](gl:region-pair) | Regional disaster | Async copy ([RPO](gl:rpo) of minutes); secondary unreadable until failover |
| **GZRS** | ZRS plus 3 in the pair | Both of the above | Roughly double LRS |
| **RA-GRS / RA-GZRS** | As above, secondary readable | Reads during a regional outage | Only if the app tries the secondary endpoint |

For the shop, ZRS in UK South is the production default; GZRS only where losing the region for a day is a real business event. A failover is something *you* initiate and it breaks the pairing until you reconfigure it, so rehearse it ([lesson 3.6](lesson:3.6)).

**[Access tiers](gl:access-tier)** are set per blob (or as the account default) and trade storage price for access price.

| Tier | Roughly, per GB-month | Retrieval | Minimum stay | The catch |
|---|---|---|---|---|
| **Hot** | $0.018 | Free | None | Highest storage price |
| **Cool** | $0.01 | Per GB | 30 days | Reads cost extra |
| **Cold** | $0.0036 | Per GB, higher | 90 days | Reads cost more again |
| **Archive** | $0.002 | Per GB, highest | 180 days | **Offline** - rehydration takes hours, up to 15 |

> [!WARNING] The archive surprise
> Archive is cheap because the data is offline. A "quick restore" of a 6 TB backup set means a rehydration request, hours of waiting and a retrieval bill; delete before day 180 and you pay the remaining days as an **early-deletion fee**. Archive is for data you expect never to read. Everything else goes to cool or cold.

You do not re-tier blobs by hand. A **[lifecycle management policy](gl:lifecycle-management-policy)** does it by rule: cool 30 days after last modification, archive at 180, delete after seven years. Set it on day one.

**[Hierarchical namespace](gl:hierarchical-namespace)** gives containers real directories and POSIX permissions - this is **Data Lake Storage Gen2**, the foundation for Synapse, Databricks and Microsoft Fabric. Enable it for analytics accounts; leave it off for the shop's images, because it changes which features are available and cannot be switched off again.

## Who gets in

Three doors, in rising order of quality:

1. **[Account keys](gl:storage-account-key)** - two root passwords for every service and operation in the account. Rotate them, and in production **disable shared-key access** so they stop working at all.
2. **[Shared access signatures](gl:shared-access-signature)** - a signed URL granting specific permissions on a specific blob or container until a specific time. A **user delegation SAS** is signed with an Entra identity instead of a key: use that one, keep expiries to minutes, and issue them from the API on demand, never from a build.
3. **[Microsoft Entra ID](gl:microsoft-entra-id) with [RBAC](gl:role-based-access-control)** - a [managed identity](gl:managed-identity) holding **Storage Blob Data Contributor** on one container. No secret anywhere. Data-plane roles are separate: Owner on the resource does not let you read a blob.

The network is the fourth door. Every endpoint is public by default, guarded only by the doors above. A **private endpoint** gives the account an address inside your virtual network so you can close the public one; [lesson 4.3](lesson:4.3) covers it.

## In practice

Create one general-purpose v2 account per workload and environment (`stshopprod`, `stshopdev`): ZRS, hot by default, anonymous blob access **off**, shared-key access **off**, [soft delete](gl:soft-delete) on, and a lifecycle policy. Images and backups get separate accounts - different redundancy, different tiers, different blast radius.

**What it costs.** Three meters: capacity per GB-month (the $0.018 hot LRS anchor), operations (fractions of a cent per 10,000, dearer in cooler tiers) and [egress](gl:egress) to the internet after the first 100 GB a month, roughly $0.08 per GB. The shop's 500 GB of images costs about $10 a month to store; serving them without a CDN could cost ten times that in egress.

**What breaks.**

- **Public access left on.** A container marked "public read" is found by a scan bot within hours. Keep it off at the account level and put a CDN in front of genuinely public content.
- **The SAS in the mobile build.** It expires, the app dies, and the fix is an app-store release. Issue SAS from the API, minutes long.
- **Archive as a backup target.** See the warning above.
- **429 throttling.** A standard account targets around 20,000 requests a second; above that you get `429 Too Many Requests`. Retry with back-off ([transient faults](gl:transient-fault)), spread hot prefixes, or split accounts.

> [!TIP] Local development
> ![Storage Explorer](az:storage-explorer) **[Storage Explorer](gl:storage-explorer)** is the free desktop client for browsing, uploading and generating SAS tokens. ![Azurite](az:azurite) **Azurite** is the local emulator (`npm install -g azurite`), so the Node API and its tests run against blobs, queues and tables with no Azure account at all.

## Map it to what you know

| You already know | The Azure equivalent |
|---|---|
| Amazon S3, or any [object store](gl:object-storage) with URL keys | Blob storage: containers instead of buckets |
| The office file server with a mapped drive | Azure Files over SMB, mounted from a VM or on-premises |
| A SQL Server table with one clustered key and no joins | Table storage: partition key plus row key, nothing else indexed |
| A `jobs` table you poll | Queue storage; Service Bus when you need topics, ordering or dead-lettering |
| A pre-signed S3 URL | A shared access signature |
| The `sa` login on SQL Server | The storage account key - and the same reason to disable it |

## Guiding your team

> [!TEAM]
> In the design review, ask:
>
> 1. **Which of the four services, and why not blobs?** Blobs are the default; Files and Tables need a reason.
> 2. **What redundancy, and what would we do in a regional failover?** If nobody can answer the second half, GRS is buying comfort, not recovery.
> 3. **Where is the lifecycle policy?** Without one the account becomes a hot-tier bill for data nobody reads.
> 4. **How does the app authenticate?** The answer contains "managed identity" or "user delegation SAS", never "the key in the config".
> 5. **Is anything public, and is a CDN in front of it?** Public without a CDN is a security problem and an egress problem.

## Key takeaways

- A storage account holds four services: blobs for objects, Files for SMB/NFS shares, Queues for simple messages, Tables for cheap key-value rows. Blobs are the default.
- Standard GPv2 is the normal kind; Premium is SSD-backed and single-purpose.
- LRS survives a rack, ZRS a data centre, GRS/GZRS a region - but geo copies are asynchronous and failover is yours to plan and rehearse.
- Hot, cool, cold and archive trade storage price for access price; archive is offline, takes hours to rehydrate and charges early-deletion fees. Let a lifecycle policy move data.
- Disable account keys. Use managed identity with data-plane RBAC roles, and short-lived user delegation SAS issued by the API.
- The bill is capacity plus operations plus egress; a CDN in front of public blobs usually cuts the largest of the three.
