## Why this matters

> [!SCENARIO] Three platforms in one week
> On Monday Marta, the new data scientist, asks for Azure Databricks. She used it at her last job, and she wants it for a churn model. On Wednesday Northline signs the deal to buy Fellside Outdoor, whose reporting runs on an Azure Synapse dedicated SQL pool with 180 stored procedures. On Friday the CTO comes back from a conference and asks whether Northline should "do data mesh".
>
> Each request makes sense on its own. Together they would give Tom's team of four three platforms, three bills, three catalogs and three sets of skills, all to serve one set of reports.
>
> Priya wants one framework that gives the same answer whoever asks, and that says what would have to change for the answer to change.

This is the module's arbitration, in the style of [lesson 2.7](lesson:2.7) and [lesson 3.7](lesson:3.7): one tree, questions in order, and a script for the design review.

==Default to Fabric for a Microsoft-centred team; add Databricks only for a named need, and keep Synapse only because it is already there.==

| # | Ask | If yes | Why it sits here |
|---|---|---|---|
| 1 | Is this reporting and analytics for a team that runs Microsoft 365, SQL Server skills and Power BI? | [Microsoft Fabric](gl:microsoft-fabric) | One capacity, one lake, one catalog, and Power BI on [Direct Lake](gl:direct-lake). Most teams stop here. |
| 2 | Is there a named need Fabric does not meet: Spark-heavy engineering at scale, MLOps as the main workload, more than one cloud, or a team already fluent in Databricks? | [Azure Databricks](gl:azure-databricks), usually beside Fabric | Each is a real reason. "The data scientist prefers it" is not one on its own. |
| 3 | Is there already a Synapse estate? | Keep [Azure Synapse Analytics](gl:azure-synapse-analytics) running and plan a phased move | A working warehouse is not an emergency. Moving it is a project. |
| 4 | Do several business domains each have their own data engineers, and is the central team the bottleneck? | A [data mesh](gl:data-mesh), on whichever platform you chose | It is an organisational choice. Without the people, it is just more workspaces. |

## The three platforms side by side

| | Fabric | Azure Databricks | Synapse |
|---|---|---|---|
| **Best for** | Microsoft-centred BI and analytics | Spark engineering, ML and MLOps, multicloud | Existing warehouses |
| **You pay for** | A [capacity](gl:fabric-capacity) per hour (pausable), plus OneLake storage | DBUs, plus VMs on classic compute; serverless bundles both | [Dedicated SQL pool](gl:dedicated-sql-pool) per DWU-hour (pausable); [serverless SQL](gl:serverless-sql-pool) per TB processed |
| **Governance** | OneLake catalog, plus Purview | [Unity Catalog](gl:unity-catalog), plus Purview | Purview |
| **Watch out for** | One capacity shared by everyone ([lesson 10.2](lesson:10.2)) | A second bill, a second catalog, cluster sprawl | New capabilities are built for Fabric |

**Synapse, stated accurately.** As of October 2026 Microsoft has announced no retirement date for Synapse as a whole. It is still supported, and existing workspaces keep running. But the new capabilities, such as Direct Lake, [mirroring](gl:mirroring) and Copilot, are built in Fabric, and Microsoft's migration tooling points one way. The Migration Assistant for Fabric Data Warehouse is generally available and moves dedicated SQL pool schemas and code. A Spark migration assistant is in preview. One part has already gone: Synapse Data Explorer, a preview, retired in October 2025.

**Databricks, stated accurately.** All Azure Databricks workspaces are now on the Premium tier. The Standard tier was upgraded automatically on 1 October 2026. New workspaces get Unity Catalog by default, and serverless compute for notebooks and jobs requires it.

**Unity Catalog beside Purview.** Unity Catalog governs *inside* Databricks: a `catalog.schema.table` namespace, grants, row filters and column masks, lineage and audit for everything Databricks touches. [Purview](gl:microsoft-purview) catalogues *across* the estate. It scans Unity Catalog for metadata and lineage, alongside Fabric, Azure SQL and Fellside's Synapse. Enforce access where the data is queried, and keep one catalog where people look for it.

To use Databricks and Fabric together, Fabric can **mirror a Unity Catalog**. Only the catalog structure is copied. Fabric reads the Delta tables in place through [shortcuts](gl:onelake-shortcut), and Power BI uses them in Direct Lake mode. This is generally available. A Databricks team and a Fabric team can share one copy of the data.

## Data mesh is an organisational choice

A **data mesh** gives each business domain ownership of its data, published as **[data products](gl:data-product)** with an owner, a documented schema and quality promises. A self-serve platform supports the domains, and federated governance sets the shared rules. Like microservices in [lesson 9.1](lesson:9.1), it solves an organisational problem: many domain teams queuing behind one central data team. In exchange it needs data engineers in every domain and a mature platform.

==A data mesh needs domain teams that can own data; without them it is a central team with more workspaces.==

## In practice

**Marta wants Databricks.** Question 1 is yes. Question 2 finds one model and one data scientist, which is not yet a named need. The answer is Fabric notebooks and MLflow experiments on the gold tables. The line for the review: "Build the churn model in Fabric. Databricks comes in when we have several models in production that need MLOps, or Spark jobs our capacity cannot carry."

**Fellside's dedicated SQL pool.** Question 3 is yes. Keep it, pause it out of hours, and copy its gold tables into OneLake for group reporting; migrate next year. The line: "It works. We run both in parallel, compare the numbers, then switch the reports."

**The CTO's data mesh.** Question 4 finds one data team and no domain engineers, so not now. Name an owner for each data product, map Fabric domains to sales, marketing and wholesale, and certify the gold tables. The line: "We take the cheap half of mesh today and revisit when a domain hires its own engineers."

Write each answer as an [architecture decision record](gl:architecture-decision-record) with its trigger. **What breaks** is predictable: two platforms with no shared catalog, Spark clusters left running, and Fellside's migration treated as a lift and shift. Its `money` and `datetimeoffset` columns and its T-SQL need rework, which the assistant flags but does not fix for you.

## Map it to what you know

| You already decide | The analytics equivalent |
|---|---|
| Adding a separate OLAP server only when SQL Server cannot do the job | Adding Databricks beside Fabric only for a named need |
| A linked server to read another team's database in place | A mirrored Unity Catalog: Fabric reads Databricks tables through shortcuts, no copy |
| A legacy SSAS cube everyone depends on | A Synapse dedicated SQL pool: supported, but not where the investment goes |
| Running old and new reports side by side before cutover | Parallel run, then switch, in a Synapse migration |
| Microservices versus a modular monolith | Data mesh versus a central data team |

## Guiding your team

> [!TEAM]
> Five questions for an analytics platform proposal:
>
> 1. **Which question moved you off Fabric?** Name the need, because a preference is not a requirement.
> 2. **Where is the one catalog people search?** Two platforms without Purview means two truths.
> 3. **What does it cost idle and at peak?** Capacities, DBUs and DWUs all bill while nobody is looking.
> 4. **For an existing estate, what is the parallel-run and cutover plan?** A migration without one becomes a permanent second platform.
> 5. **Who in each domain would own a data product?** If nobody, it is not yet time for a mesh.

## Key takeaways

- Fabric is the default for Microsoft-centred teams: one capacity, OneLake, and Power BI on Direct Lake.
- Azure Databricks earns its place through a named need: Spark at scale, MLOps, multicloud or an existing team. Mirror its Unity Catalog into Fabric so both share one copy.
- Synapse has no announced retirement and is still supported, but new capabilities land in Fabric. Plan a phased migration with a parallel run.
- Unity Catalog governs inside Databricks; Purview catalogues across the whole estate.
- A data mesh is an organisational choice. It needs domain teams that can own data products.
