## Why this matters

> [!SCENARIO] Two days of clicking for a copy of production
> The DR drill in [lesson 6.5](lesson:6.5) needed a copy of the checkout stack in UK West. Dev built it by clicking through the portal with production open in another tab. It took two days, and the copy still differed: a TLS setting, an App Service plan size, a missing diagnostic setting.
>
> The same problem shows up everywhere. Dev and production have drifted apart in a dozen small ways. Someone exported ARM templates from the portal two years ago, and they are thousands of lines nobody dares touch. And an NSG rule opened during an incident is still open, because nothing records that it was ever changed.
>
> Priya wants every environment defined in code, reviewed like code, and rebuildable in minutes. The team has to choose between Bicep and Terraform.

## Desired state, in a file

[Infrastructure as code](gl:infrastructure-as-code) from [lesson 1.5](lesson:1.5) describes *what should exist*, not the steps to create it. The tool compares the file with what is actually there and makes the difference: create what is missing, change what differs, leave the rest alone. Running it twice changes nothing the second time. That property makes it safe to run on every merge.

It pays back four ways: environments are **reviewed** before they change, **repeatable** (UK West is a parameter, not two days of clicking), **consistent** (dev and production use the same code), and **auditable** (Git history says who changed what, and why).

## Bicep or Terraform

Both are declarative, both are mature, and both deploy through [Azure Resource Manager](gl:azure-resource-manager). They differ in scope and in how they track what they own.

| | [Bicep](gl:bicep) | [Terraform](gl:terraform) |
|---|---|---|
| Scope | Azure only | Azure, other clouds, and SaaS such as GitHub, Entra ID and Datadog |
| What it has deployed | Azure itself is the record; no state file | A **[state file](gl:terraform-state)** you must store, lock and protect |
| New Azure features | Available from day one | When the provider supports them; the `azapi` provider fills gaps |
| Preview of changes | **[What-if](gl:what-if)** | `terraform plan` |
| Removing what is no longer in code | Deployment stacks | Tracked through state |
| Licence | Open source (MIT) | Business Source Licence since 2023; OpenTofu is the open-source fork |

==Choose Bicep when the estate is Azure-only and you want no state to manage; choose Terraform when you also manage other clouds or SaaS, or the team already knows it - and do not mix both for the same resources.==

The shop chooses **Bicep** for its Azure estate. It uses a small amount of Terraform for something Bicep cannot reach: the GitHub organisation's repositories and branch rules from [lesson 7.2](lesson:7.2).

## Modules and parameters

Real templates are built from **[modules](gl:bicep-module)**: reusable pieces with inputs and outputs, versioned and shared. Rather than writing every module yourself, start from **[Azure Verified Modules](gl:azure-verified-modules)**: Microsoft-maintained Bicep and Terraform modules that already follow Well-Architected defaults for each service. One template plus a parameter file per environment gives every environment the same shape:

```bicep
// workloads/shop/main.bicep
param location string = resourceGroup().location
param environment string
param appServiceSku string

module plan 'br/public:avm/res/web/serverfarm:<version>' = {
  name: 'plan'
  params: {
    name: 'asp-shop-${environment}'
    location: location
    skuName: appServiceSku
    zoneRedundant: environment == 'prod'
  }
}

module api 'br/public:avm/res/web/site:<version>' = {
  name: 'api'
  params: {
    name: 'app-shop-api-${environment}'
    location: location
    kind: 'app,linux'
    serverFarmResourceId: plan.outputs.resourceId
    managedIdentities: { systemAssigned: true }
    httpsOnly: true
  }
}
```

```bicep
// workloads/shop/prod.bicepparam
using 'main.bicep'
param environment = 'prod'
param appServiceSku = 'P1v3'
```

The UK West copy is now `location: 'ukwest'` in a parameter file. It took 20 minutes, and it matches production exactly.

## Layers and pipelines

Not everything changes at the same pace, so split code into **layers** with separate deployments: a **platform** layer (hub network, Log Analytics, shared Key Vault, Front Door) owned by the platform team, and **workload** layers (the shop, the warehouse integration) owned by product teams. A mistake in a workload deployment then cannot touch the hub.

Infrastructure changes flow like code, through the pipelines of lessons [7.3](lesson:7.3) and [7.4](lesson:7.4):

1. A pull request runs `bicep lint` and a **what-if** against each environment, and posts the result as a PR comment. Reviewers see *"2 to modify, 0 to delete"* before approving.
2. Merging deploys to dev automatically, then to production after the environment's approval.
3. A **nightly what-if** against production reports any difference between code and reality.

## Drift: when reality and code disagree

**[Configuration drift](gl:configuration-drift)** is any difference between what the code says and what is actually deployed - usually a portal change made in a hurry. Handle it in three ways:

- **Prevent it**: engineers hold Reader on production, with Contributor through PIM for emergencies ([lesson 4.5](lesson:4.5)); Azure Policy denies the worst changes; deployment stacks can deny deletion or modification of resources they manage.
- **Detect it**: the nightly what-if (or `terraform plan`) alerts when production no longer matches `main`.
- **Resolve it**: either put the change into code, or re-apply the code to remove it. Never leave the two disagreeing.

## State, and the rename that deletes a database

Terraform's state file maps code to real resources. It lives in a remote backend: an Azure Storage account with blob-lease locking, versioning, private access and one state per environment and layer. It often contains secrets in plain text, so protect it like one. A state file on a laptop, or one used by two people at once, is how environments get corrupted.

One risk applies to both tools. Resources are identified by name, so **renaming a resource in code means deleting it and creating a new one**. For a database, that is data loss. That is why every pull request shows what-if or plan output, and why reviewers read every *Delete* line before approving.

## In practice

The shop's `shop-infra` repository holds `platform/` and `workloads/shop/`, built on Azure Verified Modules, with a parameter file per environment. Pull requests post what-if results for dev and production. Merges deploy to dev automatically and to production after approval, through a federated identity scoped to each resource group. The workload is managed as a deployment stack that denies deletion outside the pipeline. A nightly what-if alerts on drift. A small Terraform configuration manages the GitHub organisation's repositories and rulesets. The DR copy in UK West comes from the same code.

**What breaks.**

- **Exported templates treated as IaC.** Thousands of generated lines nobody can maintain. Rewrite with modules instead.
- **Portal hotfixes.** Drift, undone by the next deployment, or never recorded.
- **Unread plans.** A rename that deletes a database, approved because nobody read the *Delete* line.
- **Terraform state on a laptop.** Unlocked, unversioned, full of secrets.
- **One giant template.** Every change risks everything; split by layer and lifecycle.
- **Secrets in parameter files.** Reference Key Vault instead ([lesson 4.6](lesson:4.6)).

## Map it to what you know

| You already know | In infrastructure as code |
|---|---|
| SSDT or a `.dacpac`: declare the schema, let the tool diff | Bicep or Terraform: declare the resources, let the tool diff |
| A `Dockerfile` for an application | A template for an environment |
| AWS CloudFormation | ARM templates and Bicep |
| Pulumi in TypeScript | The same idea in a general-purpose language; also supported on Azure |
| Ansible or DSC configuring servers | Configuration management inside machines; IaC creates the machines and services themselves |

## Guiding your team

> [!TEAM]
> For every environment, ask:
>
> 1. **Could we rebuild it from the repository today, in another region?**
> 2. **Does every infrastructure pull request show what-if or plan output, and does someone read the deletes?**
> 3. **How would we know if production drifted from `main` last night?**
> 4. **Where does Terraform state live, who can read it, and is it locked?**
> 5. **Which modules are hand-written, and could Azure Verified Modules replace them?**

## Key takeaways

- Infrastructure as code declares desired state; the tool computes and applies the difference, so re-running is safe.
- Bicep suits Azure-only estates with no state to manage; Terraform suits multi-cloud and SaaS but needs a secured, locked, remote state file.
- Build from modules - ideally Azure Verified Modules - with one template and a parameter file per environment, split into platform and workload layers.
- Every pull request shows what-if or plan output; renames delete and recreate, so read every Delete line.
- Prevent drift with read-only production access and policy, detect it with a nightly what-if, and resolve it by bringing code and reality back together.
