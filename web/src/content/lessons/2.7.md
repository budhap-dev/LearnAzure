## Why this matters

> [!SCENARIO] Three proposals in one week
> On Monday the mobile team asks for [Azure Functions](gl:azure-functions) to send push notifications. On Wednesday a contractor's architecture pack proposes AKS for everything, "so we stay portable". On Friday Dev asks for "just a VM, like the one we have now - it is simpler".
>
> Each proposal is defensible on its own. Together they would give Priya's retailer three platforms, three deployment stories, three sets of alerts and three on-call rotations, for one shop that takes orders and emails receipts.
>
> Priya does not need to know which of the three is right before the meeting. She needs one framework that gives the same answer whoever asks the question, and that says out loud what would have to change for the answer to change.

Six lessons have each argued their own corner. This one is the arbitration: one tree, one order of questions, one cost comparison, and a script for the review.

The tree is a ladder, not a menu. Every step to the right adds something you have to run, watch and pay for whether or not anyone is using it. ==Start at the most managed option that can run the workload, and move down the ladder only when a named requirement forces it.==

## The six questions, in order

| # | Ask | If yes | Why it sits here |
|---|---|---|---|
| 1 | Is it static files with no server logic? | [Static Web Apps](gl:static-web-apps) ([lesson 2.3](lesson:2.3)) | The cheapest thing to run is a file on a CDN. A React build is files; hosting it on a web server is paying for a process that does nothing. |
| 2 | Is it event-driven, short-lived or [bursty](gl:bursty-workload) with idle periods? | [Functions](gl:azure-functions) ([lesson 2.4](lesson:2.4)) | Per-execution billing and [scale to zero](gl:scale-to-zero) beat any fixed plan when the average load is near nothing. Ask before you assume a server is needed. |
| 3 | Does it need a runtime or OS dependency the platform will not give you? | [Containers](gl:container) ([lesson 2.5](lesson:2.5)) | An unsupported runtime, a native library or a system package is a *named* reason to package your own image - not a general preference for Docker. |
| 4 | Is it a normal long-running web app or API? | [App Service](gl:app-service) ([lesson 2.2](lesson:2.2)), or [Container Apps](gl:azure-container-apps) if it is already an image | Most services are this. App Service is the shortest path from a Node or .NET repository to a URL with slots, autoscale and a certificate. |
| 5 | Do you genuinely need cluster-level control, and is there someone to own it? | [AKS](gl:kubernetes) ([lesson 2.6](lesson:2.6)) | Two conditions, both required. Without the second, the cluster becomes one person's hobby and then their leaving present. Otherwise Container Apps. |
| 6 | Is there a hard requirement only a machine satisfies? | [Virtual machine](gl:virtual-machine) ([lesson 2.1](lesson:2.1)) | Installer-only software, a licence tied to a machine, a GPU driver, a kernel-level agent. Legitimate, and the most expensive answer in staff time. |

Question 6 sits last but short-circuits everything: if the ERP only ships as a Windows installer, no amount of architecture makes it a function. The order of the other five is deliberate - each one is cheaper to operate than the one after it, so you never adopt an [operational burden](gl:operational-burden) you were not forced into.

## The cost shapes compared

Four billing shapes, and each is cheapest in a different place. Numbers are illustrative UK South list prices for orientation only; re-run the [pricing calculator](gl:azure-pricing-calculator) before you quote one.

| Shape | Used by | What drives the bill | Cheapest when | Expensive when |
|---|---|---|---|---|
| **Per execution** | Functions Consumption, Container Apps consumption | Executions x duration x memory | Idle most of the time; spiky traffic. Near £0 for a few thousand runs a day | Steady high volume, or long-running requests billed by the second all day |
| **Per instance-hour** | App Service plans, Functions Premium | Tier x instance count x hours, running or not | Predictable load. A B1 is ~£12/month, a P1v3 ~£75-90 | Empty or forgotten plans - [lesson 2.2](lesson:2.2) opens with a £120 plan holding nothing |
| **Per cluster node** | AKS | Node VMs x size x hours. The Kubernetes control plane itself is free | Many services sharing one well-packed cluster | Three D4s v5 nodes plus a system pool (~£550-700/month) hosting two small APIs at 8% utilisation |
| **Per VM** | Virtual machines, scale sets | Size x hours running, plus disks that bill even when [deallocated](gl:deallocation) | A licence you already own, or Spot and reservations on steady work | Anything left oversized, or stopped from inside the OS instead of deallocated |

The crossover is the part people miss. A [Consumption plan](gl:consumption-plan) is nearly free at low volume and becomes dear at high, sustained volume; a fixed plan is the reverse - painful when idle, excellent value when saturated. On [lesson 2.4](lesson:2.4)'s illustrative figures, five million calls a month cost a few pounds on Consumption against about £150 for two P1v3 instances, while 130 million calls at half a second each cost £400 or more - so the crossover sits somewhere in the tens of millions, and arrives sooner when executions are slow. A cluster is different again: it charges for nodes whether or not your pods use them, so an under-packed cluster wastes money continuously and silently.

## The six options side by side

| Option | You manage | Scales to zero | Cold start |
|---|---|---|---|
| Static Web Apps | The build and the config file | n/a - it is files | None |
| Functions (Consumption) | Code and triggers | Yes | Seconds; mitigable |
| App Service | Code and app settings | No | Only after a restart |
| Container Apps | Code and the image | Yes, optionally | Seconds when at zero |
| AKS | Nodes, upgrades, add-ons, YAML | No - nodes stay | Only on pod start |
| Virtual machine | The whole OS and everything on it | No | n/a - always on |

| Option | Rough floor / month | Time to first deploy | Ops burden | [Portability](gl:portability) |
|---|---|---|---|---|
| Static Web Apps | £0 Free, ~£7-8 Standard | Minutes | Almost none | High - it is a build output |
| Functions (Consumption) | ~£0 idle | Minutes | Low | Moderate - triggers and bindings are Azure-shaped |
| App Service | ~£12 B1, ~£75-90 P1v3 | An hour | Low | High - the app is unchanged; the config is not |
| Container Apps | ~£0 idle inside the free grant, ~£25-30 for one always-on replica | Half a day, with a registry | Low to moderate | High - the image runs anywhere |
| AKS | ~£550-700 for a modest node pool | Days to weeks | High and permanent | Highest, and you pay for it every month |
| Virtual machine | ~£70+ for a small VM, more with Premium disks | Hours, then forever | Highest | Portable image, but you carry the OS with it |

Read the last two columns together. AKS buys the most [portability](gl:portability) and charges for it monthly; a VM looks portable but you take the patching, hardening and monitoring with you. Worrying about [vendor lock-in](gl:vendor-lock-in) is reasonable; paying a cluster's running cost for years to insure against a migration nobody has budgeted is not.

## Three worked examples

| Workload | Question path | Answer | The line you say in the review |
|---|---|---|---|
| Priya's shop: React front end, Node API, SQL | Q1 yes for the front end; the API is no to 1-3, yes at 4 | Static Web Apps + App Service (Linux) + Azure SQL Database | "The bundle is files, so it goes on a CDN. The API is a normal long-running API, so it goes on a plan we can size and slot-swap." |
| Nightly reconciliation, 20 minutes, once a day | Q1 no, Q2 yes - scheduled and idle 23.9 hours a day | Functions on a timer trigger, on a plan whose timeout covers 20 minutes | "It runs once a night, so we pay per run. Consumption caps out at ten minutes, so this one needs Flex Consumption or Premium." |
| Image service needing a native binary the platform will not install | Q1 no, Q2 no, Q3 yes - a named OS dependency | Container Apps, image in Azure Container Registry, pinned by digest | "The dependency forces an image, not a cluster. Container Apps runs the image, scales it and costs nothing when idle." |

Notice how each answer names the requirement that moved it down the ladder. A proposal that cannot name one has not finished its argument.

## When to revisit

Compute choices are reversible, at a cost - usually a sprint, not a rewrite. Write the triggers down when you make the decision, so revisiting is a scheduled review rather than an argument.

- **The bill crosses a threshold you set in advance.** Per-execution billing that passed the cost of a fixed plan is the classic. Set a [budget](gl:budget) alert at the crossover figure on day one.
- **You hit a scale-out or platform limit.** Instance caps, a timeout you cannot raise, a request size the platform refuses.
- **A dependency the platform will not run** appears - a native library, an unsupported runtime version, a driver.
- **The team grows past what one platform owner can support**, or the person who understood the cluster leaves.
- **A portability requirement becomes real and funded** - a customer contract or a regulator, not a preference.
- **The workload's shape changes.** A [steady-state](gl:steady-state-workload) service that used to be bursty should not still be billed per execution.

## Map it to what you know

| You already decide | The Azure equivalent |
|---|---|
| Static export versus a Node server for a React site | Static Web Apps versus App Service |
| A cron job versus a daemon that polls | Functions on a timer versus an always-on worker |
| Installing a native npm module that needs build tools | The question that forces a container image |
| `npm start` on a PaaS host versus your own Dockerfile | App Service versus Container Apps |
| Running your own Nginx, PM2 and log rotation | AKS or a VM: you own the platform, not just the app |
| Choosing a monolith before you need services | Choosing App Service before you need a cluster |

## Guiding your team

> [!TEAM]
> Five questions that make a compute proposal justify itself:
>
> 1. **Which question in the tree moved you here?** Name the requirement, not the preference. "The team knows Kubernetes" is not a requirement.
> 2. **What does it cost at zero traffic, and at ten times today's traffic?** Two numbers, or the proposal is not finished.
> 3. **Who patches, upgrades and gets paged for it?** Name a person. If the name is "we all do", it is nobody.
> 4. **What is the cheapest option we rejected, and why?** There should be an answer, and it should be a sentence long.
> 5. **What would make us change this decision?** Write the trigger and the threshold into the design document today.

## Key takeaways

- Work down the ladder: Static Web Apps, Functions, App Service or Container Apps, AKS, virtual machines. Move a step only when a named requirement forces it.
- Six questions, in order: static files, event-driven, an OS or runtime dependency, a normal web app, cluster control with an owner, a hard machine requirement.
- Per-execution billing is near-free when idle and dear at steady high volume; a fixed plan is the reverse; a cluster charges for nodes whether or not pods use them.
- Container Apps is the default for containerised services; AKS needs both a real requirement and a named owner.
- Portability has a monthly price. Buy it when a funded requirement exists, not as insurance against a migration nobody has planned.
- Record the triggers - a cost threshold, a platform limit, a new dependency, a team change - that should reopen the decision.
