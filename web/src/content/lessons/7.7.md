## Why this matters

> [!SCENARIO] Forty minutes to undo a Tuesday release
> The new checkout went out at 14:00 on a Tuesday, to everyone at once. Within minutes, 8% of card payments were failing for one card type. Rolling back meant finding the previous commit, rebuilding it and redeploying it, and that took forty minutes, while shoppers kept hitting the bug.
>
> Black Friday is six weeks away. The CTO's request is simple: releases should be boring - small, reversible, and seen by a few shoppers before they are seen by all of them.

## Deploying is not releasing

**Deploying** puts new code on servers. **Releasing** lets users experience it. When the two are the same moment, every deployment is a bet on the whole user base. The strategies in this lesson separate them, so a new version can run, be tested and be watched before most people see it - and be withdrawn in seconds when something is wrong.

==Separate deploying from releasing: get new code running where few or no users see it, expose it gradually while watching the SLOs, and make going back faster than going forward.==

## The strategies

| Strategy | How it works | Going back | On Azure |
|---|---|---|---|
| **Big bang** | Replace everything at once | Redeploy the old version - slow | What the Tuesday release did |
| **[Rolling](gl:rolling-deployment)** | Replace instances a few at a time | Roll forward or back instance by instance | VM scale sets, AKS deployments, App Service with several instances |
| **[Blue-green](gl:blue-green-deployment)** | Run the new version alongside the old, then switch all traffic at once | Switch back - seconds | App Service **slot swap**; Container Apps revisions; Front Door origins |
| **[Canary](gl:canary-release)** | Send a small share of traffic to the new version, watch, then increase | Send the share back to zero | App Service traffic routing to a slot; Container Apps revision traffic weights; Front Door weighted origins |
| **[Ring-based](gl:ring-based-deployment)** | Release to groups in order: staff, early adopters, everyone | Stop at the current ring | Feature flag targeting; app-store staged rollouts |
| **Feature flags** | Deploy code switched off, then turn it on per audience | Flag off - instant | Azure App Configuration ([lesson 4.6](lesson:4.6)) |

These combine. The shop's API uses a slot (blue-green) with a canary share before the swap, and new features sit behind flags on top of that.

## Slots and swaps, done properly

A [deployment slot](gl:deployment-slot) ([lesson 2.2](lesson:2.2)) is a full running copy of the app. A swap works like this:

1. Deploy the new artefact to the **staging** slot, which runs with production's configuration apart from the [slot settings](gl:slot-setting) that stay put.
2. Warm it up and run **smoke tests** against its URL ([lesson 7.8](lesson:7.8)).
3. Optionally route a small percentage of real traffic to it - App Service's traffic routing does this without any other service.
4. **Swap**: the staging slot's warmed-up instances become production. No cold start, no dropped requests.
5. The old version now sits in staging. **Swapping back is the rollback**, and it takes seconds.

Container Apps behaves similarly with **[revisions](gl:revision)** ([lesson 2.5](lesson:2.5)): each deployment creates a new immutable revision, traffic weights move between them, and rolling back is moving the weight back.

## Letting the metrics decide

A canary is only useful if something watches it. Compare the new version's error rate and 95th-percentile latency with the old version's, using Application Insights split by version ([lesson 6.3](lesson:6.3)). Turn that comparison into a **gate**: an Azure Monitor alert as an environment check in Azure Pipelines, or a custom deployment protection rule in GitHub. The rollout pauses or **[rolls back](gl:rollback)** automatically when the new version is worse. Make sure the canary gets enough traffic to judge. Five per cent of a quiet hour may be a few dozen requests, which proves nothing.

Feature flags add a finer control: a **[dark launch](gl:dark-launch)** deploys a feature switched off everywhere, turns it on for staff, then for 10% of shoppers, then for all. If it misbehaves, the flag is a kill switch that works without a deployment.

## The hard part: data

Code can be swapped back in seconds. Data cannot. If version 42 renames a column that version 41 reads, swapping back breaks production. Use **expand and contract** (also called *parallel change*):

1. **Expand**: add the new column or table, leaving the old one. Both versions work.
2. **Migrate**: deploy code that writes to both and reads the new one; backfill old rows.
3. **Contract**: once no running version needs the old column - releases later - remove it.

Every schema change must be compatible with the version before it, so a rollback never meets a database it does not understand. The same rule covers messages on Service Bus ([lesson 5.2](lesson:5.2)) and API contracts: mobile apps cannot be rolled back on shoppers' phones, so the API must keep serving the versions still installed ([lesson 5.5](lesson:5.5)).

## In practice

The shop's release path for the API: the pipeline deploys the artefact to the staging slot, runs smoke tests, then routes 5% of traffic to it for 30 minutes. An automated gate compares error rate and p95 with production. If they hold, the slots swap, and the previous version stays in staging for an instant swap-back. New features ship behind App Configuration flags and go to staff, then 10%, then everyone. The mobile app uses staged rollouts in both stores. Database changes follow expand and contract, one step per release.

The next checkout change went out on a Tuesday morning. A payment path failure showed up in the 5% canary within six minutes, and the canary was withdrawn in twenty seconds: 0.4% of checkouts affected for six minutes, instead of 8% for forty.

**What breaks.**

- **Swapping with the wrong settings.** A connection string that should have been a slot setting sends production traffic to the test database, or the reverse.
- **Incompatible database changes.** Rollback becomes impossible. Expand and contract, always.
- **Canaries too small to judge.** Size the share and duration so the comparison means something.
- **Flags that never leave.** Each one is a branch in the code; remove it once the feature is fully out.
- **Sticky sessions.** ARR affinity keeps some users on the old version after a swap; keep the API stateless ([lesson 3.4](lesson:3.4)).

## Map it to what you know

| You already know | In release strategies |
|---|---|
| Two server farms behind a load balancer, switched over at midnight | Blue-green, with a slot swap in seconds |
| IIS ARR weighted routing | App Service traffic routing, or Front Door weighted origins |
| LaunchDarkly | App Configuration feature flags with targeting |
| An app store's phased release | Ring-based deployment for mobile |
| A SQL migration script run during the release window | Expand and contract, spread across releases |

## Guiding your team

> [!TEAM]
> Before the next release, ask:
>
> 1. **How long does rolling back take - and have we timed it?**
> 2. **What share of users sees a new version first, and what metric decides whether it goes further?**
> 3. **Is this database change compatible with the previous version of the code?**
> 4. **Which slot settings must stay put, and are they marked?**
> 5. **Which feature flags are fully released and ready to remove?**

## Key takeaways

- Separate deploying from releasing: run new code where few people see it, expose it gradually, and make going back fast.
- Rolling replaces instances gradually; blue-green switches all at once with an instant switch back; canary sends a small share first; rings release audience by audience; feature flags switch behaviour without deploying.
- App Service slots give blue-green and canary on their own: deploy to staging, smoke test, route a share, swap, and swap back to roll back.
- Gate rollouts on SLO metrics comparing new and old versions, and roll back automatically when the new one is worse.
- Data does not roll back: use expand and contract so every schema, message and API change works with the previous version too.
