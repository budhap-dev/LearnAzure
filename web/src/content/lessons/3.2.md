## Why this matters

> [!SCENARIO] "Just put SQL Server on a VM - it's what we know"
> Priya's orders database is SQL Server 2019 on a box in the rack: 180 GB, a dozen SQL Agent jobs, a linked server to the warehouse system, and a reporting database that joins across to it with three-part names. Dev, the ops lead, wants SQL Server on an Azure VM because nothing would change. A contractor says [Azure SQL Database](gl:azure-sql-database), "obviously", then goes quiet when asked about the Agent jobs. Finance wants to know whether the SQL Server licences they already pay for count for anything. Cutover is in eight weeks.
>
> Three people, three different products, all called "Azure SQL". Priya has to pick one and defend it in a review.

**[Azure SQL](gl:azure-sql)** is the umbrella brand for three ways of running the SQL Server engine on Azure. Same engine, same T-SQL, very different amounts of control, compatibility and operational work.

## Three flavours, one engine

| | ![SQL VM](az:sql-vm) [SQL Server on VMs](gl:sql-server-on-azure-virtual-machines) | ![MI](az:sql-managed-instance) [Managed Instance](gl:azure-sql-managed-instance) | ![SQL DB](az:sql-database) SQL Database |
|---|---|---|---|
| Model | [IaaS](gl:iaas): a VM with SQL Server installed | [PaaS](gl:paas), scoped to an instance | PaaS, scoped to a database |
| Compatibility | 100% - it *is* SQL Server | Near 100%: Agent, cross-database queries, linked servers, CLR, Service Broker, restore from `.bak` | Database surface only: no Agent, no cross-database queries, no linked servers, no CLR |
| Who patches | You: OS, engine, backups | Microsoft | Microsoft |
| Network | Your VNet | Your VNet, own subnet | Public endpoint with firewall, or private endpoint |
| Provisioning | Minutes | Minutes to hours; some resizes take hours | Seconds |
| Starting size | Any VM size | Around 4 vCores, roughly $700/month list | 5 DTUs for about $5/month |
| Pick it when | You can name the feature only a VM gives you: FILESTREAM, an exact patch level, SSRS on the box, third-party agents | Lifting an instance-shaped estate with Agent jobs and cross-db dependencies, without owning an OS | New apps and single databases; the default for anything you can make fit |

==Default to SQL Database, step up to Managed Instance when instance-level features are genuinely load-bearing, and use a VM only when you can name the feature that forces it.==

Priya's estate has Agent jobs, a linked server and cross-database queries. Each has a SQL Database workaround - Elastic Jobs or a timer-triggered Function for Agent, Elastic Query for the joins - but three workarounds in eight weeks is the risk. Managed Instance is her honest first move. [Azure Hybrid Benefit](gl:azure-hybrid-benefit) applies to all three flavours, so Finance's licences do count.

## Paying for it: DTU, vCore and the tiers

Two purchasing models, because the product is old enough to have had a first attempt:

- **[DTU](gl:dtu)** bundles CPU, memory and I/O into one number. Basic is 5 DTUs for about $5/month; Standard runs from S0 (10 DTUs, about $15/month) to S3 (100 DTUs, about $150/month). Cheap at the bottom, opaque when it throttles: the meter says "100% DTU" and you cannot buy just more I/O.
- **[vCore](gl:vcore)** prices compute, memory and storage separately, takes Hybrid Benefit and [reservations](gl:reservation), and is what Microsoft steers you to. A 2-vCore General Purpose database is roughly $370/month list; Hybrid Benefit strips the licence element out of that.

Within vCore, the **[service tier](gl:service-tier)** decides the architecture underneath:

| Tier | Underneath | Use it for | Cost shape |
|---|---|---|---|
| **General Purpose** | Stateless compute over remote premium storage; single-digit ms I/O | Most OLTP; the default | Baseline |
| **Business Critical** | Local SSD, three replicas in an Always On-style cluster, one readable | Latency-sensitive or write-heavy work that also wants a readable secondary | Roughly 2.5-3x General Purpose |
| **[Hyperscale](gl:hyperscale)** | Page servers and a log service; up to around 128 TB; restores in minutes regardless of size | Databases that outgrow 4 TB, or need several named read replicas | Between the two; storage billed per GB |

Two more dials sit beside the tiers:

- The **[serverless compute tier](gl:serverless-compute-tier)** bills per vCore-second between a minimum and maximum you set, and **auto-pauses** after an hour idle by default, when you pay for storage only. Right for dev, test and the internal tool used twice a day. The first connection after a pause takes about a minute and fails until the database resumes.
- An **[elastic pool](gl:elastic-pool)** shares a budget of vCores or eDTUs across many databases. Fifty tenant databases that peak at different times cost a fraction of fifty sized one by one - and nothing at all is saved if they peak together.

> [!WARNING] Sizing mistakes that recur every quarter
> Dev databases on Business Critical "to match prod", at three times the price for no benefit. An S0 pinned at 100% DTU with nobody able to say whether it was CPU or I/O. A pool sized for the sum of every database's peak, which is the one case where pooling saves nothing.

## Availability: what your Always On knowledge becomes

PaaS Azure SQL has [high availability](gl:high-availability) built in and you cannot switch it off. General Purpose reattaches your remote storage to fresh compute when a node fails; Business Critical runs the three-replica cluster you would have built yourself and fails over in seconds. That cluster also gives you **[read scale-out](gl:read-scale-out)**: add `ApplicationIntent=ReadOnly` to the connection string and reads go to a replica, exactly as with a readable AG secondary.

Azure SQL Database publishes a 99.99% [SLA](gl:sla). **[Zone redundancy](gl:zone-redundant)** is a checkbox on General Purpose and Business Critical in most regions, UK South included, that spreads the replicas across [availability zones](gl:availability-zone) so a data-centre failure is a blip rather than an outage. Tick it for production; it costs little on General Purpose.

Across regions you have two related tools. **[Active geo-replication](gl:active-geo-replication)** is asynchronous log shipping done for you: up to four readable secondaries in other regions, failed over one database at a time, after which you repoint connection strings yourself. A **[failover group](gl:failover-group)** wraps a set of databases in one listener DNS name and fails them over together, automatically after a grace period (one hour by default), normally to the [region pair](gl:region-pair). Managed Instance supports failover groups but not active geo-replication.

## In practice

You create a **logical server** (a name, a region, an admin) and put databases on it; the server is a management boundary, not a machine. Then the settings that matter:

| Concern | Default | What to do |
|---|---|---|
| Encryption at rest | **[TDE](gl:transparent-data-encryption)** on, service-managed key | Leave it; bring a [Key Vault](gl:key-vault) key only if compliance asks |
| Authentication | SQL logins available | Set an [Entra ID](gl:microsoft-entra-id) admin, connect the API with a [managed identity](gl:managed-identity), then switch the server to Entra-only so there is no password to leak |
| Network | Public endpoint, firewall closed | IP rules for now; a private endpoint for production ([lesson 4.3](lesson:4.3)). "Allow Azure services" means *any* Azure customer - avoid it |
| Threats | Off | Defender for SQL: vulnerability scans and anomaly alerts for around $15 per server per month |
| Backups | Automatic: weekly full, differential every 12 hours, log every few minutes | [Point-in-time restore](gl:point-in-time-restore) keeps only **7 days** by default (up to 35); long-term retention is off until you configure it - [lesson 3.6](lesson:3.6) |

What breaks, in the order teams meet it:

1. **DTU throttling.** Queries slow, the meter says 100%, and the fix is a tier change rather than an index. Start on vCore for anything you will have to explain.
2. **Per-tier limits.** Concurrent workers: 30 on Basic, about 200 on a 2-vCore General Purpose database; tempdb on General Purpose is roughly 32 GB per vCore. A Node connection pool sized for a big on-premises box can exhaust the worker limit on its own.
3. **[Transient faults](gl:transient-fault).** Failovers, resumes from pause and throttling all surface as dropped connections for a few seconds. Retry with back-off in the API; on PaaS SQL it is not optional.
4. **The cross-database query nobody knew about.** Grep for three-part names *before* choosing SQL Database.
5. **Managed Instance provisioning time.** Budget hours, not minutes.

## Map it to what you know

| You already run | On Azure SQL |
|---|---|
| An Always On availability group | Business Critical's internal cluster, or a failover group across regions; readable secondary via `ApplicationIntent=ReadOnly` |
| Log shipping to a DR site | Active geo-replication: asynchronous, readable, no restore jobs to babysit |
| SQL Agent jobs | Kept on Managed Instance and VMs; Elastic Jobs or a timer Function on SQL Database |
| SQL logins in a connection string | Entra ID and managed identity; the [connection string](gl:connection-string) has no secret |
| Nightly backup job plus a tape rotation | Automatic backups with short default retention; you configure long-term retention |
| A DBA sizing cores and RAM for a new box | vCore count and service tier, changed in minutes and billed by the hour |

## Guiding your team

> [!TEAM]
> Before anyone books the migration weekend, ask:
>
> 1. **Which flavour, and which instance-level feature justified it?** "It's what we know" is not a feature.
> 2. **Are there Agent jobs, linked servers or three-part names in the code?** Grep for them; the answer decides SQL Database versus Managed Instance.
> 3. **vCore with Hybrid Benefit for prod, serverless for dev, zone redundancy ticked?** Three settings that move the bill and the uptime more than any index will.
> 4. **Does the API retry, and does it use a managed identity?** No retry means every failover is an incident; a SQL login means a password in a config file.
> 5. **What is our backup retention, and has anyone tried a restore?** Seven days is the default, and it is shorter than most finance teams expect.

## Key takeaways

- Azure SQL is one engine sold three ways: SQL Database (PaaS, per database), Managed Instance (PaaS, near-100% compatible, own VNet) and SQL Server on a VM (IaaS, you patch). Default to SQL Database; step up only for a named reason.
- Buy on vCore for anything real; DTU is cheap and opaque. General Purpose is the default tier, Business Critical is for latency and readable replicas, Hyperscale is for size.
- Serverless with auto-pause for dev and test; elastic pools for many small databases with different peaks.
- HA is built in; zone redundancy is a checkbox; a failover group is your availability group across a region pair, with one listener name and asynchronous replication.
- TDE is on, Entra ID plus managed identity replaces SQL logins, and a private endpoint beats a firewall rule.
- Backups are automatic but retention is short by default, per-tier limits bite, and every PaaS database needs retry logic in the app.
