## Why this matters

> [!SCENARIO] Three engineers, three answers
> Priya's board has agreed: the retailer is moving to Azure. Now her team has to decide *how*. Dev, who ran the on-premises servers, wants four Azure virtual machines "so nothing changes". Ana, who builds the React front end and the Node API, wants "whatever means I never SSH into a box again". Tom from the data team wants SQL Server exactly as it is, because his backups and jobs are tuned to it.
>
> All three are describing a different point on the same spectrum. Priya needs a way to compare them that the board will understand: who does what, what it costs, and what the team gives up.

The spectrum is the **service model**, and the tool for comparing points on it is the **shared responsibility model**. Once you can draw the line between "Microsoft does this" and "we do this" for any service, most hosting arguments settle themselves.

## The four service models

Every cloud service hands some layers of the stack to the provider and keeps the rest with you. The models are just names for where the line sits.

| Model | You get | You run | Azure examples |
|---|---|---|---|
| **[IaaS](gl:iaas)** - infrastructure | A [virtual machine](gl:virtual-machine), disks, a network | Everything from the operating system up | ![VM](az:virtual-machine) Virtual Machines, virtual networks, managed disks |
| **[PaaS](gl:paas)** - platform | A place to run your code or data, with the OS and runtime patched for you | Your application and its data | ![App Service](az:app-service) [App Service](gl:app-service), [Azure SQL Database](gl:azure-sql-database), Container Apps |
| **[Serverless](gl:serverless)** - functions | Code that runs when triggered; nothing to size | Only the function and its data | ![Functions](az:function-apps) [Azure Functions](gl:azure-functions), Logic Apps |
| **[SaaS](gl:saas)** - software | A finished product you sign in to | Your users, settings and content | Microsoft 365, Dynamics 365, GitHub |

Serverless is really PaaS pushed to its limit: you do not choose a machine size at all, and the bill is per execution rather than per hour. It gets its own row because the cost model and the constraints are different enough to matter.

==A managed service is one where the provider owns the operating system, the runtime and the uptime, and you own only your code, your data and your configuration.==

That word - **[managed service](gl:managed-service)** - is the key idea in this lesson. The further right you go on the spectrum, the more is managed for you, and the less control you have over how.

## The shared responsibility line

The **[shared responsibility model](gl:shared-responsibility-model)** answers the question Priya's board will ask: "If we move, what are we still on the hook for?" Read each column top to bottom.

| Layer | On-premises | IaaS | PaaS | SaaS |
|---|---|---|---|---|
| Building, power, hardware | You | Microsoft | Microsoft | Microsoft |
| Network controls (firewalls, segmentation) | You | Shared | Shared | Microsoft |
| Operating system patching | You | **You** | Microsoft | Microsoft |
| Runtime (Node, .NET, SQL engine) | You | **You** | Microsoft | Microsoft |
| Application code | You | You | **You** | Microsoft |
| Data - classification, backup, who can see it | You | You | You | **You** |
| Identity and access | You | You | You | **You** |

Two rows never move: **data** and **identity** are always yours. Microsoft 365 will not decide which of your staff should see the payroll folder, and Azure SQL will not tell you whether a column is personal data. Everything else slides to Microsoft as you move right.

> [!WARNING] "Microsoft handles security" is only half true
> Microsoft secures the platform. You secure what you put on it: who has access, which ports are open, whether backups are tested. Breaches of cloud workloads are overwhelmingly caused by the customer half of the table.

- The **React front end** is a folder of built files. [Static Web Apps](gl:static-web-apps) serves it from a global edge, wires in a CI pipeline from GitHub, and costs almost nothing. There is no server to think about.
- The **Node API** goes to App Service: Microsoft patches Linux and Node, the team deploys code, and autoscale handles the Black Friday spike from [lesson 1.1](lesson:1.1). If the API were a handful of small endpoints with spiky traffic, Azure Functions would fit too.
- The **nightly stock-sync job** that used to be a Windows service becomes a timer-triggered Function. It runs for four minutes a night and is billed for four minutes a night.
- **SQL Server** becomes Azure SQL Database. Same T-SQL, same tooling, but Microsoft owns backups, patching and failover. Tom keeps his schema and loses his weekend maintenance windows.
- The **legacy ERP** that only ships as a Windows installer stays IaaS. Not every workload fits a managed service, and pretending otherwise is how migrations stall.

React Native apps follow the same pattern: the mobile app is the client, and the backend is almost always PaaS or serverless - an App Service or Functions API behind API Management, with push via Notification Hubs. Nobody runs a VM for a mobile backend unless something forces them to.

## In practice: the trade-offs

| Moving right on the spectrum | You gain | You give up |
|---|---|---|
| IaaS to PaaS | No OS patching, built-in scaling, deployment slots, backups | Root access, custom OS agents, unusual runtimes |
| PaaS to serverless | Pay per execution, scale to zero, no idle cost | Long-running processes, predictable latency (cold starts), some portability |
| Anything to SaaS | No engineering at all | Customisation beyond what the product allows |

Three things go wrong repeatedly:

1. **Cost model surprises.** A VM or an App Service plan bills per instance-hour whether busy or idle. Functions bill per execution and gigabyte-second. A chatty API doing 200 million calls a month can cost more on Functions than on a fixed App Service plan - measure before you assume "serverless is cheaper".
2. **Lock-in.** A Node API on App Service moves to any Linux host. A Function using Azure-specific triggers and bindings is a rewrite to move. Neither is wrong; it is a decision to make on purpose.
3. **Lift-and-shift that never shifts.** Teams go IaaS "for now" and stay there for years, paying for the patching they meant to leave behind. See [lift and shift](gl:lift-and-shift).

Containers deserve a mention because they sit awkwardly across the spectrum. A [container](gl:container) packages your app and its runtime, so *you* own the runtime patching again, but Container Apps or AKS manage the hosts. It is the right answer when you need PaaS-like operations for something App Service cannot run.

## Map it to what you know

| You already know | On Azure |
|---|---|
| The IIS or Nginx server you patched at 2 a.m. | App Service: Microsoft patches it, you deploy |
| The SQL Server you installed, licensed and backed up | Azure SQL Database: same engine, automated backups and failover |
| A cron job or Windows service running a worker | Azure Functions with a timer trigger, billed per run |
| `npm install` instead of writing the library yourself | Consuming a managed service instead of running one |
| Docker Compose on a dev box | Container Apps: same images, managed hosts |
| Office installed on every laptop | Microsoft 365: the SaaS end of the same spectrum |

## Guiding your team

> [!TEAM]
> When someone proposes a hosting model, ask:
>
> 1. **Who patches the operating system next month?** If the answer is "us", say IaaS out loud and make sure someone owns it.
> 2. **What does this need that App Service or Functions cannot do?** If nobody can name it, start with PaaS.
> 3. **Is the traffic spiky or steady?** Spiky favours per-execution billing; steady favours a fixed plan.
> 4. **What would moving this off Azure cost?** Decide the lock-in deliberately, not by accident.
> 5. **Which rows of the responsibility table are still ours?** Data and identity always are. Who owns them on your team?

> [!TIP] Exam link
> AZ-900 asks you to classify services as IaaS, PaaS or SaaS and to describe the shared responsibility model. The trick questions are always about the rows that never move: data, identity and endpoints stay with the customer in every model.

## Key takeaways

- IaaS gives you a machine, PaaS gives you a platform, serverless gives you a trigger, SaaS gives you a product. Each moves more of the stack to Microsoft.
- The shared responsibility model is a table: the further right, the less you run - but data and identity are always yours.
- A managed service is the key idea: Microsoft owns the OS, runtime and uptime; you own code, data and configuration.
- Per-instance billing suits steady load; per-execution billing suits spiky load. Measure, do not assume.
- Default to PaaS. Use IaaS only when something forces it, and name that reason.
