## Why this matters

> [!SCENARIO] The refresh that 404s
> Ana ships the shop's React front end from [lesson 1.8](lesson:1.8) to an App Service instance. It costs about £50 a month for a plan that serves files nobody executes. It is slow for the growing Bengaluru customer base, because every request crosses to UK South and back. The TLS certificate is renewed by hand each January, and last year somebody forgot for six hours.
>
> Then support raises a ticket: a customer bookmarks `/orders/4821`, comes back the next day and gets a 404. The route works when you click through the app and fails when you press refresh. Nothing is broken in React. The server simply has no file at that path.

Both problems have the same root: a built React app is being hosted as if it were a server application. ==A React or Vite build is a folder of files, so hosting it is a distribution problem, not a compute problem.== [Static Web Apps](gl:static-web-apps) is the Azure service that treats it that way.

## What "static" means here

`npm run build` produces a **[static site](gl:static-site)**: `index.html`, a few hashed JavaScript and CSS bundles, and your images. Nothing on the server executes. Every visitor gets byte-identical files, which is why they can be copied to hundreds of [points of presence](gl:point-of-presence) and served from whichever one is nearest ([lesson 1.3](lesson:1.3)).

That is the whole shift: instead of running a Node process in UK South and hoping Bengaluru is patient, you put the files near the user. The app is still dynamic; fetching the data is the API's job, not the host's.

You point the resource at a GitHub repository and a branch, and Azure commits a workflow file to that repo. After that the loop is ordinary: push, the workflow runs, the **[build preset](gl:build-preset)** (Oryx) recognises Vite, Create React App, Next.js, Angular or a plain folder, builds it and uploads the output. ## What you get without writing any code

| Feature | What it replaces |
|---|---|
| Global distribution | A CDN resource, an origin, and cache rules you tuned by hand |
| **[Free managed certificate](gl:free-managed-certificate)** | Let's Encrypt renewals, a calendar reminder, and the year somebody misses it |
| Custom domains | The same, but you still own the DNS records |
| **[Preview environments](gl:preview-environment)** | "Can you deploy this branch somewhere so design can look at it?" |
| Built-in authentication | An OAuth round trip you wrote against Entra ID, GitHub, Google or Apple |

Preview environments are the feature teams notice most: open a pull request and Azure builds it to a separate URL that lives until the PR closes, so reviewers click a link instead of running the branch locally. The built-in auth deserves a look too - sign-in, sign-out and a `/.auth/me` endpoint returning the user's identity and roles, wired to [Microsoft Entra ID](gl:microsoft-entra-id) with no auth library in your bundle. Enough for an internal admin console; not a full identity platform.

## Routing, and the 404 that started this

Ana's bookmark fails because of **[client-side routing](gl:client-side-routing)**: React Router invents paths that exist only in the browser's history API, and a file server has no file at `/orders/4821`. The fix is a **[navigation fallback](gl:navigation-fallback)** - serve `index.html` for any path that matches no real file and let React read the URL - declared in `staticwebapp.config.json` at the root of the app folder.

```json
{
  "navigationFallback": {
    "rewrite": "/index.html",
    "exclude": ["/assets/*", "/api/*", "*.{png,jpg,svg,webp}"]
  },
  "routes": [
    { "route": "/admin/*", "allowedRoles": ["admin"] },
    { "route": "/legacy-pricing", "redirect": "/pricing", "statusCode": 301 }
  ],
  "responseOverrides": {
    "401": { "redirect": "/.auth/login/aad", "statusCode": 302 }
  },
  "globalHeaders": { "cache-control": "no-store" },
  "mimeTypes": { ".webmanifest": "application/manifest+json" }
}
```

The `exclude` list matters: without it a missing image returns your whole HTML page with a 200, and you lose an afternoon wondering why the browser will not decode a PNG. The same file carries route rules, role-protected paths, custom headers and MIME types.

## The optional managed API

Static Web Apps can host an `/api` route backed by [Azure Functions](gl:azure-functions) from the same repository - **[managed functions](gl:managed-functions)**. No second resource, no CORS because it is the same origin, and the signed-in user's identity arrives in a header. For a contact form or a small admin endpoint it is hard to beat.

The limits are real: a subset of the Functions feature set, fewer runtime choices, no Durable Functions, no separate scaling. When you outgrow it, Standard lets you *bring your own* Functions app - a full resource linked to the site, keeping same-origin routing. Beyond that it is an ordinary API on [App Service](gl:app-service) ([lesson 2.2](lesson:2.2)) or Container Apps.

## Free versus Standard

Illustrative figures at the time of writing; check the pricing page before you quote them.

| | Free | Standard |
|---|---|---|
| [SLA](gl:sla) | None ([lesson 1.7](lesson:1.7)) | 99.95% |
| Price | £0 | ~£7-8 per app per month |
| Bandwidth | 100 GB/month per subscription | 100 GB included, then per GB |
| App size | 250 MB | 500 MB |
| Custom domains | 2 | 5 |
| Custom authentication, private endpoints, bring your own Functions | No | Yes |

Free is genuinely free and genuinely unsupported. Use it for dev, test and internal tools; put production on Standard, because "no SLA" is a bad sentence to say in an incident review.

## Choosing between the options

| Option | Pick it when | The deciding question |
|---|---|---|
| ![SWA](az:static-web-apps) Static Web Apps | A built front end plus a small or separate API | "Does anything need to run on the server per request?" |
| ![App Service](az:app-service) App Service | The same process must render pages or hold sessions | "Is there server code that must live with the HTML?" |
| ![Storage](az:storage-account) Storage account static website | Cheapest possible bucket, one region, no pipeline | "Do I care about latency, TLS renewal or CI?" |
| ![Front Door](az:front-door) Front Door + storage | You need a WAF, complex routing or multi-origin | "Do I need rules a CDN alone cannot express?" |

**Where React Native fits.** The mobile app is not hosted here; it ships through the App Store and Google Play. Static Web Apps hosts the React Native Web build, the marketing site and the admin console. The phone app is just another client of the same API, signing in the same way.

**What it is bad at.** Server-side rendering beyond what the framework preset supports; large media, which belongs in blob storage; anything needing a long-running process; per-request server logic beyond the managed API. If you are fighting the config file, you picked the wrong host.

## Map it to what you know

| You already do | On Static Web Apps |
|---|---|
| `npm run build` then drag `dist/` onto a host | `git push`; the generated workflow does both |
| Netlify or Vercel | The same model: build from Git, edge hosting, preview URLs, serverless functions |
| Putting a CDN in front of an origin | The **[edge cache](gl:edge-cache)** is the product, not an add-on |
| Renewing Let's Encrypt certificates | A managed certificate that renews itself |
| `try_files $uri /index.html` in nginx | `navigationFallback` in `staticwebapp.config.json` |
| Branch deploy previews | Preview environments, one per pull request |

## Guiding your team

> [!TEAM]
> In the review, ask:
>
> 1. **Does the front end need a server at all?** If the honest answer is no, an App Service plan for it is £50 a month of nothing.
> 2. **Is `staticwebapp.config.json` in the repo?** Without a navigation fallback, deep links will 404 in production and pass in dev.
> 3. **Free or Standard for production?** Decide deliberately; Free carries no SLA.
> 4. **Managed API or a real one?** Managed is perfect for small endpoints and a trap for a growing API.
> 5. **Who reviews preview environments?** They are only worth the build minutes if someone actually opens the link.

## Key takeaways

- A React or Vite build is a folder of files; hosting it is distribution, not compute.
- Azure generates the GitHub Actions workflow, detects the framework and deploys on every push.
- Free managed TLS certificates, custom domains, global edge delivery and per-pull-request preview environments come with the service.
- `navigationFallback` to `/index.html` is the fix for deep-link 404s in client-side-routed apps.
- The managed `/api` is same-origin, identity-aware and deliberately limited; bring your own Functions app when you outgrow it.
- Free has no SLA. React Native ships through the app stores; only its web build lives here.
