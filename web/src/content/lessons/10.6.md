## Why this matters

> [!SCENARIO] Forty reports, forty revenues
> Gold is built ([lesson 10.4](lesson:10.4)) and revenue is one column. Yet Tom counts forty Power BI reports, and each imports its own copy of the tables and writes its own measures. "Revenue YTD" exists in eleven versions; three still add VAT back. Every night forty refreshes queue on the capacity.
>
> Two requests make it worse. Four regional managers should see only their region, and today each region gets a copied report that someone forgets to update. And the wholesale team wants a dashboard inside the wholesale portal, the React app their fifty business customers use, showing each customer only their own orders. Those customers have no Power BI licences.
>
> Priya asks Tom for one model, secured once, that every report and the portal can use.

## The semantic model: define it once

**[Power BI](gl:power-bi)** has two layers that people blur. A report is the pages and visuals. A **[semantic model](gl:semantic-model)** (until 2023 called a dataset) sits underneath: tables, relationships, measures, hierarchies and security. Every visual is a query against a model.

Measures are written in **[DAX](gl:dax)**, a formula language over the model. `Net Revenue YTD` is one line of DAX, and its meaning should live in exactly one place.

Forty reports with forty models is **model sprawl**: forty refreshes, forty copies of the data, forty chances to define revenue differently. The fix is a **shared semantic model**:

- One `Sales` model over the gold [star schema](gl:star-schema), owned by Tom's team, with the agreed measures.
- Reports are **thin**: they connect live to the shared model and hold only visuals. Analysts need Build permission on the model to create them.
- The model is **endorsed as certified**, so people can find the one to trust.

==Put every business definition in a shared semantic model, and let reports hold only visuals.==

## Import, DirectQuery or Direct Lake

Each table in a model has a storage mode, the biggest performance and cost decision in Power BI.

| | **[Import mode](gl:import-mode)** | **[DirectQuery](gl:directquery)** | **[Direct Lake](gl:direct-lake)** |
|---|---|---|---|
| Where the data lives | Copied into the model's compressed in-memory store | Stays in the source; each visual sends it a query | Delta tables in [OneLake](gl:onelake), loaded into memory on demand |
| Freshness | As of the last refresh: 8 a day on Pro, 48 on a capacity | Live | Within seconds of gold changing, with automatic updates on; "refresh" only re-reads metadata |
| Speed | Fastest | As fast as the source | Close to Import |
| Licence | Any | Any | A Fabric capacity |
| Best for | Small models, non-Fabric sources, self-service | Data that must be live and cannot be copied | Large gold tables already in Fabric |

Direct Lake comes in two forms, and the difference matters:

- **Direct Lake on OneLake**, generally available since March 2026, reads Delta tables directly, can combine several Fabric items and can mix in Import tables. It never falls back. If a table breaks the capacity's guardrails, such as 300 million rows per table on an F8, refresh fails until the table is fixed.
- **Direct Lake on SQL endpoints** goes through one item's [SQL analytics endpoint](gl:sql-analytics-endpoint). For SQL views, SQL-level security or exceeded guardrails it **falls back to DirectQuery**: queries still work, slowly. A model property can turn fallback off, so failures are loud instead.

Never point DirectQuery at the production orders database. That is [lesson 10.1](lesson:10.1)'s Monday report with extra steps.

## Row-level security

**[Row-level security](gl:row-level-security)** (RLS) adds roles to the model. Each role has a DAX filter, such as `DimRegion[Region] = "North"`, and members. Make the members [Microsoft Entra ID](gl:microsoft-entra-id) security groups, not people: `sg-pbi-region-north` is maintained by HR's joiner and leaver process, not by Tom. Microsoft 365 groups are not supported.

One report now serves all four regions. Two traps: **RLS filters only Viewers**, so workspace Admins, Members and Contributors see everything; and a user in no role sees nothing. Use **Test as role**, then sign in as a real member.

With dozens of regions or customers, use **dynamic RLS** instead: one role that filters a mapping table by `USERPRINCIPALNAME()`.

## Licences and embedding

From [lesson 10.2](lesson:10.2): below F64, everyone who views Power BI content needs a paid licence. **[Power BI Pro](gl:power-bi-pro)** lists at about $14 per user per month and **Premium Per User** at about $24 (approximate list prices, paid yearly; they vary by region and agreement). PPU adds larger models and more refreshes, but only PPU users can open PPU content. From F64, free-licence viewers can read; authors always need Pro. On Northline's F8, the four managers need Pro too.

Embedding comes in two kinds:

| | Embed for your organisation | Embed for your customers |
|---|---|---|
| Also called | User owns data | App owns data |
| Who signs in | Staff, with their own Entra accounts | Your app, as a [service principal](gl:service-principal) |
| Viewer licences | Pro each, unless F64 or above | None |
| Needs | Licences | A capacity: an F SKU, or an A SKU from **[Power BI Embedded](gl:power-bi-embedded)** |
| Northline example | Reports inside the staff intranet or Teams | The wholesale portal |

For the portal, the pattern is:

1. An [app registration](gl:app-registration) for the Wholesale API, with a certificate in [Key Vault](gl:key-vault). A Power BI admin allows that service principal to use Power BI APIs, and it joins the workspace as a Member.
2. When a buyer opens the dashboard, the Node API checks who they are, then asks Power BI for an **embed token** for one report. The token carries an effective identity, the customer's account ID, and the RLS role.
3. The React app renders the report with Power BI's JavaScript client, using only that short-lived token.

==The browser never holds a Power BI credential; it gets one short-lived token for one report, already filtered to one customer.== Service principals cannot be RLS role members themselves, so the effective identity is what filters the rows.

## In practice

- **The model.** `Sales` in Direct Lake on OneLake over `wh_gold`, plus one Import table for finance's budget spreadsheet. Measures live in source control, and changes move through deployment pipelines.
- **The reports.** The forty become fourteen thin reports. Retiring the rest takes a quarter, because every report has a fan.
- **The portal.** Embedded reports draw on the same F8. Embedding has no per-viewer charge, but buyers' clicks are interactive load on the capacity that serves finance. Watch the capacity metrics in the first month, and plan a separate capacity if it bites. Free trial embed tokens are for development only. Because the model is Direct Lake, the API needs V2 embed tokens and the model a fixed-identity cloud connection.

**What breaks.** Fallback nobody notices on a SQL-endpoint model; a Contributor who "can't see RLS working"; a portal token requested without an effective identity, which shows a customer everyone's orders. Test that last one in the pipeline, not by eye.

| SSAS roles with DAX filters | Row-level security roles |

| An Excel pivot table on a cube | Analyze in Excel on the semantic model |

## Guiding your team

> [!TEAM]
> In a reporting review, ask:
>
> 1. **Which shared model does this report use?** A new model needs a reason, or it becomes the forty-first revenue.
> 2. **What storage mode, and what happens if Direct Lake cannot load a table?** Know whether it fails or quietly falls back to DirectQuery.
> 3. **Who is in each RLS role, and which group feeds it?** Groups follow joiners and leavers; named people do not.
> 4. **Who views this, and what licence does each viewer need?** Below F64, every internal viewer needs Pro.
> 5. **For anything embedded, who owns the data: the user or the app?** That decides licences, identity and whether a capacity is required.

## Key takeaways

- A semantic model holds tables, relationships, DAX measures and security. Share one, certify it, and keep reports thin.
- Import copies and refreshes, DirectQuery queries the source live, and Direct Lake reads Delta tables in OneLake at near-Import speed. Direct Lake on OneLake never falls back; on SQL endpoints it can fall back to DirectQuery.
- RLS filters rows by role, using Entra security groups or dynamic rules, and applies only to Viewers.
- Below F64 every viewer needs Pro. Embedding for staff uses their licences; embedding for customers needs a capacity and a service principal issuing per-customer embed tokens.
