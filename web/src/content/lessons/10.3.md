## Why this matters

> [!SCENARIO] Four hours of copying, every night
> Since Priya banned reporting on production ([lesson 10.1](lesson:10.1)), Tom has fed the new lakehouse the way he fed reporting servers for fifteen years: a nightly job that copies the whole orders database. It starts at 01:00 and takes four hours. On Tuesday it overran to 06:40, early checkouts queued behind its reads, and finance's dashboard showed Monday's numbers until lunch.
>
> Two more sources are waiting. Stock levels live in the ERP's SQL Server, on a rack at the distribution centre in Daventry, behind a firewall. Campaign results live in a marketing SaaS tool that only speaks a REST API.
>
> Tom needs each source copied once, then kept current by moving only what changed.

A full copy is the easiest load to build and the hardest to live with: it grows with the business, not with the change.

## Three ways in

Fabric has three ingestion tools. Choose by the source, not by habit.

| Tool | What it does | Best for | Watch out for |
|---|---|---|---|
| **[Mirroring](gl:mirroring)** | Keeps a near-real-time replica of a database in [OneLake](gl:onelake) as [Delta](gl:delta-lake) tables | Supported databases, copied as they are | No transformation; some data types and features block it |
| **Copy job, or a [pipeline](gl:data-pipeline) with a [copy activity](gl:copy-activity)** | Moves data on a schedule, in full or incrementally | Sources mirroring cannot reach | You own the schedule and the failures |
| **[Dataflow Gen2](gl:dataflow-gen2)** | Power Query in the browser: connect, clean, reshape, load | SaaS APIs, spreadsheets, small messy sources | Dearer per row than a copy |

**Mirroring** is the one to try first for a database. Pick the tables; Fabric takes a snapshot, then applies changes as often as every 15 seconds. It is generally available for Azure SQL Database and Managed Instance, SQL Server 2016 onwards, Cosmos DB, Azure Database for PostgreSQL, Snowflake, Oracle and BigQuery, among others; MySQL is in preview. Replication compute is free, and each [capacity unit](gl:capacity-unit) includes a terabyte of free mirroring storage. Queries are charged as normal.

==If a source can be mirrored, mirror it; build a pipeline only for the sources that cannot.==

A **data pipeline** orchestrates: activities with parameters, branches, retries and a schedule. A **copy activity** inside it moves data. The **Copy job** is the pipeline-free version, with incremental copy built in. Use it for "move these tables every hour", and a pipeline when the copy is one step of a longer process.

## Incremental loads: watermarks and change data capture

An **[incremental load](gl:incremental-load)** copies everything once, then only what changed since the last successful run. There are two ways to find the changes.

A **watermark** is a column that only ever goes up: `LastModified`, an identity, or a `rowversion`. Each run copies the rows above the last value it saw, then stores the new high value. It is simple and works on almost any table. It has one blind spot: ==a watermark sees inserts and updates, never deletes, because a deleted row has no timestamp left to read.== It also trusts every update to set `LastModified`, including the one run by hand.

**[Change data capture](gl:change-data-capture)** (CDC) is the SQL Server feature you may already know. The engine reads its transaction log and writes every insert, update and delete to change tables, which a Copy job merges into the destination, deletes included. The cost is on the source: more log, change tables to clean up, and admin rights to enable it.

Mirroring is built on the same idea. For SQL Server 2016 to 2022 it uses CDC under the covers. For SQL Server 2025 and Azure SQL Database it reads changes from the log itself, and Azure SQL Database cannot be mirrored while CDC is switched on.

## Behind the firewall, and which Data Factory

The Daventry SQL Server does not accept connections from the internet, and should not. The **[on-premises data gateway](gl:on-premises-data-gateway)** is a Windows service inside the network that makes outbound connections to Azure and fetches data on Fabric's behalf, so no inbound firewall rule is needed. One gateway serves Power BI, dataflows, pipelines, Copy jobs and mirroring. Cluster two machines, or it is a single point of failure.

**[Azure Data Factory](gl:azure-data-factory)** (ADF) is the older, standalone Azure service with the same pipelines. Its gateway equivalent is the self-hosted **[integration runtime](gl:integration-runtime)**; the two are not interchangeable. Microsoft calls Fabric's Data Factory the next generation of ADF, and new features such as Copy job and mirroring land there. ADF is still supported, is billed per activity run and data movement rather than by capacity, and still runs SSIS packages on its Azure-SSIS integration runtime. Fabric's SSIS support is in preview.

## In practice

Tom's new design:

- **Orders: mirrored.** ![Azure SQL](az:azure-sql) The four-hour job is switched off. Finance sees orders a minute old, not a day.
- **Stock: a Copy job on a watermark.** ![SQL Server](az:sql-server) The ERP runs SQL Server 2019, where mirroring needs CDC, and the vendor will not support CDC. So an hourly Copy job merges rows by `LastModified` through the gateway, and a weekly copy of the item keys finds deletions.
- **Campaigns: Dataflow Gen2.** A daily dataflow flattens the paged API into a table. A few thousand rows; speed does not matter.
- **The clickstream** already arrives through Event Hubs Capture ([lesson 5.4](lesson:5.4)).

**What it costs.** Mirroring costs nothing to replicate. Copy jobs and dataflows draw on the [Fabric capacity](gl:fabric-capacity) while they run. The gateway needs two small Windows machines. The biggest saving is on the orders database: no four-hour read every night.

**What breaks.**

- **Schema drift.** An ERP upgrade renames a column; the Copy job fails at 02:00 or loads nulls. A mirrored table whose schema changes is re-seeded from scratch. Alert on failures.
- **Deletes not captured.** Watermark loads keep cancelled lines forever unless something reconciles them.
- **Load windows.** A job that "always finishes by six" stops finishing as data grows. Watch run times monthly.
- **A paused capacity.** Pause the capacity to save money and mirroring stops.
- **Long-running transactions** on a mirrored or CDC source hold the log, so it grows. Watch it.

## Map it to what you know

| You already know | In Fabric and Data Factory |
|---|---|
| An SSIS package's control flow | A data pipeline |
| A data flow task with an OLE DB source and destination | A copy activity, or a Copy job |
| A SQL Server Agent job on a schedule | A pipeline or Copy job schedule |
| Transactional replication to a reporting server | Mirroring, but into OneLake as Delta tables |
| `WHERE LastModified > @LastRun` | A watermark incremental load |
| A linked server through the firewall | An on-premises data gateway connection |

## Guiding your team

> [!TEAM]
> Before anyone builds an ingestion job, ask:
>
> 1. **Can this source be mirrored?** If it can, there is nothing to build, schedule or fix at 02:00.
> 2. **How are changes found: a watermark, CDC or a full copy?** This decides the source load and whether deletes arrive.
> 3. **How will deletes and schema changes reach the lake?** Both fail quietly unless someone designed for them.
> 4. **How fresh must this be, and how long does a run take today?** Write both down; the gap is your safety margin.
> 5. **Who owns the gateway, and is it clustered?** It is the single door to every on-premises source.

## Key takeaways

- Mirror a supported database first: near-real-time changes into OneLake, with free replication compute.
- Use a Copy job or a pipeline copy activity for sources you cannot mirror, and Dataflow Gen2 for small, messy or SaaS sources.
- Replace nightly full copies with incremental loads. Watermarks are simple but miss deletes; CDC captures deletes at a small cost on the source.
- The on-premises data gateway reaches data behind a firewall for Fabric and Power BI; the self-hosted integration runtime does it for ADF.
- Fabric Data Factory is where new features land; ADF is still supported and still runs SSIS packages.
- Design for schema drift, deletes, load windows and a paused capacity before they happen.
