## Why this matters

> [!SCENARIO] "Put it all in Cosmos, it's the global one"
> The shop is opening in Ireland and Australia. Shoppers in Sydney wait 300 ms for every catalogue call because the API and the SQL database both live in UK South. A contractor's proposal is one line long: move everything to Cosmos DB, because "that is the globally distributed database".
>
> Dev, the ops lead, has two worries. The pricing calculator estimate is four times the current Azure SQL bill, and the proposal uses `tenantId` as the partition key - with one tenant, the UK shop, holding 95% of the data. Priya needs to say which data belongs in Cosmos DB, which stays in [Azure SQL](gl:azure-sql-database), and why - before the review on Thursday.

## What Cosmos DB is, and who needs it

![Cosmos DB](az:cosmos-db) **Cosmos DB** is Microsoft's globally distributed [NoSQL](gl:nosql) database. It stores JSON items, replicates them to whichever regions you tick, reads and writes in single-digit milliseconds, and scales throughput and storage independently with no schema to migrate. It is the database behind Microsoft 365 and Xbox, and it is priced for that shape of problem.

Be honest with your team: ==most systems do not need Cosmos DB, and using it for relational data is the most expensive way to get a worse database.== It earns its place when data must be **close to users in several regions**, when **write volume** would flatten a single SQL instance, or when the **shape of the data varies** (a catalogue with different attributes per category is the classic case). Baskets, sessions, catalogues and event logs fit. Orders, stock and finance - with their joins and transactions - stay relational.

One account exposes one of six **[Cosmos DB APIs](gl:cosmos-db-api)**. **NoSQL** is the native one; pick it for anything new. MongoDB, PostgreSQL, Apache Cassandra, Apache Gremlin (graph) and Table exist so that existing code and drivers can move without a rewrite; each hides some Cosmos DB features and adds its own quirks.

The resource model is four levels deep: an **account** (the endpoint, keys, regions and default consistency) holds **databases**, which hold **containers**, which hold **items**. The container is the unit that matters. It owns the partition key, the throughput, the indexing policy and the TTL. Items are plain JSON up to 2 MB, and every property is indexed by default.

## Request units and the partition key

Cosmos DB does not sell CPU. It sells **[request units](gl:request-unit)** (RU): one RU is roughly the cost of reading a 1 KB item by id and partition key. A 1 KB write costs about five RU; a query costs whatever it reads. Throughput is bought in RU per second. Ask for more in a second than you bought and Cosmos DB does not queue the request - it answers **HTTP 429**, "request rate too large", with a `retry-after` header. The SDK retries nine times before your Node code sees the error. A 429 in the metrics is a sizing signal or, far more often, a partition problem.

The **[partition key](gl:partition-key)** is the one decision you cannot undo. Every item with the same key value forms a **[logical partition](gl:logical-partition)**, capped at 20 GB. Cosmos DB packs logical partitions on to physical ones, each capped at 10,000 RU/s and 50 GB, and spreads a container's throughput evenly across them. A good key has three properties:

| Property | Why it matters | For the basket container |
|---|---|---|
| **High cardinality** | Many distinct values, so data spreads across many partitions | `/userId` - millions of values |
| **Even spread** of storage *and* requests | One busy value becomes a **[hot partition](gl:hot-partition)** that returns 429s while the container sits at 15% utilisation | `/country` fails: the UK would take most of the traffic |
| **Appears in your hottest queries** as an equality filter | A query with the key runs on one partition; without it, Cosmos DB fans out to every partition and bills for each | `/userId` - the basket is always fetched by user |

## Consistency, regions and the change feed

A distributed database has to say what "read after write" means. Cosmos DB gives you five **[consistency levels](gl:consistency-level)**, set per account and relaxable per request:

| Level | Guarantee | Cost |
|---|---|---|
| **Strong** | Every read sees the latest committed write, in every region | Highest [latency](gl:latency); reads cost 2x RU; not available with multi-region writes |
| **Bounded staleness** | Reads lag by at most *K* versions or *T* seconds | Reads cost 2x RU |
| **Session** (default) | You always read your own writes within a session; others may lag | Normal RU |
| **Consistent prefix** | Never out of order, but may be stale | Normal RU |
| **Eventual** | Cheapest, fastest, may be stale and out of order | Normal RU |

==Session is the sane default: a shopper sees the item they just added to their basket, and nobody pays double for reads.== Reach for strong only when two users in two regions must agree on one value at once, which is rare in a shop and expensive everywhere.

Regions are a checklist on the account. Add Australia East and shoppers in Sydney read locally. Turn on **[multi-region writes](gl:multi-region-writes)** and they write locally too, with last-writer-wins or a custom policy resolving conflicts. A single-region account carries a 99.99% [SLA](gl:sla); with multi-region writes it is 99.999% for reads and writes - the highest of any Azure data service, and you pay for every copy.

Two features turn a container into more than a store. The **[change feed](gl:change-feed)** is an ordered log of inserts and updates per container, read by an [Azure Functions](gl:azure-functions) [trigger](gl:trigger). It is how you update a search index, build a materialised view of "orders per product", or publish events without a second write path. Deletes are not in the default feed; use TTL as a soft delete. **[Time to live](gl:time-to-live)** (TTL) is a container default with a per-item override; expired items are removed in the background using spare RU, so baskets that vanish after 30 days cost nothing to clean up.

## In practice

You create one account per environment in `rg-shop-prod`, choose the NoSQL API, tick UK South, and add a database with one container per aggregate: `baskets` (`/userId`, TTL 30 days), `catalogue` (`/productId`, no TTL). Three capacity modes decide the bill:

| Mode | How it bills | Fits |
|---|---|---|
| **[Provisioned throughput](gl:provisioned-throughput)** (manual) | A fixed RU/s per container or database, minimum 400, billed per hour whether used or not. Roughly $0.008 per 100 RU/s-hour, so 400 RU/s is about $24 a month per region | Steady, predictable load |
| **[Autoscale throughput](gl:autoscale-throughput)** | Set a maximum; Cosmos DB scales between 10% and 100% of it and bills the peak each hour at about 1.5x the manual RU rate | Spiky production traffic, which is most of it |
| **[Cosmos DB serverless](gl:cosmos-db-serverless)** | Pay per million RU consumed (around $0.25) plus storage, no minimum, single region, capped burst per container | Dev, test, and low-traffic apps |

Storage is around $0.25 per GB-month per region. Every extra region multiplies throughput and storage: 4,000 RU/s in three regions is three bills, not one. The **free tier** - the first 1,000 RU/s and 25 GB on one account per subscription - covers a real dev environment for nothing.

What breaks, in the order you will meet it:

- **Cross-partition fan-out.** A query without the partition key runs in every physical partition and bills for each: at 50 partitions, fifty reads for one answer.
- **A partition key with one giant value.** `tenantId`, `country`, `status`, `date` - anything with few values or one dominant value becomes a hot partition.
- **Unbounded document growth.** A `user` item with an ever-growing `orders` array heads for the 2 MB item limit and the 20 GB logical partition limit. Put unbounded lists in their own items.
- **Treating it as SQL Server.** No joins across items, no cross-partition transactions, no `ALTER TABLE` to fix a key. Model for the queries, or stay relational.

> [!WARNING] The indexing tax
> Every property is indexed by default, and every index costs write RU. A catalogue item with 200 attributes pays for 200 index updates per write. Exclude the paths you never query - it is the cheapest optimisation in the product.

## Map it to what you know

| You already know | In Cosmos DB |
|---|---|
| A table with a schema | A **[document database](gl:document-database)** container: a collection of JSON, no schema, each item can differ |
| A row | An item - the JSON your Node API already sends, plus `id`, `_ts` and `_etag` |
| Choosing the clustered index | The partition key: decided at creation, changed only by creating a new container and migrating |
| [DTU](gl:dtu) on Azure SQL | RU - a blended unit of work, but metered per request, not per hour |
| `JOIN` across tables | Not there. Embed what is read together; reference what changes independently |
| An availability group failover | Regions ticked on the account; failover is automatic and replication is built in |
| A `DELETE WHERE created < ...` job | TTL on the container |

## Guiding your team

> [!TEAM]
> Before anyone provisions a Cosmos DB account, ask:
>
> 1. **What does this data need that Azure SQL cannot give it?** If the answer is not "several regions", "extreme write rate" or "genuinely variable shape", stop.
> 2. **Show me the top five queries and the partition key on one whiteboard.** Every hot query should carry the key; every value should stay small.
> 3. **Which consistency level, and who justified it?** Session unless someone can name the conflict strong prevents.
> 4. **Who watches the 429 and normalised RU consumption metrics?** A container at 15% with 429s is a hot partition, not a capacity problem.
> 5. **Which regions, and has finance seen the multiplier?** Each region is another full copy of throughput and storage - and is TTL set on every transient container?

## Key takeaways

- Cosmos DB is a globally distributed, schema-flexible JSON store priced in request units; most systems do not need it, and relational data should stay in Azure SQL.
- The partition key is the decision you cannot change: high cardinality, even spread, and present in your hottest queries. A dominant value is a hot partition, and 429s at low utilisation are its signature.
- Session consistency is the default and the right answer almost every time; strong doubles read cost and rules out multi-region writes.
- Multi-region writes buy a 99.999% SLA and local latency everywhere, and every region is a full extra copy of the bill.
- Autoscale for production, serverless for low traffic, the free tier for dev; TTL and the change feed turn a container into a self-cleaning event source.
