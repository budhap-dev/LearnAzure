## Why this matters

> [!SCENARIO] Port 3389, open to the world
> The shop's first penetration test comes back with two findings marked critical. The warehouse VM from [lesson 2.1](lesson:2.1) has a [public IP](gl:public-ip-address) with RDP open to "Any", and its security log shows forty thousand failed logins a day. And the orders database still accepts connections from "all Azure services", which means any Azure customer's code, not just the shop's.
>
> Dev, the ops lead, wants to fix both by "putting everything in a VNet". Then he finds that last year's dev network and this year's prod network both use `10.0.0.0/16` - the same range as the office - so none of them can ever be joined up.
>
> Priya needs a network design the team can grow into, and a rule for who may open which port.

## A private network you rent by the region

A **[virtual network](gl:virtual-network)** (VNet) is your own private network inside one Azure region. You give it an **address space** - a block of private IP addresses written in **[CIDR notation](gl:cidr-notation)**, such as `10.20.0.0/16` - and carve that into **[subnets](gl:subnet)**. Resources that sit in a subnet, such as a virtual machine's network card, get a private IP from it and can talk to anything else in the VNet by default.

The VNet itself costs nothing. It is a boundary and an address plan, not a device: traffic between resources in it runs over Microsoft's network, and nothing you can patch or lose sits in the middle.

| CIDR | Addresses | Usable in Azure | Typical use |
|---|---|---|---|
| `/16` | 65,536 | - | One VNet per workload and environment |
| `/24` | 256 | 251 | A large subnet |
| `/26` | 64 | 59 | Azure Bastion's subnet; App Service integration (recommended) |
| `/27` | 32 | 27 | A small VM or private-endpoint subnet |

Azure keeps five addresses in every subnet (the first four and the last), so a `/29` gives you three. Some services need a subnet of their own, **delegated** to them and of a minimum size: App Service's [VNet integration](gl:vnet-integration) from [lesson 2.2](lesson:2.2), Container Apps environments, Azure Bastion (which insists on the name `AzureBastionSubnet`).

==Plan the address space before the first VNet exists: ranges must never overlap anything you might one day connect - other VNets, the office, a partner's network.== Adding a range later is possible; renumbering a subnet full of resources is a rebuild.

## Network security groups: the firewall on every subnet

A **[network security group](gl:network-security-group)** (NSG) is a list of allow and deny rules attached to a subnet or a network card. Each rule names a source, a destination, a port, a protocol and a **priority** from 100 to 4096; Azure evaluates them in priority order and the first match wins. NSGs are **stateful**: allow a request in and the reply goes out without a rule of its own.

Every NSG starts with three hidden inbound defaults: allow traffic from inside the VNet, allow Azure's load-balancer health probes, **deny everything else**. So a new VM with an NSG and no public IP is already closed; exposure is always something someone added.

Two features keep the rules readable:

- **[Service tags](gl:service-tag)** name Microsoft-maintained address ranges - `Internet`, `VirtualNetwork`, `AzureLoadBalancer`, `Sql.UKSouth`, `Storage` - so nobody pastes IP lists that go stale.
- **[Application security groups](gl:application-security-group)** (ASGs) let a rule say "from web servers to database servers" instead of listing addresses, and new VMs join by tag.

For the warehouse subnet, the whole NSG is three rules:

| Priority | Direction | Source | Destination | Port | Action |
|---|---|---|---|---|---|
| 100 | Inbound | `AzureBastionSubnet` range | `snet-vm` | 3389 | Allow |
| 110 | Inbound | Office VPN range | `snet-vm` | 443 | Allow |
| 4000 | Inbound | Any | Any | Any | Deny (explicit, so it shows in the portal) |

> [!WARNING] What an NSG cannot see
> An NSG filters on addresses, ports and protocols. It does not read HTTP, so it cannot stop SQL injection or a bad bot - that is a web application firewall ([lesson 4.2](lesson:4.2)). And if a NIC and its subnet both have an NSG, traffic must pass both; half the "port is open but it still does not work" tickets are the second NSG nobody remembered.

## Getting in, getting out, and joining networks up

**In, for admins.** **[Azure Bastion](gl:azure-bastion)** gives RDP and SSH through the portal over HTTPS, so VMs need no public IP and port 3389 is never on the internet. Basic is roughly $140 a month; a free Developer tier covers dev and test.

**Out, to the internet.** A VM without a public IP historically still reached the internet through a shared, unpredictable address. Azure is retiring that "default outbound access": new subnets are becoming private by default. A **[NAT gateway](gl:nat-gateway)** gives a subnet explicit outbound access through static public IPs a partner can allowlist, for around $32 a month plus a few cents per GB.

**Between VNets.** **[VNet peering](gl:vnet-peering)** joins two VNets over Microsoft's backbone at close to local latency, charged at about a cent per GB each way. Peering is **not transitive**: if A peers with B and B with C, A still cannot reach C.

That is why larger estates use **[hub-and-spoke](gl:hub-and-spoke)**. The hub VNet holds shared things - the VPN gateway to the office, an **[Azure Firewall](gl:azure-firewall)**, Bastion - and each workload or environment is a spoke peered to it. **[User-defined routes](gl:user-defined-route)** send spoke traffic through the firewall, which is how spoke-to-spoke and internet traffic gets inspected and logged.

Azure Firewall Standard costs roughly $900 a month before traffic, so a hub is a decision, not a default. One workload in one region needs one VNet and good NSGs; the hub earns its place with the second workload, the office connection, or a compliance rule that all outbound traffic is inspected.

## In practice

For the shop, Priya's design is: one VNet per environment, `10.20.0.0/16` for prod and `10.21.0.0/16` for dev, both clear of the office's `192.168.0.0/16`, with the plan recorded in one shared sheet. Four subnets as in the first diagram, an NSG on every subnet with an explicit deny, Bastion for the one VM, and no public IP on anything that is not a front door.

**What it costs.** VNets, subnets, NSGs and route tables are free. The bills are the managed devices - Bastion, NAT gateway, VPN gateway, Azure Firewall - plus peering and outbound traffic per GB. A single-VNet design with Bastion costs about $140 a month; a hub with a firewall starts near $1,000.

**What breaks.**

- **Overlapping ranges.** Two VNets on `10.0.0.0/16` can never peer. The fix is renumbering, which means rebuilding.
- **Management ports open to Any.** RDP or SSH from the internet is found by scanners within minutes. Use Bastion and deny by default.
- **Subnets sized for today.** App Service integration and Container Apps take an address per instance; a `/28` blocks scale-out on a busy day.
- **Believing PaaS is "in the VNet".** VNet integration is outbound only: the API can reach into the VNet, but the API and the database keep their public endpoints until [lesson 4.3](lesson:4.3)'s private endpoints close them.
- **No flow logs.** Without Network Watcher flow logs, "was that blocked?" is a guess.

## Map it to what you know

| You already know | On Azure |
|---|---|
| The office LAN and its VLANs | A VNet and its subnets |
| Windows Firewall rules or a router ACL | A network security group |
| A jump box everyone RDPs into | Azure Bastion, with no public IP anywhere |
| A static route on the office router | A user-defined route in a route table |
| A leased line between two offices | VNet peering - but not transitive |
| Your home router's NAT | A NAT gateway |
| A Docker Compose network the containers share | A VNet: private addresses, reachable only from inside |

## Guiding your team

> [!TEAM]
> Before anyone creates a VNet, ask:
>
> 1. **Who owns the IP plan, and where is it written down?** Every range, every environment, the office and any partner. Overlap is permanent.
> 2. **Which rules allow traffic from `Internet` or Any, and why?** Anything on 22 or 3389 is a finding, not a rule.
> 3. **Is there an NSG on every subnet, ending in an explicit deny?** Default-closed is the posture; each allow names its source.
> 4. **Do we need a hub yet?** One workload in one region does not. A second workload, an office link or mandatory inspection does.
> 5. **Which PaaS services still have public endpoints?** List them now; [lesson 4.3](lesson:4.3) is how they close.

## Key takeaways

- A VNet is a free, regional private network with an address space you carve into subnets. Azure keeps five addresses per subnet, and some services need a delegated subnet of a minimum size.
- Plan non-overlapping address ranges before the first VNet exists; overlap blocks peering and VPNs for good.
- NSGs are stateful allow/deny lists evaluated by priority, deny inbound by default, and use service tags and ASGs instead of raw IPs. They do not inspect HTTP.
- Bastion replaces public RDP and SSH; a NAT gateway gives predictable outbound IPs.
- Peering is fast and cheap but not transitive. Hub-and-spoke with a firewall and user-defined routes is for when there is more than one workload to connect, and it costs real money.
- VNet integration lets PaaS reach in, not the world reach PaaS privately - private endpoints do that.
