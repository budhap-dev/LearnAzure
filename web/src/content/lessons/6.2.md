Dev cannot get answers out of it: "it looks like SQL but it isn't", so he exports rows to CSV and pivots them in Excel. And the first month's bill for the workspace is $900, three times the estimate, and nobody can say which logs caused it.
>

## Tables in a workspace

A Log Analytics workspace is a database of append-only tables, one per kind of record, each with a `TimeGenerated` column. You will meet the same handful again and again:

| Table | Holds |
|---|---|
| `AppRequests`, `AppDependencies`, `AppExceptions`, `AppTraces` | Application Insights telemetry ([lesson 6.3](lesson:6.3)) |
| `AzureActivity` | The activity log: who changed what in Azure |
| `AzureDiagnostics` and resource-specific tables such as `AppServiceHTTPLogs` | Resource logs from diagnostic settings |
| `Event`, `Perf`, `Syslog`, `Heartbeat` | VM data from the Azure Monitor Agent |
| `Usage` | How much data each table ingested - the bill, in a table |

## KQL for SQL Server people

Queries are written in **[KQL](gl:kql)**, the Kusto Query Language. It reads top to bottom as a **pipeline**: start with a table, and each `|` passes the rows to the next step. If you can write T-SQL, you already know the ideas:

| T-SQL | KQL |
|---|---|
| `FROM AppRequests` | `AppRequests` (the table comes first) |
| `WHERE Success = 0` | `\| where Success == false` |
| `WHERE TimeGenerated > DATEADD(hour, -1, GETUTCDATE())` | `\| where TimeGenerated > ago(1h)` |
| `SELECT Name, DurationMs` | `\| project Name, DurationMs` |
| `SELECT COUNT(*) ... GROUP BY Name` | `\| summarize count() by Name` |
| `COUNT(DISTINCT UserId)` | `dcount(UserId)` |
| `ORDER BY n DESC` and `TOP 10` | `\| order by n desc` and `\| take 10`, or `\| top 10 by n` |
| `LIKE '%timeout%'` | `contains "timeout"`, or the faster `has "timeout"` for whole words |
| Grouping into 5-minute buckets | `by bin(TimeGenerated, 5m)` |
| `JOIN` | `\| join kind=inner (...) on operation_Id` |
| `CASE WHEN` | `iff()` or `case()` |

==Always filter on time first: `where TimeGenerated > ago(...)` as the first line after the table is the difference between a query that returns in a second and one that scans months.==

## Five queries every team needs

**1. What is failing right now?**

```kusto
AppRequests
| where TimeGenerated > ago(1h) and Success == false
| summarize failures = count() by Name, ResultCode
| order by failures desc
```

**2. What does the error rate look like today?**

```kusto
AppRequests
| where TimeGenerated > ago(24h)
| summarize total = count(), failed = countif(Success == false) by bin(TimeGenerated, 5m)
| extend errorRate = round(100.0 * failed / total, 2)
| render timechart
```

**3. Which dependency is slow?** The 95th percentile, because averages hide the shoppers who wait.

```kusto
AppDependencies
| where TimeGenerated > ago(1h)
| summarize p95 = percentile(DurationMs, 95), calls = count() by Target, Name
| top 10 by p95 desc
```

**4. What changed?** The first question in any incident.

```kusto
AzureActivity
| where TimeGenerated > ago(6h) and OperationNameValue endswith "/write"
| project TimeGenerated, Caller, OperationNameValue, ResourceGroup
| order by TimeGenerated desc
```

**5. What is costing us?** The `Usage` table records the billable volume of every table.

```kusto
Usage
| where TimeGenerated > ago(30d) and IsBillable == true
| summarize GB = round(sum(Quantity) / 1000, 1) by DataType
| order by GB desc
```

For the shop, query 5 explained the $900 in one screen. `AppServiceHTTPLogs` was 58% of the volume. It duplicated what Application Insights already records per request, at far higher volume.

## Saving it: queries, functions and workbooks

A query run once is an answer. A query saved is a tool. Save the team's queries in the workspace, keep them in Git too, and wrap repeated logic in **functions** that others can call like a table.

An **[Azure Workbook](gl:azure-workbook)** turns queries into an interactive report: parameters for time range and environment, charts, grids and links to the resources involved. The shop's *Shop health* workbook shows requests, error rate, p95 latency, Service Bus queue depth, WAF blocks and ingestion by table on one page. It is the first thing opened in an incident, and the last thing checked before a release.

## Paying for logs deliberately

The bill has three levers.

**What you collect.** The cheapest GB is one never ingested. Drop duplicate categories, such as HTTP logs when Application Insights records requests. Use data collection rule **transformations** to discard noisy rows or unneeded columns before they are billed.

**The [table plan](gl:log-table-plan).** Every table has a plan:

| Plan | Cost per GB | You can | Use for |
|---|---|---|---|
| **Analytics** | Full price, about $2.30-2.80 | Query anything fast, alert, join | Data you investigate and alert on |
| **Basic** | Roughly a quarter, plus a charge per GB scanned by queries | Query with limits; no alerting | High-volume logs read occasionally |
| **Auxiliary** | Lowest | Occasional search | Verbose logs kept for audit or compliance |

**[Log retention](gl:log-retention).** Analytics tables keep data for 31 days at no extra charge, and interactive retention can be extended to two years. Beyond that, **long-term retention** keeps data for up to 12 years at a fraction of the price, to be searched or restored when needed. Audit logs that must be kept for years belong there, not in interactive retention.

At steady volume, a **[commitment tier](gl:commitment-tier)** - from 100 GB a day upwards - discounts ingestion in exchange for a daily commitment. It is worth it only when volume is predictable.

## In practice

The shop's changes after the first bill:

- `AppServiceHTTPLogs` switched off, since Application Insights covers requests; storage logs reduced to writes and deletes.
- Front Door access logs moved to the Basic plan and kept for 30 days; WAF logs stay on Analytics, because they are alerted on.
- Key Vault audit events and the activity log kept for a year, 90 days interactive and the rest in long-term retention.
- Twenty saved queries and the *Shop health* workbook in Git, deployed with the infrastructure.

The workspace bill falls from $900 to about $280 a month, and nobody loses a query they actually use.

**What breaks.**

- **No time filter.** Slow queries, timeouts, and on Basic tables a charge for every GB scanned.
- **`contains` everywhere.** It scans every character; `has` uses the term index and is much faster for whole words.
- **Alerting on a Basic table.** Basic and Auxiliary tables cannot drive alert rules; keep alerted data on Analytics.
- **Retention shorter than the auditor's question.** Check retention against compliance requirements before an audit, not during one.
- **Everyone's personal queries.** Knowledge that lives in one engineer's browser history leaves with them. Save and share.

| You already know | In Log Analytics |

## Key takeaways

- A workspace is a set of append-only tables; the same dozen cover most investigations, and `Usage` shows what they cost.
- KQL is a pipeline: table, then `where`, `summarize`, `project`, `order by`, `render`. It maps closely onto T-SQL.
- Filter on time first, prefer `has` to `contains`, use percentiles rather than averages, and save the queries that matter.
- Workbooks turn queries into the page everyone opens first.
- Control cost by collecting less, choosing table plans (Analytics, Basic, Auxiliary), setting retention deliberately and using commitment tiers when volume is steady.
